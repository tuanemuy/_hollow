# 動作確認計画 — Issue #363: 取り込みのディレクトリ提案: 新規ネストパス（多階層）の作成をサポートする

**Issue:** #363
**作成日:** 2026-05-31

---

## 確認環境

このIssueの変更を確認するために必要な手順のみ記載。

### 検証環境の起動

```bash
pnpm db:migrate   # ローカル D1 にマイグレーション適用（初回 / 未適用時のみ）
pnpm dev          # vite dev (Cloudflare 構成) でローカルサーバー起動
```

取り込み（アップロード）は P13 モーダル（ヘッダーの「アップロード」CTA → `UploadDialog` / `IngestionPreviewForm`）から行う。ジョブ一覧の「そのまま登録」（クイックコミット）は `IngestionJobRow` から行う。

### LLM 接続の前提

LLM が新規ネストパスを提案するか（確認項目1）は Anthropic 等への接続が成立している必要がある。`P41 管理: LLM 設定画面` の接続テストが成功している状態で確認する。接続不可の環境では、プレビューフォームに手動でネストパスを入力する経路（確認項目2以降）で検証する。

### デプロイ方法

なし（検証環境のみで確認できる。staging 反映は通常の `pnpm deploy:staging` フローに従う）。

## 確認項目

### 1. LLM が新規ネストパスを提案できる

- **目的:** 既存ツリーに該当が無い内容で、`技術/AI` のような多階層パスが提案されること（プロンプト制約解除）
- **手順:**
  1. 既存ディレクトリにマッチしない内容のサンプル（例: 専門的なネスト構造が自然な内容）を取り込む
  2. プレビューフォームのディレクトリ提案欄を確認する
- **期待結果:** 新規提案が単一名だけでなく `親/子` のような `/` 区切りパスになりうる（内容に応じて）
- **確認ポイント:** 既存ツリーに完全一致がある場合は従来どおり既存ディレクトリが選択済みで提示される（新規ネストへフォールバックしない）

### 2. 新規ネストパスをそのまま作成してコミットできる

- **目的:** プレビューフォームで `技術/AI` を確定すると、root→技術→AI が作成され末端にノートが入ること（resolveDirectoryId のネスト ensure）
- **手順:**
  1. サンプルを取り込み、プレビューフォームの新規ディレクトリ入力に `技術/AI` を入力して登録する
  2. 登録後、ディレクトリツリー / ノート詳細で配置先を確認する
- **期待結果:** `技術` の下に `AI` が作成され、ノートが `技術/AI` 配下に入る
- **確認ポイント:** 中間ディレクトリ（技術）も実体として作成されていること

### 3. 既存ディレクトリへの部分合流

- **目的:** 親が既存・末端が新規のとき、既存親を再利用して末端のみ新規作成されること
- **手順:**
  1. 事前に `技術` ディレクトリを作っておく
  2. 取り込みフォームで新規ディレクトリ入力に `技術/機械学習` を入力して登録する
- **期待結果:** 既存の `技術` が再利用され、その下に `機械学習` だけが新規作成される（`技術` が重複作成されない）
- **確認ポイント:** ディレクトリツリーに `技術` が1つだけ存在し、配下に `機械学習` が追加されている

### 4. クイックコミット（そのまま登録）経由のネストパス作成

- **目的:** ジョブ一覧の「そのまま登録」でも提案されたネストパスがそのまま作成されること（`IngestionJobRow` 経路）
- **手順:**
  1. LLM がネストパスを提案したジョブを、プレビューを開かず一覧の「そのまま登録」で確定する
  2. 配置先を確認する
- **期待結果:** 提案された `親/子` パスが作成され、ノートが末端に入る
- **確認ポイント:** プレビューフォーム経由と同じ結果になること

### 5. DirectoryPicker の入力ヒント（ingestion 側のみ）

- **目的:** 取り込みプレビューの新規ディレクトリ入力に「`/` 区切りで階層指定」のヒントが出ること
- **手順:** プレビューフォームの新規ディレクトリ入力欄のラベル/placeholder を確認する
- **期待結果:** `/` 区切りで階層を指定できる旨が示される（例 `技術/AI`）

## エッジケース・異常系

### 1. 深さ上限超過（ユーザー手入力）

- **目的:** `MAX_DIRECTORY_DEPTH`（=10）を超えるパスを手入力して登録すると業務エラーになること
- **手順:** 新規ディレクトリ入力に 11 階層以上のパス（`a/b/c/.../k`）を入力して登録する
- **期待結果:** フォーム内に inline で `TooDeep` 系の業務エラーが表示され、コミットが失敗する（クラッシュしない）

### 2. 不正セグメント・空パスの正準化

- **目的:** `技術//AI`、` /技術/AI/ ` のような表記揺れが正準化されること
- **手順:** 新規ディレクトリ入力に重複スラッシュ・前後スラッシュを含むパスを入力して登録する
- **期待結果:** 空セグメントが除去され `技術/AI` として正しく作成される。全セグメントが空なら新規作成されず root 配置になる

### 3. 深すぎる LLM 提案（非致命）

- **目的:** LLM が深すぎる/長すぎるパスを提案した場合に取り込みが落ちないこと
- **手順:** （再現可能なら）LLM が 11 階層以上を提案するケースを確認する
- **期待結果:** プレビュー段階では提案が採用されず（無提案 = root フォールバック等）、取り込みジョブ自体は完走する

## 既存機能への影響確認

- NoteEditor 通常編集のディレクトリ作成が従来どおり単一名で動作すること（`allowNestedPath` 未指定で `/` を含む入力は従来どおり禁止文字エラー）
- 既存ツリー完全一致時の id 解決提案が従来どおり動くこと（ADR-005 のマッチ順序）
- 単一名（`/` 無し）の新規提案も 1 セグメントのネストパスとして矛盾なく作成されること（後方互換）
- 取り込みパイプライン全体（各ファイル分岐）が従来どおり完走すること
