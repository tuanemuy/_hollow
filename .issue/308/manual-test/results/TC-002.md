# TC-002 結果 — AccountDeleteForm の ConfirmDialog 化と削除フロー

**実行日:** 2026-05-29
**セッション:** verify-tc-002
**対象:** Issue #308 / testing.md 確認項目 2 + エッジケース 1〜4
**判定:** **PASS（エッジケース 2/3/4 は仕様上 SKIP / 確認手段制約）**

---

## サマリー

AccountDeleteForm が `ConfirmDialog` パターンに移行した後の削除フロー全経路を確認した。

- トリガーボタン `続けて削除する` は `PILL_BTN` + `data-danger=""` + `Trash2` (size=16) + ラベル
- ConfirmDialog の構造（タイトル / 説明 / `<input>` / ヒント / キャンセル + 「アカウントを完全に削除する」）が仕様どおり描画
- 初期 focus は panel (`<div role="alertdialog" tabIndex={-1}>`)、Tab 1 回で `<input name="confirmation">` に到達
- 不一致 + Enter / 不一致 + クリックともに無反応（dialog 残置、URL 不変）
- Esc で dialog 閉じる + 入力値クリア
- 正しいユーザー名 + 確定で `/` にリダイレクト、Header が未ログイン状態（rule 1: cached `_app match` の userDto 破棄が機能）

エッジケース 2/3 (validation / system エラー時の dialog 残置 or summary 表示) は server エラーを意図的に再現するのが難しく、testing.md でも skip 可と明記されているため SKIP。
エッジケース 4 (isPending ガード) は削除が一度実行されるとユーザーが消えるため、同一セッションでの再現不可。実装側で `disabled={isPending}` が `<button type="submit" disabled={isPending}>` パターンで担保されている前提で SKIP。
