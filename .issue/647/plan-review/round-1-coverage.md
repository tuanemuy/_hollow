# Round 1 レビュー — Issue #647 計画（視点: 要件カバレッジ・スコープ整合性）

**対象:** `.issue/647/plan.md` / `.issue/647/adr.md`
**Issue:** #647 「SectionErrorBoundary で捕捉したセクション失敗を本番で観測可能にする」
**レビュー日:** 2026-06-14

---

## レビューの前提（Issue 要件の抽出）

`gh issue view 647` の本文から、合意済み要件を抽出した（コメントは0件＝本文が唯一の合意源）。

- R1: `SectionErrorBoundary` に `componentDidCatch` を追加する。
- R2: 「セクション名＋発生回数程度の最小情報」を「計測エンドポイント or 構造化ログ」へ送る。
- R3: redaction 前提のため、エラー詳細は「サーバー側ログ（worker / server fn）との突き合わせで追える設計」にする。
- 参照: `.issue/636/review/review-001.md` N-003（= SectionErrorBoundary のロギング無しは将来のテレメトリ課題）、`.issue/636/adr.md` ADR-003（= セクション失敗は client ErrorBoundary＋汎用文言＋リトライに留める。本番では React が詳細を redact する）。

この4点を AC-1〜AC-6 への落とし込みと照合した。

---

## 問題点（要修正）

- **[P-001]** AC で「発生回数（occurrence count）」要件のトレースが曖昧。Issue 本文は明示的に「セクション名**＋発生回数程度**の最小情報を…送る」と書いているが、計画は payload を `{section, scope, path}` とし、回数フィールドを持たない。計画は「発生回数程度」を AC-5（多重送信抑止＝送りすぎない）に読み替えているが、AC 表・スコープ・設計のどこにも「Issue の『発生回数』はカウント値の送信ではなく『発生ごとに1回（重複は丸める）送る』という解釈に倒した」という**明示的な解釈の宣言**がない。
  - 理由: 要件カバレッジレビューの核心は「Issue の文言が AC に検証可能な形で落ちているか」。現状、読み手が AC 表を見ても「発生回数」がどの基準に対応するのか追えない（AC-5 の由来欄は「送りすぎない」とだけ書かれ、Issue 文言「発生回数程度」との対応が明示されていない）。さらに「カウント値を送らない」という設計判断は妥当だとしても、Issue 文言からの**意図的な逸脱**なので、暗黙にせず根拠を残すべき。レビュー指示文でも「『componentDidCatch でセクション名＋発生回数程度の最小情報を送る』がきちんと受け入れ基準に落ちて検証可能か」を最重要確認事項として挙げている。
  - 提案: 次のいずれかを行う。(a) 「発生回数」をカウント値として payload に含める要件と解釈するなら、payload に件数（例: 同一境界での連続発生回数 or 1）を足し AC を追加。(b) 計画どおり「発生ごとに送る（重複抑止つき）」解釈を採るなら、スコープ「含まれないもの」または ADR に「Issue の『発生回数程度』は集計カウントの送信ではなく、発生イベントを最小情報で（重複を丸めつつ）都度送る意味と解釈する。回数の集計は ADR-002 によりログ基盤側に委ねる」と1文で明記し、AC-5 の由来欄に「Issue『発生回数程度』」を併記して検証可能性を担保する。

## 改善提案（検討推奨）

- **[S-001]** AC-2 の「redact 済みエラー詳細を送らない」が **検証可能な形**になりきっていない。「送らないこと」は negative assertion であり、テスト方針（ステップ4）にも payload に `message`/`stack` が含まれないことを assert する項目が明記されていない（現状テストは「section/scope/path 付きで1回呼ばれる」という positive 検証のみ）。
  - 理由: AC-2 は Issue の核心要件「最小情報」「redaction 前提」の直接の受け皿。漏えい防止の基準は「余計なものが入っていない」ことの検証まで含めて初めて担保される。
  - 提案: ステップ4のテスト項目に「報告 fn 呼び出し引数が `{section, scope, path}` の3キーのみで、`message`/`stack`/`error` を含まないこと」を明示的に追加し、AC-2 の検証手段とする。

- **[S-002]** AC-4（相関の成立）は plan/ADR-003 で「report は別 HTTP POST なので `cf-ray` は一致せず、時刻近接＋route+section で人手突き合わせ」と明確に設計されている点は良い一方、AC 表の文言「相関キーが成立し」が `cf-ray` ベースの自動相関を想起させ、設計本文（人手突き合わせ）と読み手の期待がずれうる。
  - 理由: AC は検証の合否を一意に決める文。表だけ読むと「相関キーで機械的に結合できる」と誤読され、レビュー/受け入れ時に齟齬が出る。
  - 提案: AC-4 の文言を「相関**手段**（時刻近接＋route path＋section 名の人手突き合わせ手順）が成立し、`docs/runtime_cloudflare.md` に手順と『cf-ray は別 POST のため主キーにしない』旨が記載されている」と、設計判断（ADR-003）に揃えて具体化する。

- **[S-003]** スコープ整合性は総じて良好だが、「報告 fn の配置」が plan 内で揺れている（ステップ1/3 は `app/components/common/sectionFailureReport.ts`、設計 §UI-2 は「または `app/core/presentation/` 配下、後述リスク参照」と二択を残す）。これはスコープ外作業ではないが、計画段階で配置が未確定だと実装時のブレ要因になる。
  - 理由: 要件カバレッジ上の欠落ではないが、AC-3/AC-6 に紐づく実装ステップの一意性が下がる。
  - 提案: ADR-004 で「presentation の transport 受け口」と判断済みなので、ファイル配置も1つに確定（`app/components/common/` 同居 or `app/core/presentation/`）し、リスク欄の二択記述を解消する。配置自体は本レビュー視点（要件カバレッジ）の範囲外なので、リスク・アーキ視点のレビューに委ねてよい。

## 良い点

- Issue 本文の R1（componentDidCatch）→ AC-1、R2（最小情報を構造化ログへ）→ AC-2/AC-3、R3（サーバー側ログとの突き合わせ）→ AC-4 と、主要3要件がそれぞれ AC へ概ね一対一で落ちており、由来欄で Issue 文言への逆引きができる。トレーサビリティの作りは良い。
- 「計測エンドポイント or 構造化ログ」の二択に対し、ADR-001 で既存 `Logger` ポート（構造化ログ）採用を CLAUDE.md「cross-cutting concerns behind ports」と `errorResponseMiddleware.logServerError` の既存パターンに基づいて根拠づけており、Issue が許した選択肢内での妥当な確定。スコープを「ログ化」に限定する判断（ADR-002: admin/metrics に載せない、永続化・集計は対象外）も Issue の「最小情報」要件と整合し、over-engineering を明確に排している。
- スコープ「含まれないもの」が4項目で明示され、それぞれ ADR で裏付けられている。特に「redact 済み詳細を client から送る経路」を明示的に対象外にしている点は、R3（redaction 前提）の趣旨と完全に一致しており、スコープへの混入もない。
- N-003 / #636 ADR-003 の参照が正確。実コード（`SectionErrorBoundary.tsx` に `componentDidCatch` 無し、`getDerivedStateFromError` のみ、ロギングゼロ）・`logger.ts`（`warn(message, meta?)` シグネチャ）・`errorResponseMiddleware`（`await getContainer()` → `logger.error(...,{kind,code,...})`）と計画記述が一致しており、調査結果に虚偽がない。
- AC-6（既存 UX・a11y 契約の不変、報告失敗が UI を壊さない）を独立基準として立て、`componentDidCatch` を副作用専用・fire-and-forget に限定する設計で担保している。回帰防止の観点が抜けていない。

## 総評

要件カバレッジ・スコープ整合性は高い。主要3要件はすべて AC に落ち、スコープ外作業の混入もなく、対象外項目が ADR で裏付けられている。唯一の要修正は **P-001（Issue 文言「発生回数程度」の解釈が AC に明示的に落ちていない）**。これは「カウントを送らない」という設計判断自体の是非ではなく、Issue 文言からの意図的な解釈変更を計画に明記して検証可能にするための指摘。S-001〜S-003 は検証可能性・文言の精度を上げる推奨。
