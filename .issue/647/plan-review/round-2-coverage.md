## 1周目指摘の解消確認

要件カバレッジ視点の指摘（P-001、S-001〜S-003）の反映状況を確認した。

- **[P-001]（要修正・解消済み）** Issue 文言「発生回数程度」の解釈が AC に落ちていない件。
  - 解消: AC-5 が「同一セクションの失敗回数（境界インスタンスごとの累積カウント）を `count` としてペイロードに含め、2回目以降に増えることをテスト検証」へ拡張され、由来欄に Issue 文言「発生回数程度」を併記（plan.md:21）。スコープ「含まれないもの」に「`count` は局所カウンタ／横断集計はログ基盤に委ねる」という解釈宣言を追記（plan.md:30）。ADR-001 にも `count` が最小情報の一部であることを明記（adr.md:12）。提案 (a)（カウント値を payload に含める）を採用した形で、検証可能性が担保された。

- **[S-001]（解消済み）** AC-2 の negative assertion。
  - 解消: AC-2 自体に「テストで『送信ペイロードが許可キーのみで `message`/`stack`/`error` を含まない』ことを assert する」を明記（plan.md:18）。ステップ4・テスト方針にも negative assertion を明示（plan.md:132, 170）。さらにステップ1でスキーマの許可キーを4つに限定し構造的にも担保（plan.md:104）。

- **[S-002]（解消済み）** AC-4 の文言が `cf-ray` 自動相関を想起させる件。
  - 解消: AC-4 が「相関する**手段**（時刻近接＋route path＋section 名による人手突き合わせ手順。`cf-ray` は別 POST のため主キーにしない）」へ修正され（plan.md:20）、設計本文・ADR-003 と一致（plan.md:94, adr.md:51）。

- **[S-003]（解消済み）** 報告 fn 配置の二択。
  - 解消: `app/components/common/sectionFailureReport.ts` に一意確定。設計 §UI-2・リスク欄・ADR-004 すべてで二択記述が消え確定表現に統一（plan.md:84, 159, adr.md:72）。

要件カバレッジ視点の1周目指摘はすべて解消されている。

## 問題点（要修正）

問題点ゼロ。

Issue の核心2点を再検証した結果、いずれも検証可能な形で AC に落ちている。

- 「componentDidCatch で最小情報（セクション名＋発生回数程度）を送る」
  - `componentDidCatch` 追加は AC-1。セクション名は payload `section`、発生回数は `count`（境界累積カウント）として AC-5 に検証可能化（2回目で増えることをテスト）。最小情報＝4キー限定＋ negative assertion（AC-2）。Issue 文言「セクション名」「発生回数程度」「最小情報」がそれぞれ AC へ一対一でトレースできる。
- 「redaction 前提でサーバー側ログとの突き合わせで追える設計」
  - redact 詳細を送らないこと＝AC-2（negative assertion）＋スコープ「含まれないもの」での明示除外。突き合わせ手段＝AC-4（時刻近接＋section 主／route path 補助の人手手順を `docs/runtime_cloudflare.md` に記載）。構造化ログ出力＝AC-3。Issue 趣旨が忠実に AC へ落ちている。

スコープ外混入も認められない。「含まれないもの」5項目（APM 基盤、汎用 correlation-ID 基盤、redact 詳細送信、サーバー側集計・時系列保存、errorResponseMiddleware 経由の通常失敗）はいずれも Issue の核心（最小情報をログへ）を超える拡張であり、各 ADR で裏付けられている。

## 改善提案（検討推奨）

改善提案ゼロ。

要件カバレッジ・スコープ整合性の観点で追加すべき推奨はない。1周目の S-001〜S-003 がすべて取り込まれ、AC のトレーサビリティ・negative assertion・文言精度・スコープ確定がいずれも十分なレベルに達している。残る論点（report fn 配置の妥当性、`useServerFn` 経由の取得経路、テストのモック方法）は本視点の範囲外であり、arch/risk 視点で扱われている。

## 良い点

- 1周目で唯一の要修正だった P-001 を、解釈を暗黙にする (b) ではなく `count` を実フィールドとして送る (a) で対応した点。「発生回数程度」という Issue 文言に対し、読み替えで逃げず Issue により忠実な解として payload に乗せたうえで、横断集計はスコープ外と明記して over-engineering も同時に回避している。要件忠実度とスコープ統制の両立として質が高い。
- AC-5 が「`count` の累積」と「多重送信抑止（同一 section+resetKey を1回に丸める）」を別概念として整理し（plan.md:116）、`count` は丸めた実報告回数を数える、と区別を明文化している。当初混同しやすかった「発生回数を送る」と「送りすぎない」の二要件が衝突なく両立する設計になっている。
- AC 表の由来欄が Issue 文言（やること1・最小情報・redaction 前提・構造化ログへ・突き合わせ・発生回数程度）へ逆引きでき、対応ステップ列とも紐づいていて、要件→基準→ステップのトレーサビリティが一貫している。
- スコープ「含まれないもの」の `count` 解釈宣言（局所カウンタであり全境界横断の総回数ではない、集計はログ基盤に委ねる）が、AC-5 の検証内容（境界インスタンス単位の増分）と齟齬なく整合している。client が送る `count` の意味論が一意に固定され、受け入れ時の解釈ブレを排除している。

---

## 総評

要件カバレッジ・スコープ整合性は高水準で、2周目として指摘すべき問題点・改善提案はない。1周目の要修正 P-001（発生回数のトレース）および改善提案 S-001〜S-003 はすべて適切に反映されており、Issue 核心「componentDidCatch で最小情報（セクション名＋発生回数程度）を送る」「redaction 前提でサーバー側ログとの突き合わせで追える設計」が検証可能な AC（AC-1〜AC-6）へ漏れなく落ちている。スコープ外の混入もなく、対象外項目は ADR で裏付けられている。本視点では承認可能。
