# 動作確認計画 — Issue #647: SectionErrorBoundary で捕捉したセクション失敗を本番で観測可能にする

**Issue:** #647
**作成日:** 2026-06-14

---

## 確認環境

このIssueの変更を確認するために必要な手順のみ記載（プロジェクト全体のセットアップは省略）。

### 検証環境の起動

サーバー側の構造化ログ（`console.warn` → Workers Logs 相当）を本番に近い形で観察したいので、Workers ランタイムで動かす:

```bash
pnpm start   # wrangler dev（Workers ランタイム。console.* がターミナルに出る）
```

ローカル DB へのマイグレーションが未適用なら先に:

```bash
pnpm db:apply:local
```

確認用の管理者ユーザーが必要な場合:

```bash
pnpm seed:dev-admin
```

> 補足: `pnpm dev`（vite dev）でもセクション分割描画自体は動くが、本 Issue の主眼である「サーバー側の構造化ログがどう出るか」を本番に近い形で見るには `pnpm start`（wrangler dev）が適切。

### デプロイ方法

本 Issue の確認は検証環境（ローカル wrangler dev）で完結する。ステージング反映が必要な場合のみ:

```bash
pnpm deploy:staging
```

## 確認項目

### 1. セクション失敗時にサーバーへ報告が送られ、構造化ログが出る

- **対応する受け入れ基準:** AC-1, AC-3
- **目的:** 境界がエラーを捕捉したとき `componentDidCatch` 経由で報告 server fn が呼ばれ、サーバー側に構造化ログが残ることを確認する。
- **手順:**
  1. いずれかのセクション RSC（例: ホームのノート一覧セクションの async サーバーコンポーネント）に一時的に `throw new Error("forced section failure")` を仕込む。
  2. `pnpm start` でサーバーを起動し、ログイン後に該当画面を開く。
  3. ブラウザ上で当該セクションが `SectionErrorBoundary` の汎用フォールバック（「◯◯を読み込めませんでした。」＋再読み込みボタン）に切り替わることを確認する。
  4. サーバーを起動したターミナルの出力を確認する。
- **期待結果:** ターミナルに `Section render failed` というメッセージと、`event: "section_failure"`, `section`, `scope`, `path`, `count` を含む構造化メタが出力される。
- **確認ポイント:** メタのキー名が `event`（`kind` ではない）であること。`section` がフォールバックに表示されるセクション名と一致すること。

### 2. 報告ペイロードに redact 済みエラー詳細が含まれない

- **対応する受け入れ基準:** AC-2
- **目的:** クライアントが送る情報が最小情報（section/scope/path/count）に限られ、`message`/`stack`/`error` を送らないことを確認する。
- **手順:**
  1. 確認項目1と同じ状態でセクション失敗を発生させる。
  2. ブラウザの DevTools → Network タブで、報告 server fn への POST リクエストのペイロードを確認する。
- **期待結果:** リクエストボディに `section`/`scope`/`path`/`count` のみが含まれ、`message`・`stack`・`error` キーは存在しない。
- **確認ポイント:** 仕込んだエラーメッセージ文字列（"forced section failure"）がペイロードのどこにも含まれていないこと。

### 3. 多重送信の抑止と count の増分

- **対応する受け入れ基準:** AC-5
- **目的:** リトライ連打・再 throw で報告がフラッディングせず、同一セクションの捕捉累積回数 `count` が増えることを確認する。
- **手順:**
  1. 確認項目1の状態（セクションが恒常的に throw する状態）でフォールバックの「再読み込み」ボタンを複数回押す。
  2. Network タブで報告 POST の発生回数と、各ペイロードの `count` 値を確認する。
- **期待結果:** 同一キー（section + resetKey）の連続報告は1回に丸められ、再 throw ごとに `count` が増分する。同一の捕捉で何件もの重複 POST が連射されない。
- **確認ポイント:** `count` が「実送信回数」ではなく「境界インスタンスの捕捉累積回数」として増えること。

### 4. ログ突き合わせ手順がドキュメント化されている

- **対応する受け入れ基準:** AC-4
- **目的:** 報告ログと、サーバー側に既に出ている RSC 原エラーログを突き合わせる手順が運用ドキュメントに書かれていることを確認する。
- **手順:**
  1. `docs/runtime_cloudflare.md` を開く。
- **期待結果:** セクション失敗の報告ログ（`Section render failed`）と RSC 原エラーログを「時刻近接＋route path＋section 名」で突き合わせる手順と、`cf-ray` は別 POST のため主キーにしない旨の注記が記載されている。

## エッジケース・異常系

### 1. 報告送信が失敗しても UI が壊れない

- **対応する受け入れ基準:** AC-6
- **目的:** fire-and-forget な報告送信が失敗（ネットワーク断・サーバーエラー）しても、フォールバック UI とリトライが正常に機能することを確認する。
- **手順:**
  1. 確認項目1の状態でセクション失敗を発生させる。
  2. DevTools の Network を Offline に切り替えるなどして報告 POST を失敗させる。
- **期待結果:** フォールバック表示・再読み込みボタン・a11y（`role="alert"`）は変わらず機能し、報告失敗による未捕捉例外やコンソールエラーの噴出が起きない。

## 既存機能への影響確認

- **正常時のセクション描画:** 仕込んだ `throw` を外した状態で、各主要画面（ホーム・ノート詳細・管理画面・サイドバー等）のセクションが従来どおりスケルトン → 実データで描画され、不要な報告 POST が発生しないこと。
- **既存の `SectionErrorBoundary` UX:** 汎用文言・リトライ（`routerInvalidate` / `appShellInvalidate`）・`fallbackHeading`・`resetKey`・`scope` の挙動が #636 から変わらないこと（既存テストでも担保）。
