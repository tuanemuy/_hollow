# 残存課題 — Issue #452

本 PR（#462）でスコープ内の受け入れ条件はすべて満たした。以下は意図的にスコープ外とした、フォローアップ候補の残存事項。

## 1. ソースファイルの保持期間ポリシー（TTL）未導入

- **内容:** 元ソースファイルは無期限保持（ADR-004）。容量・コストの最適化（TTL / 自動削除 / 古い source の段階的アーカイブ）は導入していない。
- **理由:** Issue 本文の「容量・コスト: 保持期間ポリシーの要否」は検討事項であり、受け入れ条件には含まれない。スコープを永続保存・閲覧・DL・認可・既存互換に集中させた。
- **影響範囲:** ストレージ消費が単調増加する。運用が進んでコストが顕在化したら別 Issue で TTL を設計。

## 2. commit の put 成功・DB ロールバック時の source blob 孤児

- **内容:** commit の3段フローで、ステージ (a)（UoW 前の `objectStorage.put`）が成功し、ステージ (b)（UoW 内の DB 書き込み）がロールバックした場合、永続ストレージに source blob が残るが対応する `MediaAsset` 行が作られないため、既存 purge worker（`status IN ('orphan','deleting')` 対象）の回収対象にならず孤児化する。
- **理由:** `uploadMedia` の bytes-first パターンと同種の許容。commit の DB 失敗は稀（previewing 状態の確定操作）。
- **影響範囲:** 稀なケースで回収不能 blob が残る。`{ownerId}/source/{mediaId}` プレフィックスのキー命名規則を使えば、MediaAsset 行に存在しない source キーを走査して回収するスイープ的バッチで対処可能。上記 1（TTL）と同じ「source ストレージ衛生」テーマなのでフォローアップ Issue に同梱する。

→ 上記 1・2 をまとめてフォローアップ Issue **#468**（ソースファイルのストレージ衛生: 保持期間ポリシー(TTL)と孤児blobの回収）として起票済み。
