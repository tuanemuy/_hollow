# 動作確認計画 — Issue #683: ページ再訪時のスケルトンflash解消

**Issue:** #683
**作成日:** 2026-06-13

## 確認環境

このIssueの変更を確認するために必要な手順のみ記載。

> [!IMPORTANT]
> 本変更は `staleTime: import.meta.env.DEV ? 0 : Number.POSITIVE_INFINITY` パターン。
> **`import.meta.env.DEV=false`（本番ビルド相当）でのみフラッシュ解消が観測できる。**
> `pnpm dev`（DEV=true）では `staleTime` は `0` のままで挙動が変わらないため、
> **AC-1/AC-2/AC-3 のフラッシュ検証は本番ビルドで行う。**
> 一方、機能リグレッション（mutation 後の即時最新化・SavedView リダイレクト）は
> dev サーバーでも確認できる。

### 検証環境の起動（フラッシュ検証用 / 本番ビルド相当）

```bash
pnpm db:apply:local   # 初回のみ: ローカル D1 にマイグレーション適用
pnpm seed:dev-admin   # 初回のみ: 管理者ユーザーのシード
pnpm build            # 本番ビルド（DEV=false）
pnpm start            # wrangler dev がビルド成果物を配信（http://localhost:8787）
```

> [!NOTE]
> 配信は `pnpm start`（`wrangler dev`）を使う。`@cloudflare/vite-plugin` の
> `pnpm build` 出力を `wrangler dev` が読み込み、本番モード（DEV=false）で配信する
> （`docs/runtime_cloudflare.md` 参照）。`pnpm preview`（`vite preview`）ではなく
> `pnpm start` が Cloudflare Workers ランタイムでの本番ビルド配信の正規手順。

### 検証環境の起動（機能リグレッション確認用 / dev）

```bash
pnpm dev              # 開発サーバー（DEV=true）。mutation 後の最新化・リダイレクト動作の確認に使う
```

### デプロイ方法

なし（検証環境のみで確認できる。本番反映は別途 `pnpm deploy:staging` / `pnpm deploy:production` 系を運用手順に従って実行）。

## 確認項目

### 1. (A) 認証済みルート再訪時のフラッシュ解消（ホーム ★最優先）

- **対応する受け入れ基準:** AC-1
- **目的:** 一度開いた認証済みコンテンツルートに再訪してもスケルトンフラッシュが起きないこと
- **前提:** 本番ビルド（`pnpm build && pnpm start`, http://localhost:8787）／ログイン済み
- **手順:**
  1. ホーム（`/`）を開き、Toolbar / FilterBar / NoteList が描画されるまで待つ
  2. ノート詳細（NoteList のいずれかのノート）へ遷移する
  3. ブラウザバック（戻る）でホームに再訪する
  4. 同様にアプリ内リンク（ナビゲーション）でホームへ再訪する
  5. ノート詳細・変更履歴・タグ・ゴミ箱・SavedViews でも再訪を試す
- **期待結果:** 再訪時に各セクションがスケルトンに切り替わらず、キャッシュ済みコンテンツがそのまま表示される（フラッシュなし）
- **確認ポイント:** 「一瞬コンテンツ → スケルトン → 再描画」の順序が消えていること。特にホームの全セクション

### 2. mutation 後の即時最新化

- **対応する受け入れ基準:** AC-4
- **目的:** 編集・削除・タグ操作などの mutation 後は従来どおり `routerInvalidate()` で即時最新化されること
- **前提:** dev でも本番ビルドでも可
- **手順:**
  1. ノートを編集して保存 → 一覧/詳細に戻る
  2. ノートを削除 → 一覧から消えることを確認
  3. タグを操作（追加/削除/リネーム）→ 反映を確認
  4. admin 設定（design / prompts / llm / users / registration）でフォームを保存 → 反映を確認
- **期待結果:** mutation 直後に最新状態が反映される（stale な古い表示が残らない）
- **確認ポイント:** `staleTime: Infinity` 化後も invalidate 経路が生きていること

### 3. ホームの SavedView リダイレクト

- **対応する受け入れ基準:** AC-5
- **目的:** viewId 正規化のための SavedView リダイレクトが初回ロードで従来どおり発火すること
- **前提:** SavedView が 1 件以上存在する状態
- **手順:**
  1. SavedView に紐づく URL でホームを初回ロード（直リンク or リロード）
  2. 正規化された viewId へリダイレクトされることを確認
- **期待結果:** 初回キャッシュミス時に loader handler が走り、従来どおりリダイレクトされる
- **確認ポイント:** `Infinity` 化でリダイレクトが抑止されていないこと

### 4. (B) 公開ルートの再訪フラッシュ解消と gcTime 越え反映

- **対応する受け入れ基準:** AC-2 / AC-6 / AC-11
- **目的:** 公開ルート再訪（gcTime 内）でフラッシュなし、gcTime（60s）超でサーバー側更新が反映されること
- **前提:** 本番ビルド／公開ノート・公開プロフィールが閲覧可能な状態
- **手順:**
  1. 公開検索（`/search`）・公開プロフィール（`/u/:username`）・公開ノート（slug / id）を開く
  2. 別ページへ遷移し、60 秒以内に戻る（gcTime 内再訪）
  3. 次に 60 秒以上空けてから再訪する（gcTime 超）。その間にサーバー側で当該コンテンツを更新しておく
- **期待結果:**
  - gcTime 内再訪: キャッシュ再利用でフラッシュ（背景再検証による再 suspend）なし
  - gcTime 超再訪: キャッシュ破棄済みでクリーンに再ロードされ、サーバー側更新が反映される
- **確認ポイント:** gcTime 超再訪で出る per-section Suspense は「初回フルロード相当の別問題（RSC streaming/hydration 起因、スコープ外）」。AC-2/AC-6 の合否では「背景再検証由来のフラッシュ」とこれを**混同しない**

### 5. (C) 静的（legal）ルート再訪

- **対応する受け入れ基準:** AC-3
- **目的:** about / terms / privacy で再訪時にスケルトンフラッシュが起きないこと
- **前提:** 本番ビルド
- **手順:**
  1. `/about` を開く → 別ページへ遷移 → 戻る
  2. `/terms`・`/privacy` でも同様
- **期待結果:** 再訪時にフラッシュなし
- **確認ポイント:** コンテンツはビルド時固定なので再検証が走らないこと

### 6. ライブ要件ルートの非回帰

- **対応する受け入れ基準:** AC-7
- **目的:** ⛔ 据え置きルート（ダッシュボード・メトリクス・ジョブ監視・エクスポート進捗・editor）が従来どおりナビゲーション時に最新を取得すること
- **前提:** 本番ビルド／admin 権限
- **手順:**
  1. admin ダッシュボード・メトリクス・ジョブ監視を開き、別ページから戻って最新値が取得されることを確認
  2. エクスポート進捗（`/exports/:jobId`）でジョブ状態がライブ更新されることを確認
  3. ノート編集画面（editor）で editLock の鮮度検証が従来どおり動くことを確認
- **期待結果:** これらのルートは再訪/ナビゲーションのたびに最新を取得する（変更前と同じ）
- **確認ポイント:** これらのルートに staleTime 変更が**入っていない**こと

## エッジケース・異常系

### 1. DEV モードでの鮮度維持

- **対応する受け入れ基準:** AC-8
- **目的:** `pnpm dev`（DEV=true）では `staleTime: 0` のまま HMR の鮮度が維持されること
- **手順:**
  1. `pnpm dev` で起動
  2. ルートファイルや表示コンポーネントを編集し、HMR でナビゲーション時に最新が反映されることを確認
- **期待結果:** dev では従来どおり毎ナビゲーションで loader が再実行され、編集が即反映される

### 2. 初回フルロード時のスケルトン残存観察（スコープ外・観察のみ）

- **目的:** F5・直リンクでの初回フルロード時に per-section Suspense のスケルトンが残るかを観察
- **手順:**
  1. 本番ビルドでホーム/公開ノートをキャッシュ無し状態（ハードリロード）で開く
- **期待結果:** スケルトンが一瞬出る可能性は残る（本変更のスコープ外）。残る場合は別 Issue 化を判断する
