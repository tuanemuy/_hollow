## 問題点（要修正）

- **[P-001]** AC-6（reduced-motion）の対応ステップが「2, 4」になっているが、進捗バーの reduced-motion 挙動はステップ1で実装される
  - 理由: ステップ2は「`__root.tsx` に `RouteProgressBar` を import して配置する」だけで、reduced-motion ロジック（`motion-safe:` のみアニメ / `motion-reduce:` は静的）を含むのはステップ1（RouteProgressBar コンポーネント本体）である。実際、ステップ1の変更内容に「prefers-reduced-motion を尊重」と明記されている。AC-6 は「進捗バー**および**スケルトンのアニメが 0ms 相当」を要求するのに、進捗バー側の実装ステップ（1）が紐づけられていない。基準と実装ステップの紐づけが不正確。
  - 提案: AC-6 の対応ステップを「1, 4」（進捗バー＝ステップ1、スケルトン＝ステップ4）に修正する。ステップ2は配置のみで reduced-motion に無関係なので外す。

- **[P-002]** AC-1（クリック後 200ms 以内のフィードバック）と、ちらつき緩和のための「進捗バー表示遅延」がトレードオフ関係にあるが、遅延の許容予算が未定義
  - 理由: 計画のリスク欄・ADR-002 は高速遷移時のちらつき対策として「進捗バー側の表示遅延で対応」を条件付き（必要なら）で挙げている。しかし編集遷移の空白A（loader ラウンドトリップ中）では進捗バーが唯一のフィードバック源であり（スケルトンはRSCシェル到着後）、ここに表示遅延を入れると AC-1 の「200ms 以内」を侵しうる。AC-1 はハードな受け入れ基準なのに、遅延を入れる場合の上限（例: 遅延 ≤ N ms かつ総フィードバック ≤ 200ms）が計画に定義されておらず、実装者が任意の遅延（例: 150–200ms）を入れると AC-1 と衝突しても検知できない。
  - 提案: 「表示遅延を入れる場合でも、遷移開始から視覚変化まで 200ms 以内を保証する上限（例: 遅延 ≤ 100ms 程度）」を計画に明記するか、または「空白Aでは遅延を入れず即時表示、ちらつきは isLoading 立ち下がり側のフェードで吸収する」と方針を確定させ、AC-1 と矛盾しないことを検証可能な形にする。

## 改善提案（検討推奨）

- **[S-001]** AC-7 の由来「既存挙動の維持（回帰防止）」は正確でない（現状の編集ルートは not-found で `RouteErrorFallback`＝error boundary に落ちる）
  - 理由: 現在の `edit.tsx` は `renderNoteEditor` 内で `loadNoteDetail` を Suspense 外で await するため、非存在ノートの notFound は loader を貫通して `errorComponent`（`RouteErrorFallback`）に到達する。一方 AC-7 が要求する「detail と同じ『見つかりません』JSX 表示」は detail の挙動であって、現状の編集の挙動ではない。つまり AC-7 は「既存挙動の維持」ではなく「編集の not-found 表示を detail に**合わせる**変更（＋クラッシュ防止）」である。由来ラベルが実態と食い違うと、レビュー時に「表示が変わったこと」を意図的変更か回帰か判別しづらい。
  - 提案: AC-7 の由来を「detail パターンへの整合＋not-found 時のクラッシュ（500）防止」に修正し、「編集の not-found 表示が `RouteErrorFallback` から『見つかりません』JSX に変わるのは意図的」と明記する。検証内容（500 にならず not-found JSX が出る）は妥当なので基準文言自体は維持でよい。

- **[S-002]** AC-3（モバイルでのフィードバック）の検証方法「モバイル幅（intent プリロード無効相当）」は、intent プリロードを実際には無効化しない
  - 理由: `intent` プリロードは hover で発火するため、デスクトップのウィンドウ幅を狭めても hover は残り、プリロードが効いてしまう。真の「プリロードが効かない環境」はタッチデバイス（hover なし）である。幅だけを狭めた検証では、プリロード有効のままキャッシュヒットで isLoading がほぼ立たず、進捗バーが出ない／出るの判定を誤る恐れがある。ロジック（isLoading 全期間で進捗バー表示）自体は健全なので AC-3 のカバレッジは満たされるが、検証手段が要件を正しく再現しない。
  - 提案: テスト方針の該当箇所を「タッチ/hover 無効のエミュレーション、または `defaultPreload` を切った状態」で検証する、と補強する。あるいは単体テストで「isLoading=true の間は preload 状態に関係なくバーが出る」ことを担保し、手動検証は補助と位置づける。

## 良い点

- Issue の受け入れ基準4点がすべて AC 表に1対1で対応し、由来列で追跡可能。derived な a11y 基準（AC-6）と回帰基準（AC-7）を能動的に追加しており、Issue 明記外の品質リスクも基準化している。
- Issue の改善案5つを採用/不採用まで漏れなく判断し、不採用（pendingComponent / トランジション / staleTime）も ADR-001〜003 で理由付き。「優先度上位の案を黙って落とす」ことがなく、スコープ判断が透明。
- スコープ「含まれないもの」が明記され、詳細・一覧スケルトンの再設計や staleTime 変更といった隣接作業の混入を明確に排除。プレゼンテーション層限定で、ドメイン/ユースケース/アダプター影響なしと正しく整理されている。
- 詳細ルートの確立パターン（loader 即返し＋Suspense＋not-found JSX 返却）を実コード（index.tsx / NoteDetail.tsx）と照合済みで、編集への転用が「盲目的模倣ではなく是正」と根拠付けられている。not-found を throw せず JSX 返却する制約（`.issue/12/adr.md` ADR-004）もリスク欄で押さえている。
