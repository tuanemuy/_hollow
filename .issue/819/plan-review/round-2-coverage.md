## 総評

1周目の指摘4点はすべて正しく反映されている:

- **P-001（AC-6 の対応ステップ）** → 「2, 4」を「1, 2, 4」に修正。進捗バーの reduced-motion 実装（ステップ1）を紐づけ。提案は「1, 4」だったが、進捗バーは実装（1）と配置（2）の両方が揃って初めて reduced-motion 挙動が画面に出るため「1, 2, 4」はむしろ完全で、妥当な反映。
- **P-002（ちらつき緩和と AC-1 のトレードオフ）** → 「純 CSS の opacity トランジション（表示は即時、消える側のみ短いフェード、JS 遅延タイマーなし）」に方針確定。設計・ステップ1・リスク欄・ADR-002 の TBD をすべて解消し、AC-1「200ms 以内」が常に成立することを構造的に保証。
- **S-001（AC-7 の由来）** → 由来を「意図的変更: detail との整合性向上」に修正。リスク欄・テスト方針でも「フルページエラー→インライン表示は意図的変更」と期待値を明確化。
- **S-002（AC-3 の検証方法）** → テスト方針を「実機タッチ/hover 無効エミュレーション、または `defaultPreload` を切った状態」＋「単体テストで preload 非依存に isLoading=true 中はバーが出ることを担保」に補強。

Issue 本文の受け入れ基準4点は AC-1/3/4/5 に、改善案5つは採用（案1,2）・不採用（案3,4,5）が ADR-001〜003 に漏れなく落ちている。スコープはプレゼンテーション層に限定され、逸脱・混入なし。派生基準（AC-6 a11y / AC-7 意図的変更）も適切に基準化されている。

新規の重大なカバレッジ漏れ・スコープ逸脱はない。1点だけ AC↔ステップ紐づけの精度に軽微な不正確さが残る。

## 問題点（要修正）

- **[P-001]** AC-7 の対応ステップが「3」のみだが、not-found のインライン「見つかりません」JSX を実際に描画するのはステップ4（`NoteEditorLoader`）である
  - 理由: AC-7 は「非存在ノートで detail と同じインライン『見つかりません』表示に落ちる（`RouteErrorFallback` にせず 500/クラッシュにもしない）」を要求する。ステップ3（`edit.tsx` server fn）は「redirect ガードを Suspense 外に残し、データ取得を await せず即 `NoteEditorSection` を返す」だけで、not-found の catch＋JSX 返却は行わない。実際の「`isNotFoundError` を catch して『ノートが見つかりません』JSX を返す」ロジックはステップ4の `NoteEditorLoader` の変更内容に明記されている（テスト方針も「`NoteEditorLoader` のインライン『見つかりません』JSX へ落ちること」と step4 を参照）。ステップ3だけでは、not-found が RSC 内で raw throw され `SectionErrorBoundary` のセクションエラー表示になり、AC-7 が求める「detail と同じインライン表示」にはならない。AC-7 は step3（Suspense 外 await の除去）と step4（JSX 返却）の**両方**に依存する。1周目 P-001 と同種の「基準と実装ステップの紐づけ不正確」。
  - 提案: AC-7 の対応ステップを「3, 4」に修正する（Suspense 外 await 除去＝step3、not-found JSX 返却＝step4）。

## 改善提案（検討推奨）

- **[S-001]** AC-4「一覧→詳細→編集の各遷移で『読み込んでいる感』が一貫している」は主観的で、単独では検証手順が曖昧
  - 理由: 「一貫している」の合否判定基準がないため手動確認者の主観に委ねられる。実体は「全ルート共通の進捗バー（step1,2）＋ 各詳細/編集のスケルトン（既存 `NoteDetailSkeleton`／新規 `NoteEditorSkeleton`）が各遷移で出る」に分解できるので、検証可能な下位条件（各遷移で進捗バーが出る／詳細・編集それぞれでスケルトンが出る）へ具体化しておくとレビュー時の判定が安定する。カバレッジ自体は満たされているため必須ではない。

## 良い点

- 1周目の4指摘がいずれも該当箇所（AC 表・設計・ステップ・リスク・ADR・テスト方針）まで波及して反映され、レビュー履歴にも要約が残っている。特に P-002（ちらつき vs AC-1）は「JS 遅延タイマーを導入しない」と明言して AC-1 との衝突可能性を構造的に消しており、条件付き曖昧さが完全に解消された。
- Issue 受け入れ基準4点と改善案5つが採用/不採用まで漏れなく AC 表・ADR に対応。不採用（pendingComponent/トランジション/staleTime）も理由付きで、優先度上位案のサイレント脱落がない。
- AC-7 の not-found 挙動変更を「既存維持」ではなく「detail 整合を狙った意図的変更」と正しく位置づけ、リスク欄で多層防御（catch 忘れでも `SectionErrorBoundary` が 500 を防ぐ）まで押さえている。スコープ「含まれないもの」も明示され隣接作業の混入を排除。
