## 確認項目

### 1. 詳細 → 編集の遷移で 200ms 以内にページ側フィードバックが出る

- **対応する受け入れ基準:** AC-1, AC-2, AC-5
- **目的:** 編集ルートの Suspense ストリーミング化＋グローバル進捗バーで、クリック直後に「遷移している感」が出ることを確認。
- **手順:**
  1. ノート詳細画面（`/notes/$noteId`）を開く
  2. 「編集」への導線をクリックし、クリック直後の画面変化を観察する（可能なら遷移を遅めに感じられるよう devtools の Network throttling を有効化）
  3. 画面最上部のトップ進捗バーの出現タイミングと、編集画面スケルトンの表示を確認する
- **期待結果:** クリック直後（体感 200ms 以内）に画面最上部へトップ進捗バーが出現し、続いて編集用スケルトン（タイトルバー・ディレクトリピル・タグ行・本文ブロック等）が表示され、3クエリ完了後に実エディタへ差し替わる。「クリック→無反応→いきなり編集画面」にならない。
- **確認ポイント:**
  - リンク／ボタン自体の押下スピナーに依存せず、ページ側（進捗バー＋スケルトン）でフィードバックが完結していること（AC-5）。
  - **編集ルート streaming 不変条件（R2 test W-002 の受け入れ条件）:** スケルトンが実エディタより **先に** 出ること自体が、`renderNoteEditor`（`edit.tsx`）が 3 クエリ（`loadNoteDetail`／`loadDirectoryTreeFlat`／`loadAllTags`）を await せず `NoteEditorSection` を即返している証拠。Network throttling 下でスケルトンが視認できれば本不変条件は満たされる。逆にスケルトンが出ず「無反応→いきなりエディタ」に戻った場合は、ルート側が再び await している（＝AC-2 の劣化）と判断する。この不変条件はルート＋`createServerFn`＋`renderServerComponent` を巻き込むためユニット化が重く、本項を回帰の検知点とする（`NoteEditorSection` の単体テストは loader を無限 suspend させるため、ルートが await しても緑のままで検知できない）。

### 2. モバイル／hover プリロード無効環境でも進捗バーが出る

- **対応する受け入れ基準:** AC-3
- **目的:** intent プリロード（hover）が効かない環境でも、loader 往復中にページ側フィードバックが得られることを確認。
- **手順:**
  1. devtools のデバイスエミュレーション（タッチ）を有効化するか、hover が発生しない操作（タッチ相当）で詳細→編集へ遷移する
  2. 遷移中のトップ進捗バーの表示を確認する
- **期待結果:** hover による事前プリロードが効かない条件でも、クリック（タップ）後の loader 往復中にトップ進捗バーが表示される。
- **確認ポイント:** 単なるウィンドウ幅縮小では hover プリロードは切れないため、タッチエミュレーション等で hover を実際に無効化した状態で確認すること。単体テスト（RouteProgressBar の `isLoading=true` でバー可視化）でも担保する。

### 3. 一覧 → 詳細 → 編集で「読み込んでいる感」が一貫している

- **対応する受け入れ基準:** AC-4
- **目的:** 各遷移で共通のトップ進捗バーが出て、かつ各画面のスケルトンが表示される一貫体験を確認。
- **手順:**
  1. ノート一覧画面を開く
  2. 一覧 → 詳細 → 編集 と順に遷移する
- **期待結果:** どの遷移でも遷移中に共通のトップ進捗バーが表示され、詳細画面では `NoteDetailSkeleton`、編集画面では `NoteEditorSkeleton` が出る。遷移フィードバックの体験が画面をまたいで一貫している。
- **確認ポイント:** 編集だけフィードバックが欠落する非対称が解消されていること。

### 4. 非存在ノートを編集で開いたときインライン not-found に落ちる

- **対応する受け入れ基準:** AC-7
- **目的:** Suspense 化後、非存在ノートの編集アクセスがフルページエラーではなく詳細と同じインライン「見つかりません」表示になる（意図的な挙動変更）ことを確認。
- **手順:**
  1. 存在しない noteId で編集 URL（`/notes/<存在しないID>/edit`）に直接アクセスする
- **期待結果:** フルページの `RouteErrorFallback` ではなく、詳細画面と同型のインライン「ノートが見つかりません」表示になる。500 やクラッシュにならない。
- **確認ポイント:** これは既存挙動の維持ではなく、detail との整合を取るための意図的変更。errorComponent へ落ちていないことを確認する。

## エッジケース・異常系

### 1. `prefers-reduced-motion: reduce` 時の静的表示

- **対応する受け入れ基準:** AC-6
- **目的:** モーション無効設定時に進捗バー／スケルトンのアニメが 0ms 相当（静的プレースホルダ）になることを確認。
- **手順:**
  1. OS または devtools で `prefers-reduced-motion: reduce` をエミュレート
  2. 詳細→編集へ遷移する
- **期待結果:** 進捗バーは動かず静的なバーとして表示され、スケルトンの pulse アニメも止まる。フィードバック自体（バー表示・スケルトン表示）は失われない。
- **確認ポイント:** アニメが消えても「遷移している／読み込んでいる」ことは静的表示で伝わること。

### 2. 高速遷移（キャッシュヒット等）でのちらつき

- **目的:** ごく短時間で解決する遷移で進捗バーが不快に点滅しないことを確認。
- **手順:**
  1. 一度読み込んだ詳細→編集を素早く行き来する
- **期待結果:** 進捗バーは表示自体は即時（表示遅延タイマーは持たない方針）だが、消える側の短い CSS フェードにより不快な点滅にならない。`prefers-reduced-motion` 時はフェードも 0ms。

## 既存機能への影響確認

- **編集中状態のリセット回帰:** `NoteEditor` は lazy initializer で初回のみ seed する設計。呼び出し経路が server fn → server async component（`NoteEditorLoader`）に変わっても、編集画面でタイトル／本文を編集した状態が意図せずリセットされないことを確認する（編集中に別操作でローダーが再走しても入力が消えない）。
- **編集ロック取得:** 編集画面表示後に編集ロック（`useEditLock`）が従来どおり取得されること。他タブで同ノートを開くとロック競合表示が出る既存挙動が維持されること。
- **詳細・一覧のスケルトン:** 既存の `NoteDetailSkeleton` ／リストスケルトンは無改修。詳細・一覧の表示が変わっていないこと。
- **全ルートへの進捗バー適用:** `__root.tsx` へ常設したことで、public/auth を含む他ルートの遷移でも進捗バーが出る。既存レイアウト（ヘッダ z-50・ドロワー z-100）に被って操作を妨げないこと（進捗バーは fixed・最上位 z で非侵襲）。
