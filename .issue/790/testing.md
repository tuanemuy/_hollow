# 動作確認計画 — Issue #790: 未処理アップロードバッジをヘッダーCTAからサイドバー upload 項目へ移設

**Issue:** #790
**作成日:** 2026-06-28

---

## 確認環境

このIssueはフロントエンドのみの変更（件数フック/ラベルの整理、サイドバー upload ナビ項目のクライアント化 `UploadNavItem` 新設、ヘッダー `UploadButton` のバッジ削除、モック同期）。データ取得・通知契約は不変。確認に必要な手順のみ記載する。

### 検証環境の起動

フロントエンドのコンポーネント変更なので、HMR が効く vite dev を使う。

```bash
pnpm db:migrate   # ローカル D1 にマイグレーション適用（未適用なら）
pnpm dev          # vite dev（workerd / @cloudflare/vite-plugin）。http://localhost:3000
```

> 本番相当のビルドで確認したい場合のみ `pnpm build && pnpm start`（wrangler dev、`dist/worker` を配信）。フロントエンド反復には `pnpm dev` の方が適する。

### シードデータ（必須）

サイドバー・`/upload` 画面は `_app` 配下の認証必須ルートなので、ログイン済みユーザーが要る。`docs/test.md` の手順に従い、決定論的な管理者ユーザーとセッションを投入する。

```bash
pnpm seed:dev-admin
```

出力されるトークンを CDP 経由でセッション cookie に注入する（cookie 名 `__Host-session` は Secure 必須で `document.cookie` 注入不可）。

```bash
agent-browser cookies set "__Host-session" "<token>" \
  --url http://localhost:3000 --path / --secure --sameSite Lax
```

**件数バッジの表示には「未処理」ステータスの ingestion ジョブが必要**。件数源は `countActiveIngestionJobs`（`pending` / `processing` / `previewing` を数える。`failed` は除外）。非ゼロの件数を見るには、`/upload` 画面からファイルをアップロードしてジョブを作る。アップロードはバックグラウンドで進むため、`pending` / `previewing` 段階のジョブが残っているうちにサイドバー件数を観察する。件数ゼロの状態（非表示）の確認はアップロード前 or 全ジョブ処理完了後に行う。

### デプロイ方法

なし（検証環境のみで確認できる。本番反映は通常のデプロイフロー `pnpm deploy:staging` / `pnpm deploy:production` に従う）。

## 確認項目

### 1. サイドバー upload 項目への件数表示

- **対応する受け入れ基準:** AC-1
- **目的:** サイドバー管理セクションの「アップロード」ナビ項目に未処理件数が右寄せ（`NAV_COUNT`）で表示されることを確認する。
- **手順:**
  1. ログイン後、`/upload` からファイルを 1〜数件アップロードして未処理ジョブを作る。
  2. サイドバーの管理セクション「アップロード」項目を観察する。
  3. 件数がゼロの状態（アップロード前 / 全処理完了後）も観察する。
- **期待結果:** 未処理ジョブがあるとき「アップロード」項目の右端に件数が表示される。99 を超えると `99+`。件数ゼロのときは count スパンが出ない（非表示）。
- **確認ポイント:** 件数表示が既存のライブラリ note 件数と同じ右寄せインライン（`ml-auto`・小サイズ・ink-tertiary）の見た目であること。

### 2. ヘッダーCTAが純粋な「アップロード開始」ボタンになっている

- **対応する受け入れ基準:** AC-2
- **目的:** ヘッダーの upload CTA から件数バッジが消え、純粋な開始ボタンに戻っていることを確認する。
- **手順:**
  1. 未処理ジョブがある状態でヘッダー右上の upload CTA を観察する。
  2. CTA をクリックしてアップロードダイアログ（`#upload`）が開くことを確認する。
- **期待結果:** ヘッダーCTAに件数チップ（バッジ）が一切表示されない。クリックでアップロードを開始する挙動は従来どおり。プライマリCTAとしての見た目（accent 塗り・先頭配置）は維持されている。
- **確認ポイント:** ヘッダーCTAとサイドバーの両方に件数が二重表示されていないこと（件数はサイドバーのみ）。

### 3. イベント駆動更新（アップロード成功・各種 mutation）

- **対応する受け入れ基準:** AC-3
- **目的:** `notifyIngestionQueueChanged` 経由でサイドバー件数がリアルタイムに更新されることを確認する。
- **手順:**
  1. サイドバー件数を見ながら、`/upload` で新規アップロードを成功させる。
  2. ingestion ジョブ行の編集・削除など、件数に影響する操作を行う。
- **期待結果:** ページをリロードしなくても、アップロード成功・ジョブ操作の直後にサイドバー件数が増減する。
- **確認ポイント:** 常時ポーリングではなくイベント駆動（mutation 成功時のみ再フェッチ）であること（不要なネットワークリクエストが流れ続けない）。

### 4. visibility 復帰での再フェッチ

- **対応する受け入れ基準:** AC-3
- **目的:** タブを離れて戻ったときに件数が再取得されることを確認する。
- **手順:**
  1. サイドバーが見える状態で別タブに切り替える。
  2. 件数が変わるような操作（別経由でのジョブ完了など）を挟む、もしくは時間を置く。
  3. 元のタブに戻る。
- **期待結果:** タブ復帰時にサイドバー件数が再フェッチされ最新値になる。
- **確認ポイント:** hidden（非表示）中は再フェッチが走らないこと。

### 5. アクセシブルなテキスト表現（一度だけアナウンス）

- **対応する受け入れ基準:** AC-4
- **目的:** 件数がスクリーンリーダーにちょうど一度だけアナウンスされ、欠落も二重もないことを確認する。
- **手順:**
  1. 未処理ジョブがある状態でサイドバー「アップロード」項目の DOM を DevTools で確認する。
  2. `aria-label` 属性の値を確認する。
  3. 可視 count スパンが別途読み上げ対象になっていないことを確認する。
- **期待結果:** ナビ `<a>`（Link）に `aria-label="アップロード（未処理 N 件）"`（件数ゼロ時は `アップロード`）が付く。`aria-label` が子孫テキストを上書きするため、可視 count が二重に読み上げられない。
- **確認ポイント:** アクティブ時に `aria-current="page"` / `data-active` が `aria-label` と共存していること（状態と名前が別々に担保される）。

### 6. 実装とモックの一致

- **対応する受け入れ基準:** AC-5
- **目的:** 実装がデザインモック（`spec/design/pages/P13-upload.html` と mobile 版）と一致することを確認する。
- **手順:**
  1. `/upload` 画面の実装とモック P13（desktop / mobile）を見比べる。
- **期待結果:** ヘッダーCTAは件数なし、サイドバー管理「アップロード」項目に `.nav-item .count` 規約の件数表示があり、モックと実装が一致する。

## エッジケース・異常系

### 1. settings ページでの挙動

- **目的:** `/settings/*` ではメイン Sidebar が settings 用に差し替わり `UploadNavItem` がアンマウントされる（件数非表示）が、戻ると再表示されることを確認する。
- **手順:**
  1. 未処理ジョブがある状態で `/settings` 系ページへ移動する。
  2. settings 用サイドバーに upload 件数が出ないことを確認する。
  3. 通常画面（`/` 等）に戻る。
- **期待結果:** settings 滞在中は件数がどこにも出ない（仕様）。通常画面に戻ると `UploadNavItem` が再マウントされ、mount 時再フェッチで件数が復帰する。

### 2. 件数取得失敗時の挙動

- **目的:** 件数フェッチが失敗しても画面が壊れず、前回値が保持されることを確認する。
- **手順:**
  1. DevTools で `getIngestionQueueCountFn` のリクエストをブロック / オフラインにする。
  2. mutation などで再フェッチを誘発する。
- **期待結果:** エラーで UI が壊れず、直前の件数表示が保持される（初回失敗時はゼロ＝非表示のまま）。

## 既存機能への影響確認

- **ヘッダーCTAの開始フロー**: バッジ削除後もアップロードダイアログ（`#upload` ハッシュ）の開閉・アップロード開始が従来どおり動くこと。
- **サイドバーの他ナビ・ツリー・保存ビュー**: `UploadNavItem` のクライアント化により、サーバーレンダリングされる他のナビ項目・ディレクトリツリー・保存ビューが退行していないこと。
- **モバイルのオフキャンバスサイドバー**: ドロワーを閉じていても DOM 上はマウントされ、件数更新が効くこと（settings とは異なる）。
