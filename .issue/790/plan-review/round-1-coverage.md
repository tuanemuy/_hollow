# Issue #790 計画レビュー — Round 1（要件カバレッジ・スコープ整合性）

レビュー視点: Issueの要件カバレッジ・スコープ整合性
対象: `.issue/790/plan.md` / `.issue/790/adr.md`

## 総評

Issue本文の受け入れ基準6項目はすべて plan の AC 表（AC-1〜AC-6）に1対1で写像されており、漏れはない。Issueが明示した「設計の問い」4つ（ヘッダーバッジ remove/relocate、アクセシブル名の扱い、#628 との順序整合、クライアント境界）はすべて plan / ADR が明確な結論を出している。スコープ「含まれないもの」も Issue の意図（件数取得・通知契約は不変、P10 全面同期は別タスク）と整合する。指摘は主にモック同期の網羅範囲とステップ紐づけの精度に関する軽微なもの。

## 設計の問い → 結論の対応（全問クローズ確認）

- 問い1（ヘッダーバッジ remove or relocate-only?）→ ADR-001: 完全移設（ヘッダーは純粋CTA、件数はサイドバーのみ）。結論あり。
- 問い2（アクセシブル名の扱い）→ ADR-002: 可視は `NAV_COUNT` インライン、SR名は `<Link>` の `aria-label={uploadQueueLabel}`。`aria-label` の子孫テキスト上書きで一度だけアナウンス。結論あり。
- 問い3（#628 との順序整合）→ AC-2 / 実装ステップ5: `data-primary`・`pillBtnPrimary`・先頭配置を維持（順序・ランクは不変）。結論あり（専用ADRはないが plan 内で明確に決着）。
- 問い4（クライアント境界）→ ADR-003: 専用クライアント `UploadNavItem` のみクライアント化、`Sidebar` はサーバーのまま。結論あり。

## Issue受け入れ基準 → AC 写像（全項目カバー確認）

- Issue「サイドバー管理 upload 項目に件数表示」→ AC-1（検証可能）
- Issue「ヘッダーCTAを純粋ボタンに」→ AC-2（検証可能）
- Issue「イベント駆動更新が新位置でも動く」→ AC-3（検証可能）
- Issue「件数のアクセシブルなテキスト表現を一度だけ保持」→ AC-4（検証可能）
- Issue「実装とモックが一致」→ AC-5
- Issue「品質ゲート通過」→ AC-6（検証可能）

#### 問題点（要修正）

- **[P-001]** モック同期（AC-5）の範囲がモバイル P13 について曖昧。実装ステップ7は `spec/design/pages/mobile/P13-upload.html` を「（必要なら）」とし、ADR/スコープも desktop P13 のみを確定的な同期対象としている。
  - 理由: サイドバーは単一の共有コンポーネント（`Sidebar` → `UploadNavItem`）で、desktop / mobile いずれのビューポートでも同じ upload 件数を描画する。実機で確認したところ、モバイル P13（`mobile/P13-upload.html` L1032-1034）も desktop P13（L1084-1086）と同様に「アップロード」ナビ項目（active）を**件数なし**で描画している。desktop だけ件数を追記すると、(a) モバイルモックが実装と一致しなくなり AC-5「実装とモックが一致」を部分的にしか満たさない、(b) 2つのモック間でも不整合が生じる。
  - 提案: ステップ7の「必要なら」を「mobile P13 も同期する（必須）」に確定させる。モバイル P13 の upload ナビ項目（active）にも desktop と同じ `<span class="count">N</span>` を追記し、AC-5 の対応ステップに mobile を明記する。ヘッダーCTA（mobile L983 `pill-btn primary icon aria-label="アップロード"`）は既に件数なしで変更不要、という確認も desktop 同様に記載するとよい。

#### 改善提案（検討推奨）

- **[S-001]** AC-5（実装とモックが一致）の「対応ステップ」が `5, 7` のみで、サイドバー実装側を作るステップ3（`UploadNavItem` 新設）・ステップ4（組み込み）が紐づいていない。
  - 理由: AC-5 の「一致」はヘッダー側（ステップ5）とモック（ステップ7）だけでなく、件数を表示するサイドバー実装（ステップ3・4）が揃って初めて検証可能。表の対応ステップに 3, 4 を加えると AC とステップの追跡性が上がる。

- **[S-002]** ファイル改名（`IngestionQueueBadge.tsx` → `useIngestionQueueCount.tsx`）と関数改名（`uploadButtonLabel` → `uploadQueueLabel`）は Issue が直接要求していない追加リファクタで、スコープ拡張の唯一の候補。
  - 理由: Issue本文は「`useIngestionQueueCount` / `IngestionQueueBadge` は再利用可能」と reuse を前提に書いており、改名そのものは要求していない。ただし ADR-001/002 で「完全移設＝絶対配置チップ削除」を選んだ結果、`IngestionQueueBadge`（チップ）は唯一の消費者を失い死にコードになるため、削除と命名整合は妥当な範囲。リスクは import / テスト / JSDoc 参照の更新漏れだが、ステップ8で grep 検証が計画済みで対処されている。実害なし。スコープ拡張として意図的であることを確認できればこのまま進めてよい（改名を避けて最小差分にする選択肢もあるが、死にコード・誤称ファイル名が残るデメリットの方が大きいと判断、現計画を支持）。

#### 良い点

- Issueが「resolve before implementation」と明示した4つの設計の問いすべてに、plan 本文と ADR-001〜003 が明確な結論を与えている。問いの放置がない。
- スコープ「含まれないもの」が Issue の意図（件数取得・通知契約は不変、P10 管理セクションは既存乖離で全面同期は spec-sync の別タスク、`NAV_COUNT` を note 件数と差別化しない）と正確に一致しており、過剰な作業の混入がない。実機確認でも P10-home の管理セクションは upload 項目自体が未反映で、plan のスコープ判断は正しい。
- AC 表が「由来」列で Issue 本文／設計の問い／参照ADR への traceability を持ち、各基準が検証可能な形（0で非表示・99超で `99+`・一度だけアナウンス等）で書かれている。
- アクセシビリティ契約（`aria-label` の子孫テキスト上書きで件数を一度だけアナウンス、`aria-current`=状態 と `aria-label`=名前 の共存）が現行コード（`UploadButton.tsx` L26-27, `IngestionQueueBadge.tsx` L64-65）の挙動と整合しており、AC-4 の「重複なし・欠落なし」を満たす設計になっている。
- 依存方向（`layout → ingestion`、既存 `Header → UploadButton` と同型）を踏襲し、逆流を持ち込まない判断が明示されている。
