## 検証した事実

- **Issue の受け入れ基準 6 項目はすべて AC 表（plan L15-22）に写像済み**で、各 AC に対応ステップが紐づいている。欠落なし。
  - AC-1（サイドバー件数表示）/ AC-2（ヘッダー純粋CTA）/ AC-3（イベント駆動更新）/ AC-4（アクセシブル名・一度だけ）/ AC-5（実装＝モック）/ AC-6（品質ゲート）。
- **Issue の「設計の問い」4 つはすべて解決済み**:
  - ヘッダーバッジ remove or relocate-only → ADR-001（完全移設）。
  - アクセシブル名の扱い → ADR-002（`NAV_COUNT` 可視 + `aria-label` で一度だけ）。
  - #628 とのオーダリング整合 → AC-2 / ステップ5（`data-primary`・`pillBtnPrimary`・先頭配置を維持）。
  - クライアント境界 → ADR-003（専用 `UploadNavItem`、Sidebar はサーバーのまま）。
- **モックの現状を実ファイルで確認**: desktop / mobile 両 P13 とも、ヘッダーCTAは既に `aria-label="アップロード"`（件数なし）、管理セクションの upload ナビ項目は count スパンなし。ステップ7（両モックに `<span class="count">N</span>` を追記）は正確で、AC-5 の根拠が成立する。ヘッダーCTAは変更不要という記述も正しい。
- **陳腐化コメントの実在箇所を grep で確認**: ステップ1・8 が列挙する `UploadForm.tsx` / `actions.ts` / `IngestionJobEditDialog.tsx` / `queueBadgeBus.ts` / テスト3本（`IngestionJobRow` / `UploadForm` / `UploadDialog`）が実際にヒットし、「該当する全箇所」の網羅指示と整合する。
- **スコープ除外（plan L26-30）は明確かつ正当**: データソース・pub-sub・notify 呼び出し側は不変、管理セクションの構成変更なし、`P10-home.html` の全面同期は別タスク（既存乖離）、`NAV_COUNT` の視覚差別化はしない。いずれも Issue の意図（表示位置の移設のみ）と整合し、過剰スコープも不足もない。

#### 問題点（要修正）

**問題点ゼロ。**

1・2 周目の指摘（モバイル P13 同期の明記、AC-5 の対応ステップ補完、settings 差し替え時のアンマウント挙動訂正、層責務分割テスト、`activeProps` モック要件、陳腐化コメント全箇所化、a11y 非対称の意図明記）はすべて反映済み。要件カバレッジ・スコープ整合性の観点で実装着手を妨げる欠落は残っていない。

#### 改善提案（検討推奨）

- **[S-001]** ステップ7でモックに追記する count の例示値を desktop / mobile で揃える旨を一言添えてもよい。/ 既存の note 件数が両モックとも `127` で一致しており、upload 件数も両モック同値の妥当な小さい数（例: `3`）に揃えないと、モック相互の見た目が揺れる可能性がある。実装をブロックする問題ではなく、ステップ7の「両モックに反映」に内包される運用上の細部。

#### 良い点

- Issue の AC・設計の問いを表形式・ADR で一対一に解決まで落とし込んでおり、トレーサビリティが高い。
- スコープ除外を「なぜ除外か」付きで列挙（P10 既存乖離・データ契約不変・視覚差別化なし）し、スコープクリープと過小実装の両方を防いでいる。
- `/settings/*` でのサイドバー差し替えという非自明な挙動変更を AC-3 の根拠（常時マウントではなく mount 時再フェッチによる復帰）まで掘り下げ、ADR-001 Consequences に許容可能な帰結として記録している。要件解釈の地に足がついている。
- 「完全移設＝死にコードを残さない」を改名（ファイル/関数）とステップ8 grep 検証まで一貫させ、移設の徹底と過剰修正の回避（`queueBadgeBus` バス名は据え置き）を両立している。
