## 観察事項（重要）

実装は **HTTP 4xx 経路では provider レスポンス body の `error.type`（OpenAI なら `invalid_request_error`）をそのまま prefix として使う**（`app/core/adapters/openai/connectionPing.ts:73`）。

これは ADR-004（messagesClient は category 化せず masking のみ）の方針を connectionPing にも踏襲した設計判断と思われる。catch 経路（fetch TypeError / timeout）でのみ `sanitizeErrorReason` を通して `auth_failed:` / `network:` / `timeout:` 等の category prefix が付く。

testing.md の TC-002 期待は「`auth_failed:` などの category prefix」と書かれているが、これは plan.md と testing.md の文言ズレと思われる。HTTP 4xx 経路の本来意図と照合すれば、provider の type prefix を使う現実装が ADR-004 と整合している。

**secret 漏洩の観点では完全に問題なし**：

- OpenAI が返す `Incorrect API key provided: sk-test-*****************xxxx` 内の API key は OpenAI 側が事前に masking している
- メッセージ全体は `maskSecrets()` を通過（`connectionPing.ts:74`）するが、すでに masking 済みなので冪等

## 補足: spec-sync の対象候補

testing.md の TC-002 期待文言（「`auth_failed:` などの category prefix」）と実装挙動（HTTP path は provider type prefix）の認識ズレは spec-sync で testing.md または plan.md 側を更新することで解消できる。
