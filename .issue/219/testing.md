このIssueの変更を確認するために必要な手順のみ記載（プロジェクト全体のセットアップは省略）。

```bash

```

ホーム `/` のノート一覧でビュー切替を確認するため、ログイン済みユーザー＋ノートが数件以上ある状態が必要。テストユーザーが無ければ `/signup` から作成し、手動で 5〜10 件以上のノートを作成しておく（カレンダー表示の見映えのため、作成日が複数日にばらつくと尚良し）。SavedView 確認用には NoteList から SavedView を 1 件作成しておく。

## 確認項目

### 1. リスト → タイル → カレンダー切替で `_serverFn` リクエストが発火しないこと

- **目的:** Issue 完了条件 1（同じデータならクライアント即時反映）。loader 再実行 = サーバー往復が止まったことを確認。
- **手順:**
  1. ログイン後 `/` を開く
  2. DevTools の Network タブを開いて Fetch/XHR でフィルタする
  3. ヘッダー上の `DisplayModeSwitch`（リスト/タイル/カレンダーボタン群）でリスト → タイル → カレンダー → リストの順に切替
- **期待結果:** display 切替ボタン押下のたびに `_serverFn` / `renderHome` 系のリクエストが発火しない（0 件）。URL の `?display=` だけが変化する。
- **確認ポイント:** Network タブを開いたまま切替を行い、Pending リクエストが瞬時に出ないかを目視確認。

### 2. 切替が即時で体感遅延が消えていること

- **目的:** Issue 完了条件 1（体感遅延がほぼ消える）。
- **手順:**
  1. `/` でリスト/タイル/カレンダーを連続で切替
  2. ボタン押下 → 表示変更までの体感遅延を目視確認
- **期待結果:** 1 フレーム（~16ms）以内に表示が切り替わる。ボタンクリック直後に応答が無い瞬間が存在しない。
- **確認ポイント:** 連続でカチカチ切替して、止まる瞬間や引っかかりが無いこと。

### 3. ローディング表示のチラつき / 空白が消えていること

- **目的:** Issue 完了条件 2（ローディング表示のチラつきが消える）。
- **手順:**
  1. `/` でリスト/タイル/カレンダーを切替
  2. 切替の瞬間に画面が空白になる時間や、スピナーが瞬間表示される現象が無いことを確認
- **期待結果:** 旧ビュー → 新ビューがチラつき無く差し替わる。ローディング表示（スピナー、スケルトン、aria-busy 表示等）が瞬間的にも出ない。
- **確認ポイント:** カレンダー → タイル → リストのような重い遷移で特に注意して観察。

### 4. URL に `?display=` が反映されてリロードでも維持されること

- **目的:** Issue 完了条件 3（切替が URL に反映されてリロード／共有しても同じビューで開ける）。
- **手順:**
  1. `/` を開く（既定はリスト想定）
  2. タイルボタンをクリック
  3. URL が `?display=tile` 等になっていることをアドレスバーで確認
  4. ブラウザで Reload (Cmd+R)
  5. リロード後もタイル表示で開くことを確認
  6. 続けてカレンダーボタンをクリック → URL が `?display=calendar` になり、リロードでもカレンダー表示で開くことを確認
  7. URL をコピーして別タブで開いても同じ表示で開けることを確認
- **期待結果:** URL の `display` クエリパラメータと表示モードが常に一致する。リロード／共有 URL から開いても保存された表示で開ける。
- **確認ポイント:** `replace: true` のため、複数回切替してから戻るボタンを押しても切替前の URL に戻る（履歴に積まれていない）こと。

### 5. SavedView 復元との整合性

- **目的:** SavedView 復元時に display が SavedView の `displayMode` で開き、URL も正規化されることを確認。既存仕様を壊さない。
- **手順:**
  1. `/` でタイル表示にして、その状態で SavedView を「タイル View」として保存
  2. リスト表示に戻す
  3. サイドバーまたは Views ページから先ほど保存した「タイル View」を選択
  4. URL に `?viewId=xxx&display=tile` が乗り、タイル表示で開くことを確認
  5. その状態でリストボタンをクリック
  6. URL が `?viewId=xxx&display=list` に変化し、リスト表示になることを確認
  7. リロードしても URL の display が踏襲されてリスト表示で開くことを確認
  8. もう一度 SavedView を選び直すと、また `?display=tile` に正規化されてタイル表示で開くこと
- **期待結果:** SavedView 適用時、URL の `display` が SavedView の `displayMode` で確定する。SavedView 適用後にユーザーが手動で display を変えると、その手動切替が以降の URL に反映される。再度 SavedView を選び直すと SavedView の display で正規化される。
- **確認ポイント:** redirect ループが起きていないこと（Network タブで `_serverFn` が無限に発火しないこと）。

## エッジケース・異常系

### 1. 無効な viewId（削除済み・他人の SavedView）でアクセス

- **目的:** SavedView が見つからない場合の fallback 挙動が壊れていないこと。
- **手順:**
  1. 適当な無効な viewId を URL に付けて開く: `/?viewId=00000000-0000-0000-0000-000000000000`
- **期待結果:** redirect は発動せず、ノート一覧がリスト表示（または URL の `display`）で表示される。エラーや無限 redirect は発生しない。
- **確認ポイント:** Network タブで `renderHome` が 1 回だけ発火し redirect ループが起きないこと。

### 2. URL 直接編集での `?display=tile` 直アクセス

- **目的:** 初回ロード時の `display` 反映が正常であること。
- **手順:**
  1. アドレスバーで `/?display=tile` と直接入力してアクセス
- **期待結果:** 初回ロード時点でタイル表示で開く。リスト表示が一瞬出てからタイルに切り替わる、というチラつきが無い。
- **確認ポイント:** 初回 SSR + hydration 時点でクライアントが URL の display を読めていること。

## 既存機能への影響確認

- **`SaveViewDialog` の挙動**: SavedView 保存時、現在の `display` が `displayMode` として保存されること（`searchToViewQuery` が `search.display` を読めていること）。
- **`FilterBar` の `clearAll` 等**: 他フィルタ条件のクリアで `display` が消えないこと。
- **Sidebar の `<Link to="/" search={HOME_SEARCH}>`**: 既知挙動として display が消える（現状踏襲のため Issue スコープ外）。Issue で意図的に変えていないことを確認するだけ。
