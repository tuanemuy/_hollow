#### 改善提案（検討推奨）

- **[S-001]** AC-2 のトレーサビリティに検証ステップ（8）を含めるか整理の余地（任意）
  - 理由: AC-2 は「…/admin/speech から選択・保存・**接続テスト（probe 2xx）ができる**」であり、probe 2xx の実機確認はステップ8（テスト方針3）でしか実演されない。現状 AC-2 の対応ステップは `1,2,3,4,5,6,7`（=配線まで）で、検証ステップ8が含まれていない。一方 AC-3/AC-1 は検証ステップ（8/9）を対応列に持つため、AC ごとに「配線ステップを書くか/検証ステップを書くか」の方針が割れている。実害は無い（配線=1-7で正しく、probe 検証は AC-1 と同じ手動枠で担保される）が、1周目 P-001 の提案末尾でも「probe 2xx の実機確認まで含めるなら ,8 も」と示唆されていた点。
  - 提案: AC-2 行に `,8`（probe 2xx の実機確認）を補うか、表の凡例に「対応ステップは配線ステップのみ／検証は AC-1 ステップ8で代表」と一言添えて方針を明示する。どちらでも可。

#### 良い点

- 1周目指摘 4 件を全件取り込み、見送りゼロ。各修正が plan 本文・ADR・リスク・テスト方針の該当箇所すべてに横展開され、表と本文の整合が取れている。
- AC-1 の合否判定を「ノート保存成功」ではなく「adapter／ネットワーク層で実 Gemini が 2xx + **非空** transcript」と規定し、`runIngestionJob` の `SpeechFailureError` 握り潰し（空 transcript 化）による偽陽性を AC-1/ステップ8/9/リスク/テスト方針4・6 の全箇所で一貫して排除している。受け入れ基準の「検証可能性」が極めて高い。
- スコープ外（#788 / Files API / 録音 UI 変換 / 契約変更）を明示隔離し、Gemini を REST diff-only に限定。Issue の「Gemini に絞る／Workers AI は #788」という分割意図に忠実。
- dual-list ドリフト（`SPEECH_PROVIDERS` ⇔ `SPEECH_PROVIDERS_TRANSPORT`）と default-model 二重定義（VO コメント／UI Record）を原子的更新リスクとして特定し、ステップ1・2・6 に分配。実コードと一致。
- `.issue/738` ADR-002 の OK/NG 別状態遷移（Superseded / Accepted）まで AC-6 の射程に含め、ADR 連鎖の後始末を取りこぼしていない。
