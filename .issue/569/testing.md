# 動作確認計画 — Issue #569: 領域3 P18 タグ管理の未追従機能（検索・ソート・最終使用列）

**Issue:** #569
**作成日:** 2026-06-07

---

## 確認環境

このIssueはタグ管理画面（`/tags`）に検索・ソート・最終使用日時の列を追加するフロント＋read-time 集約の変更。最終使用列はDB列追加ではなく `MAX(notes.updatedAt)` の集約で導出するため**新規 migration は無い**。実機確認はローカル開発サーバで行う。

### 検証環境の起動

```
pnpm db:apply:local
pnpm dev
```

`pnpm db:apply:local`（= `wrangler d1 migrations apply hollow-local-d1 --local`）で既存マイグレーションをローカル D1 に適用（本Issueでの新規追加なし、冪等）後、`pnpm dev`（`vite dev`、Cloudflare ランタイム）でローカルサーバを起動する。表示された URL をブラウザで開き、ログイン済みユーザーで確認する。

確認には少なくとも以下のデータを持つユーザーが必要:
- 複数のタグ（名前が五十音順で散らばるもの・ノート件数が異なるもの・**ノートに一度も付いていない未使用タグ**を含む）
- タグ付きノート（各ノートの `updatedAt` がばらつくよう、更新タイミングをずらしたもの）
- 検索ヒット確認用に、共通の部分文字列を持つタグ名（例: `research` / `re-read` など `re` で部分一致するもの）

開発用 admin ユーザーは `pnpm seed:dev-admin` で投入できる。追加のシードは `pnpm db:execute:local <SQLファイル>` で流せる（manual-test スキルが seed を準備する）。

### デプロイ方法

なし（検証環境のみで確認できる。ステージング反映が必要な場合は `pnpm deploy:staging`。新規 migration が無いため D1 反映は不要）。

## 確認項目

### 1. タグ検索（A）

- **目的:** 検索フォームで `q` が URL に反映され、`nameNormalized` の部分一致でタグが絞り込まれるか。
- **手順:**
  1. `/tags` を開く。
  2. 検索フォームに部分文字列（例 `re`）を入力して submit する。
  3. URL を確認する（`/tags?q=re`）。
  4. 検索欄を空にして submit する。
- **期待結果:** `q` を含むタグだけが残る。URL に `?q=re` が乗る。空 submit で `q` が URL から消え全件に戻る。大文字小文字を区別しない（`nameNormalized` 比較）。
- **確認ポイント:** デザイントークン整合（surface 背景・focus shadow、リテラル px の浮きがない）。

### 2. タグ検索ヒット0件の空状態（A-5）

- **目的:** 検索ヒット0件のとき、タグ未作成とは別の文言が出るか。
- **手順:** 存在しない文字列（例 `zzzzz`）で検索する。
- **期待結果:** 「『zzzzz』に一致するタグが見つかりません」等の検索向け空状態が出る。「タグがまだありません / 本文中で #tagname と…」（未作成向け文言）は出ない。
- **確認ポイント:** タグは存在するのに「ありません」と誤表示されないこと。

### 3. タグソート（B）

- **目的:** ソート軸（名前/ノート数/作成日時/最終使用）と方向（昇順/降順）が URL に反映され、並びが変わるか。
- **手順:**
  1. `/tags` を開く（既定は名前・昇順）。
  2. ソート軸を「ノート数」に切り替える。
  3. 方向を降順に切り替える。
  4. URL を確認する（`/tags?sort=noteCount&order=desc`）。
  5. 軸を「作成日時」「最終使用」にそれぞれ切り替える。
- **期待結果:** 各軸・各方向で並びが正しく変わる。URL に `sort`/`order` が乗る。UI の現在値（select の選択・方向トグル）が URL と一致する。未指定時は名前・昇順で初期表示される。
- **確認ポイント:** 「最終使用」軸が項目4・5（C）と連動して並ぶこと。

### 4. 最終使用日時の列（C）

- **目的:** 各タグ行に最終使用日時（= 紐づく active ノートの `MAX(updatedAt)`）が表示されるか。
- **手順:**
  1. `/tags` を開く。
  2. ノートが付いているタグの行を見る。
  3. 未使用タグ（ノート0件）の行を見る。
  4. ウィンドウを 1024px 未満に狭める。
- **期待結果:** 使用済みタグは最終使用日時が `ja-JP` 形式の日付で出る（`TrashList` の削除日と同形式、時刻なし）。未使用タグは「未使用」フォールバック表示。狭幅（`max-lg`）では `tag-count` と同様に畳まれる。
- **確認ポイント:** 表示日付が実際のノート最終更新と一致するか。

### 5. 最終使用ソートの並び（C × B）

- **目的:** `sort=lastUsedAt` で使用済みタグが日時順、未使用タグ（NULL）が一貫位置に並ぶか。
- **手順:**
  1. `/tags?sort=lastUsedAt&order=desc` を開く。
  2. 並びを確認する（新しい使用順、未使用タグは末尾）。
  3. `order=asc` に切り替える。
- **期待結果:** desc で最終使用が新しいタグが上、未使用タグ（NULL）が末尾。asc で未使用タグが先頭付近。同値・NULL でも `tags.id` のタイブレークで順序が安定（リロードで並びがブレない）。

## エッジケース・異常系

### 1. 不正なURLパラメータ

- **目的:** 手打ちの不正パラメータでルートが壊れないか。
- **手順:** `/tags?sort=bogus&order=xxx&q=` を直接開く。
- **期待結果:** `.catch(undefined)` で各パラメータがデフォルトに落ち、エラーにならず既定（名前・昇順・全件）で表示される。

### 2. リネーム/削除の楽観反映と検索/ソートの併存

- **目的:** 検索/ソート適用中にリネーム・削除しても `useOptimistic` 表示が崩れないか。
- **手順:**
  1. 検索 or ソートを適用した状態にする。
  2. 表示中のタグをリネームする。
  3. 別のタグを削除する。
- **期待結果:** リネーム・削除が即時に楽観反映され、その後 loader 再取得で確定。検索/ソート状態（URL）が保持されたまま。リネームしても `noteCount`・`lastUsedAt` が保持される。

## 既存機能への影響確認

- **`loadTagsForOwner`（全件取得）の温存**: `resolveTagNamesToIds` 経由のタグ名→ID解決（ノート一覧のタグフィルタ等）が従来どおり全件を引けるか（新 loader 分離で影響していないか）。
- **`toTagDTO` シグネチャ変更**: `createTag` / `renameTag` の戻り値経路が回帰なく動くか（タグ作成・リネームが成功するか）。
- **既存の検索/ソート backend**: `listTags` / `findByOwner` の `query`/`sort`/`order` が他の呼び出し元に影響していないか。
