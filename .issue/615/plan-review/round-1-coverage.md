# Round 1 レビュー — Issue #615 計画（観点: 要件カバレッジ・スコープ整合性）

レビュー対象: `.issue/615/plan.md` / `.issue/615/adr.md`
観点: Issue 本文スコープ4項目の基準への落とし込み / 検証可能性 / 基準↔ステップ紐づけ / スコープ外混入 / geo 見送りと虚偽表示禁止の整合

## サマリ

Issue 本文のスコープ4項目（device-parser / geo / 最終アクセス時刻 / 相対時刻整形）は
すべて受け入れ基準に対応づけられており、geo 見送りも「未実装＝虚偽回避」として
AC-6 + ADR-002 に明示されている。Issue の意図（虚偽表示禁止）と矛盾しない。
計画が引用する既存コードの記述（`resolve` が `updatedAt` を更新しない、
`SessionDTO.updatedAt` は projection 済み・UI 未使用、`SessionIcon` 単一 glyph、
`sessionTitle` フォールバック）は実コードと一致することを確認した。

致命的な要件漏れは無い。指摘は検証可能性の精緻化と紐づけの整合に関する軽微なものに留まる。

問題点ゼロ

#### 改善提案（検討推奨）

- **[S-001]** AC-3（デバイス種別ごとのアイコン切替）の検証可能性が「unknown=汎用 glyph」止まりで、4種別すべての glyph 差異を確認する基準になっていない
  - 理由: Issue スコープ1 は「スマホ/PC のアイコン切替」を要求し、mock（L785-820）は desktop/mobile/tablet を出し分けている。AC-3 は「kind に応じて切り替わる」と書くが、検証時に desktop と mobile が同一 glyph でも AC-3 を満たすと読めてしまう。ステップ8・テストでは kind 別アイコンを検証するとあるので意図は揃っているが、基準文言を「desktop / mobile / tablet で互いに異なる glyph、unknown は汎用」とすると検証粒度が一意になる。

- **[S-002]** mock の `session-meta` 1行目は「device · geo · IP」を `·` 連結した複合行（L787 等）だが、計画 UI ステップは「device.label をタイトルへ」「IP は据え置き（meta）」とするだけで、geo を抜いた meta 行の最終的な構成（device トークンを meta に出すのか、タイトルのみか／IP との並び）が基準・ステップに明示されていない
  - 理由: AC-2 は label を「タイトル表示」と紐づけるが、mock では OS/ブラウザは meta 行にある。タイトルへ寄せる判断自体は妥当だが、geo を除いた結果 meta 行が「IP のみ」になるのか「最終アクセス + IP」の2行構成かが受け入れ基準から読み取れず、検証者ごとに解釈が割れうる。スコープ整合上の欠落ではないが、ADR か AC-2/AC-4 に「geo を抜いた meta 行構成」を1文足すと mock 差分の意図が明確になる。

- **[S-003]** AC-5 の相対時刻ヘルパーが「最終アクセスとログイン日時の両方に使われる」と書かれているが、ログイン日時（createdAt）は現状 `formatLoginTime`（locale 絶対表示）で出ており、これを相対表示へ変えるのか併用なのかが基準とステップ8で揺れている
  - 理由: AC-5 は「ログイン日時の表示にも使われる」と必須化する一方、ステップ8は「ログイン日時は維持」と書き、ADR-004 consequences は「既存 toLocaleString 直書き箇所の一括置換はしない」とする。mock のログイン日時相当（最終アクセス）は相対だが「ログイン日時」ラベル自体は mock に無い（#572 が追加した独自表示）。AC-5 の「ログイン日時にも使う」が必須要件なのか努力目標なのかを一意にしておかないと、検証時に「createdAt が絶対表示のまま＝AC-5 違反」と誤判定されうる。最終アクセス（updatedAt）に使うことが本質なので、AC-5 を「最終アクセスに使われ、ログイン日時表示にも適用可能な共有ヘルパーとして実装される」に緩めるか、ログイン日時も相対化すると明確化することを推奨。

- **[S-004]** AC-7（spec 反映）の検証対象が `spec/usecases/identity.md` のみに見えるが、地名見送りの判断は spec 側のどこに残すかが基準に含まれていない
  - 理由: ステップ9で「geo は別 Issue と spec に明記」とあり方向性は正しいが、AC-7 の文言は device projection / updatedAt 更新経路の反映のみを挙げ、geo 見送りの記録が AC として独立に検証されない。虚偽表示禁止の一貫性（AC-6・リスク欄「spec/ADR に残す」）を spec 反映の受け入れ基準にも結びつけると、見送り判断のトレーサビリティが基準レベルで担保される。

#### 良い点

- Issue スコープ4項目が AC へ漏れなく対応している。スコープ1→AC-1/2/3、スコープ2→AC-6、
  スコープ3→AC-4、スコープ4→AC-5。判断保留（「要検討」等の宙吊り）が無く、各項目が
  「実装する／見送る」のいずれかに明確に決着している。
- geo 見送りが Issue の虚偽表示禁止原則と整合している。AC-6 + ADR-002 が
  「手元データで解決不能な唯一の要素」「不正確な geo は捏造禁止違反」「別 Issue 化」
  と論証し、UI は #572 の IP 素出し据え置きで一貫させる、と明示。Issue 本文
  「実データを取得・更新する仕組みを伴って初めて表示する」と矛盾しない。
- device-parser の置き場所（ドメイン層・純粋関数・判別不能は null）が虚偽表示禁止を
  型レベルで担保する設計になっており、Issue 原則の「推測でラベルを埋めない」を
  実装・テスト（ステップ3）で検証可能にしている。
- 「最終アクセス」を実データ化する唯一の backend 不足（`resolve` が updatedAt を
  更新しない）を正確に特定し、`recordActivity` + スロットルで塞ぐ。Issue スコープ3
  の「更新経路が無い場合はラベルを出さない」を AC-4 が条件付きで明文化している。
- スコープ外の線引きが明示的。既存 `revoke`/`revokeSession` 温存、専用 last-active 列・
  イベント駆動の不採用、相対時刻ヘルパーの全画面一括展開の見送りを「含まれないもの」
  に列挙しており、スコープクリープが入り込んでいない。
- 各 AC が「対応ステップ」列でステップに紐づいており、AC-1→1、AC-4→4,5,6,8 等の
  紐づけが実際のステップ内容と一致している（紐づけの誤りは検出されず）。

## 既存コードとの整合確認（事実確認）

- `D1SessionService.resolve`（adapter L78-107）は select のみで `updatedAt` を更新しない → 計画の記述と一致。
- `SessionDTO.updatedAt`（dto/identity.ts L68-76）は projection 済みかつ JSDoc で「最終アクセスに出すな」と明記 → 一致。
- `SessionIcon`（SecurityForm L58-76）は全行同一 glyph、`sessionTitle`（L90-93）は UA 素出し→「不明な端末」 → 一致。
- `getCurrentUser`（currentUser.ts L51-62）が `resolve(token)` を呼ぶ唯一の cache() 経路 → 計画の注入点記述と一致。
- mock（P22 L787-820）は device・geo・IP を `·` 連結 1 行 + 「最終アクセス: 相対時刻」行で構成 → 計画のリッチ化対象と一致。
- #572 ADR-002 の「最終アクセスラベルを使わない／updatedAt を将来用に保持」と本計画の段階導入方針が整合。
