# 実装計画 — Issue #460: docs(design): §7.1 ボタン形態を「規範」から「文脈ごとの判断」原則ベースへ見直す（a11y 硬直適用の緩和含む）

**複雑度:** 中〜大規模

## 目的

`spec/design/index.md` §7.1「ボタン形態の使い分け」(L127-146) を、禁止・必須(MUST)を列挙する**規範(rule-based)**から、その都度の文脈で「ここでは何が読みやすく押しやすいか」を判断するための**原則(principle-based)**へ書き換える。あわせて a11y タップ領域 44×44 の硬直適用を、WCAG の最低ラインと意図を明文化したうえで文脈判断に緩め、例外の列挙を原則の適用例へ畳み込み、§7.1 が参照する ADR の整合を取る。

## 実装ステップ

### 1. 見出し直下の導入文を原則宣言に差し替え

- **対象ファイル:** `spec/design/index.md`（§7.1「ボタン形態の使い分け」L127-129）
- **変更内容:** 「判断基準と a11y 要件を以下に定める」を、「3形態は禁止・必須の規範ではなく、*意味のまとまり・優先度・利用頻度・密度* を踏まえて『ここでは何が読みやすく押しやすいか』を判断するための指針」と明記する。§4 冒頭(L62-)の原則筆致に合わせる。
- **理由:** Issue 要件1。ドキュメント冒頭(L4)の「数値で表現できない判断基準・原則を扱う」宣言にも回帰させる。

### 2. 3形態を「向き・不向き」の指針として残す

- **対象ファイル:** `spec/design/index.md`（L131-135）
- **変更内容:** 「アイコン+ラベル（既定）」「テキストのみ」「アイコンのみ」を「こういう時はこちらが向く」という指針として残す。「テキストのみ」のタブ/トグル・フィルタチップ・リンク的ボタンの具体例は判別の手がかりとして保持しつつ、「のみ使う」等の断定を「向く/適する」に和らげる。
- **理由:** Issue 要件1。3形態の trade-off は実務上有用なので捨てず、規範から指針へトーンを変える。

### 3. アイコンのみの MUST/SHOULD を原則 + 最低ラインに再構成

- **対象ファイル:** `spec/design/index.md`（L136-140）
- **変更内容:** `aria-label` 必須・accessible name 二重化回避は **a11y 契約として §8 と整合する形で残す（緩めない）**。「同種を並置しない」は「並ぶと意味の判別が落ちるため避ける」という trade-off 説明へ。「44×44 MUST」はステップ5の a11y 原則に移送する。
- **理由:** Issue 要件1・2。SR 契約は WCAG 準拠の床なので温存し、形態・密度に関わる部分だけ指針化する。

### 4. 混在禁止(L141)+例外(a)(b)・chip close(L145)・admin(L146) を「畳んだ原則」に再編

- **対象ファイル:** `spec/design/index.md`（L141-146）
- **変更内容:** 「揃える/混在しない」を絶対規範ではなく「意味のまとまり・優先度・密度を揃えると一覧の認知負荷が下がる。ただし *選択UI(タブ/トグル)* は別カテゴリ、*密度差を意図する場合*、*親要素に内包される付属要素(chip close)*、*デスクトップ専用で密度優先の文脈(admin 行アクション)* では、揃えないことが文脈上正しい」という適用例へ変換する。DisplayModeSwitch / chip close / admin 小型行アクションを「なぜ妥当か」の例として畳み込む。
- **理由:** Issue 要件3。例外を消すのではなく、原則の適用例として再配置することで条文探しを不要にする。
- **注意（実装名の鮮度）:** admin 例外を書くときは、もはや存在しない `BTN_SM_CLASS` という名前を使わず、現実装の語彙 `pillBtn` + `pillBtnSm`（`app/components/common/styles.ts`）で書く。`pillBtnSm` は `data-[sm]:h-7`（28px）で、base `pillBtn` が持つタッチ床 `max-sm:min-h-[44px]` を `data-[sm]:max-sm:min-h-0` で解除する定数。消えた名前を書き込むと書いた瞬間にドキュメントが実装と乖離する（レビュー指摘 R1-S001/R2-S001）。

### 5. a11y タップ領域を「最低ライン明文化 + 文脈判断」へ

- **対象ファイル:** `spec/design/index.md`（§3 L56 と §7.1 の 44 記述）
- **変更内容:** WCAG を明記する。
  - 最低ライン: WCAG 2.5.8 Target Size (Minimum) AA = **24×24px** を下回らない（譲れない床）
  - 望ましい目標: 2.5.5 Target Size (Enhanced) AAA = **44×44px**（本プロジェクトの既定目標値）
  - 適用: タッチ主体の文脈（モバイル、`pointer: coarse`）では 44 を確保する。デスクトップ専用でマウス精度が前提の密度優先 UI（admin 等）は 24 を最低ラインに密度を取る判断を許す
  - 意図 =「タッチで押し間違えない」を明記
  - `spec/design/review/004.md` L259-264 の `(pointer: coarse)` 整理と語彙を揃える
  - **適用例として実装と符合させる**（レビュー指摘 R2-S002）: ① base `pillBtn` の `max-sm:min-h-[44px]` は「タッチ床 44 を担保しデスクトップは自由」という新原則そのもの。② admin の `pillBtnSm`（`data-[sm]:h-7`=28px、床を `max-sm:min-h-0` で解除）は「デスクトップ密度優先で 24 床を満たす」例。③ `Dialog` の `dialogCloseButton`（`w-8 h-8`=デスクトップ 32px / `max-sm:min-w-[44px] max-sm:min-h-[44px]`=タッチ時 44px）は「タッチでは目標 44、デスクトップでは 24 床は満たすが 44 目標未達を許容」という文脈判断の例。
- **理由:** Issue 要件2。a11y を完全な判断任せにせず、AA(24) を床・AAA(44) を目標とする二段で WCAG 準拠を保ちつつ適用に余地を残す。既存実装がこの二段原則の妥当な適用例になっていることを文面で示す。

### 6. ADR 参照を namespace 付きリンクへ修正

- **対象ファイル:** `spec/design/index.md`（L142 / L146）
- **変更内容:** bare 「ADR-002」「ADR-005」を、L179 の `[#221 ADR-003](../../.issue/221/adr.md)` と同形式で `[#292 ADR-002](../../.issue/292/adr.md)` / `[#292 ADR-005](../../.issue/292/adr.md)` に直す。44px に関わる文脈では `[#292 ADR-003](../../.issue/292/adr.md)` も適宜参照する。
- **理由:** Issue 要件4。詳細は下記「設計判断」参照。

### 7. §3 L56 / §8 との相互参照を整える

- **対象ファイル:** `spec/design/index.md`（§3 L56 / §8 L150-161）
- **変更内容:** §3 L56 の現行文言「最小 `44 × 44px` を確保する（ピル/icon-btn は 36px だが、`padding` または `min-height: 44px` のラッパで領域を担保）」を二段構成（AA 24 床 / AAA 44 目標、タッチ主体で 44 確保・デスクトップ密度優先は 24 床）へ書き換える。現実装は base `pillBtn` の `max-sm:min-h-[44px]` でタッチ床を担保しているので、「36px をラッパで担保」という旧表現も実装語彙（`max-sm:min-h-[44px]`）に寄せて更新する。§7.1 から §3・§8 を参照する。§8 のコントラスト記述同様、a11y 数値の出所を WCAG 成功基準に紐付ける。
- **理由:** Issue 要件2の整合確保。数値の二重管理による矛盾と、旧ラッパ表現の取りこぼしを防ぐ（レビュー指摘 R1-S002）。

### 8. §7.1 冒頭「使う場面」L118 の断定トーンを軽く緩める（同セクション内の一貫性）

- **対象ファイル:** `spec/design/index.md`（§7.1 L118「主要アクションボタン…にはアイコン+テキストで表示する」）
- **変更内容:** ボタン形態サブセクション(L127-)を指針化するのに合わせ、直前の L118 の「アイコン+テキストで表示する」断定を「既定としてアイコン+テキストが向く」程度に軽く和らげ、サブセクションの指針と接続する。**最小限の語調調整に留め、列挙された使用場面の内容自体は変えない。**
- **理由:** 要件①の「規範→原則」がセクション内で不徹底に見えないようにする（レビュー指摘 R1-S003）。スコープは §7.1 内に閉じる。

## 設計判断

詳細は `.issue/460/adr.md` を参照。要点:

- **ADR 参照の扱い（要件4の核心）:** §7.1 L142/L146 の bare「ADR-002」「ADR-005」は壊れた参照でも内容の取り違えでもなく、**出典 issue (#292) の namespace を省いた bare 参照**。指している決定（#292 ADR-002=DisplayModeSwitch 例外 / ADR-005=admin `BTN_SM_CLASS` 例外）は内容的に正しい。問題は、CLAUDE.md が ADR 番号を `.issue/70/adr.md`（ADR-002=`@apply` 不使用 / ADR-005=backdrop-filter）に紐付けて運用しているため、読者が同番号を #70 のものと誤読すること。→ **「正しい参照に直す」**（`[#292 ADR-NNN](../../.issue/292/adr.md)` 形式）を採用。ADR の新規起票・削除・本文変更は不要。
- **WCAG 最低ラインの明文化方針:** 24×24(AA 最低)を譲れない床、44×44(AAA)を既定目標とする二段で書く。判断余地は「床と目標の間で、タッチ/デスクトップ・密度・役割に応じて目標値に達しない選択を許す」範囲に限定し、AA 未満を許さない。`aria-label` 等の SR 契約は緩めず §8 と一体で残す。
- **原則の畳み込み方:** 例外を消さず「原則 → なぜこの文脈では揃えない/縮めるのが正しいか」の適用例として再配置。既存実装（admin `h-7`・chip close・DisplayModeSwitch・`Dialog` の `max-sm:min-44`）は全て原則の妥当な帰結として残り、ドキュメントと実装の非整合を作らない。

## リスクと注意点

- **a11y を緩めすぎるリスク:** 24×24 を床として明記し、`aria-label` 等 SR 契約を §8 と一体で温存することで WCAG AA 準拠は維持する。「判断余地」は AAA(44) と AA(24) の間に限定し、AA 未満を許す書き方にしない。
- **#459 との順序依存:** 本 Issue が先（設計の根拠）、#459 が後（適用）。「混在禁止」を緩めても #459 が「揃えない」結論を出すとは限らない — 判断材料の提供に留め、実装方針を先取りしない旨を明記する。
- **ADR 番号の二重運用:** `.issue/70/adr.md`（CLAUDE.md anchor）と `.issue/292/adr.md` が同じ ADR-002/005 番号を持つ。namespace 付きリンク化で誤読は解けるが、「#292 の ADR」と明示することが肝。CLAUDE.md styling 節（#70 anchor）には手を入れない。
- **既存実装との整合:** 書き換え後も admin `h-7` / chip close / DisplayModeSwitch / `Dialog` `max-sm:min-44` は原則の適用例として妥当。逆に「44 を床に格上げ」しないこと（admin が即違反になる）。
