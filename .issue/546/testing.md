## 確認環境

このIssueはバックエンド変更を伴わない認証・エラー面の UI 追従:
1. 認証フォーム3枚（P01-signup / P03-login / P01b-admin-setup）の送信失敗サマリーを `.alert alert-error` 案D へ追従。
2. P34 エラーページにバックリンク「一つ前に戻る」を追加し、アクションをバリアント別に出し分け。

実機確認はローカル開発サーバで行う。

### 検証環境の起動

```
pnpm dev
```

`vite dev`（Cloudflare ランタイム）でローカルサーバが起動する。表示された URL をブラウザで開いて確認する。

D1 ローカルにシードが無い場合はマイグレーション適用 → シード投入を行う:

```
pnpm db:migrate
pnpm seed:dev-admin
```

`seed:dev-admin` は dev 用の管理ユーザー（既存メール）を作る。確認には少なくとも以下が必要:

- 既存ユーザー（サインアップ失敗＝メール重複を誘発する用 / ログイン失敗を誘発する用）
- `/setup`（初回管理者セットアップ画面。Setup Token の誤り/未設定で失敗サマリーを誘発する）

確認用データが不足する場合は UI からアカウント作成して既存メールを用意するか、`pnpm db:execute:local --file <SQLファイル>` で補う。

### デプロイ方法

なし（検証環境のみで確認できる。ステージング反映が必要な場合は `pnpm deploy:staging`）。

## 確認項目

### 1. P01 サインアップ — 送信失敗サマリーの案D 追従

- **目的:** 登録失敗時のエラーサマリーが `.alert alert-error` 案D（白地 + error ヘアライン枠 + アイコン + title + body）で表示されること。
- **手順:**
  1. `/signup` を開く。
  2. 既存メール（`seed:dev-admin` で作成したアドレス等）で登録を試みる。
  3. 送信し、エラーサマリーの見た目を確認する。
- **期待結果:** 白地に error 色のヘアライン枠 + 左にアイコン + 「登録に失敗しました。」の title + 詳細 body の案D アラートが出る。旧 `FORM_ERROR` の塗りつぶし箱（`bg-error-surface`）ではない。
- **確認ポイント:** 塗りつぶしでなく白地+細枠であること、アイコン併用、リテラル px 混入が無いこと。field 単位のバリデーションエラー（必須未入力等）は従来どおり各 field 直下に出る（回帰）。

### 2. P03 ログイン — 失敗サマリーの案D 追従と未認証 alert の回帰

- **目的:** ログイン失敗サマリーが案D 化され、かつ既存の未認証 status alert が壊れていないこと。
- **手順:**
  1. `/login` を開く。
  2. 登録済みメール + 誤ったパスワードでログインを試みる。
  3. エラーサマリーを確認。
  4. （別途）未認証アカウントでログインし、未認証 alert + 再送ボタンが従来どおり出ることを確認。
- **期待結果:** 失敗時に「ログインできませんでした。」の案D アラート（白地+error枠+アイコン）。未認証時は従来の `role="status"` 案D alert + 「確認メールを再送」導線（回帰）。
- **確認ポイント:** 失敗サマリーは `role="alert"`、未認証 alert は `role="status"` のまま。両者を取り違えていないこと。

### 3. P01b 管理者セットアップ — Setup Token エラーの案D 追従

- **目的:** Setup Token の誤り/未設定および一般登録失敗が、それぞれ正しい title の案D アラートで表示されること。
- **手順:**
  1. `/setup` を開く。
  2. 誤った Setup Token を入力して送信 → サマリーを確認。
  3. （Setup Token 未設定環境の場合）未設定時のサマリーを確認。
- **期待結果:** Token 誤り → 「Setup Token が正しくありません。」、未設定 → 「Setup Token が設定されていません。」の title + 「値を確認してもう一度入力してください。」body の案D アラート。一般登録失敗は「登録に失敗しました。」案D。
- **確認ポイント:** 既存の `role="note"` callout（「このページは特権操作です」）は案D のまま壊れていない（回帰）。

### 4. P34 エラーページ — バックリンクとバリアント別アクション

- **目的:** 全バリアントにバックリンクが出て、アクションが kind 別に出し分けられること。
- **手順:**
  1. `/error?kind=notFound` を開く → アクションとバックリンクを確認。
  2. `/error?kind=forbidden` を開く → 同上。
  3. `/error?kind=gone` を開く → 同上。
  4. `/error?kind=system` を開く → 同上。
  5. 各画面で「一つ前に戻る」を押下し、直前ページへ戻ることを確認。
  6. `system` の「再読み込み」を押下し、ページがリロードされることを確認。
- **期待結果:**
  - 404(notFound): プライマリ「ホームへ戻る」+ セカンダリ「検索ページを開く」+ 検索ボックス + バックリンク。
  - 403(forbidden): プライマリ「ログイン」(`/login`) + セカンダリ「ホームへ戻る」+ バックリンク（検索ボックスなし）。
  - 410(gone): プライマリ「ホームへ戻る」+ 検索ボックス + バックリンク。
  - 500(system): プライマリ「再読み込み」+ セカンダリ「ホームへ戻る」+ バックリンク（検索ボックスなし）。
  - 「一つ前に戻る」押下 → ブラウザ履歴で直前ページへ戻る。「再読み込み」押下 → 現ページがリロードされる。
- **確認ポイント:** バックリンクのスタイル（白地・ink-tertiary・hover で ink/surface）がモックと一致。プライマリアクションに accent（`data-primary`）が当たっている。

## エッジケース・異常系

### 1. バックリンクで戻り先が無い場合

- **目的:** 直接 `/error?kind=...` に外部から到達して履歴が無い場合のバックリンク挙動。
- **手順:** 新規タブで直接 `/error?kind=notFound` を開き「一つ前に戻る」を押下。
- **期待結果:** `history.back()` 相当の標準挙動（履歴が無ければ何も起きない or ブラウザ既定）。エラーや白画面にならない。

### 2. 不正な kind パラメータ

- **目的:** `validateSearch` の `catch("notFound")` が機能すること。
- **手順:** `/error?kind=invalid` を開く。
- **期待結果:** notFound バリアント（404）として表示され、バックリンク・検索ボックスが出る。

## 既存機能への影響確認

- **認証フォームの field バリデーション:** 案D 化は送信失敗サマリーのみ。各 field 直下のバリデーションエラー表示は不変（回帰なし）。
- **P04 / P05 パスワードリセット:** `FORM_ERROR` を温存しているため、送信失敗時の表示は従来どおり（変更なし）。
- **P02 メール検証 / P06 メール変更確認 / P07 ランディング:** 本Issueで触らない。従来どおり表示される（P06 の warning 案D alert、P07 のヘッダー/hero/footer 含む）。
- **ErrorPage の SSR:** client 島（`ErrorNavActions`）切り出し後も、エラーページ本体がサーバーレンダリングされ初期表示・タイトルが正しく出ること。
