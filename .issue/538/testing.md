## 確認項目

### 1. 単一ファイルアップロードが投げっぱなしになる

- **対応する受け入れ基準:** AC-1
- **目的:** モーダルがアップロード API 完了時点で `queued` 結果ビューを表示し、推論待ち（waiting）・編集（editing）に遷移しないこと。
- **手順:**
  1. ヘッダーのアップロードボタンでモーダル（`#upload`）を開く。
  2. Markdown ファイルを 1 件ドロップして送信する。
  3. アップロード完了直後のモーダル表示を観察する。
- **期待結果:** 「1 件をキューに追加しました」相当のメッセージと「キュー画面を開く」リンクが即座に表示される。スピナーで LLM 完了を待つ画面・プレビュー編集フォームは現れない。
- **確認ポイント:** LLM の推論が終わる前（数秒以内）に結果ビューが出ること。文言に「キューで編集・保存できる」旨が含まれること。

### 2. 複数ファイルアップロードも同じ `queued` ビューに着地する

- **対応する受け入れ基準:** AC-1
- **目的:** 単一・複数で結果ビューが統一されていること。
- **手順:**
  1. モーダルでファイルを 3 件まとめて送信する。
  2. 件数進捗（uploading）後の表示を観察する。
- **期待結果:** 「3 件をキューに追加しました」＋キューへのリンクが表示される。
- **確認ポイント:** 旧 `multiResult` と同等の情報（成功件数）が出ること。

### 3. `queued` ビューからの「続けてアップロード」「閉じる」

- **対応する受け入れ基準:** AC-2
- **目的:** 結果ビューで操作がブロックされないこと。
- **手順:**
  1. 確認項目 1 の状態（`queued` ビュー）にする。
  2. 「続けてアップロード」を押す → ドロップゾーン（select）に戻ることを確認し、別ファイルを即座に送信する。
  3. 再度 `queued` にして「閉じる」を押す。
- **期待結果:** 2 で待ち時間なく次のアップロードができる。3 でモーダルが閉じ、背後のページ操作にすぐ移れる。
- **確認ポイント:** `queued` 表示中に disabled なボタン・スピナー・ジョブ完了待ち要素が存在しないこと。「続けてアップロード」で前回の検証エラー表示が残らないこと（カスタムプロンプト入力は保持される）。

### 4. キュー行からの編集 → 保存（commit）

- **対応する受け入れ基準:** AC-3
- **目的:** `previewing` ジョブをキュー導線で編集して保存できること（本 Issue の核心その 2）。
- **手順:**
  1. ファイルをアップロードし、`/upload` のキューでジョブが `previewing`（プレビュー保留）になるまで待つ。
  2. 該当行の「編集」ボタンを押す。
  3. 開いた編集ダイアログでタイトル・ディレクトリ・タグ・Front Matter をそれぞれ変更する。
  4. 保存（commit）する。
- **期待結果:** 作成されたノートのページ（`/notes/$noteId`）に遷移し、変更したタイトル・ディレクトリ・タグ・Front Matter が反映されている。
- **確認ポイント:** 「編集」ボタンが `previewing` の行にのみ表示されること。ダイアログを開いた直後タイトル入力にフォーカスが当たること。ディレクトリツリーが選択肢として読み込まれること。

### 5. 編集ダイアログからの破棄・再生成

- **対応する受け入れ基準:** AC-4
- **目的:** 編集ビューから破棄・再生成が実行でき、再生成はキューのポーリング表示が状態を追跡すること。
- **手順:**
  1. `previewing` の行で編集ダイアログを開き、「破棄」を実行する。
  2. 別のファイルで再び `previewing` にし、編集ダイアログから「再生成」を実行する。
  3. 再生成後のキュー表示を観察する。
- **期待結果:** 破棄: ダイアログが閉じ、行が破棄済みの表示になる。再生成: ダイアログが閉じ、行が `pending / processing` の進捗表示に変わり、完了後 `previewing` に戻る。
- **確認ポイント:** 再生成後にモーダル内で待機する旧挙動には**ならない**（ダイアログが閉じてキュー行で追跡するのが新仕様）。`previewing` 復帰後に再度「編集」を開くと新しい提案値が見えること。

### 6. ヘッダーのキュー件数バッジ

- **対応する受け入れ基準:** AC-5
- **目的:** 未処理（pending / processing / previewing）件数のバッジが表示され、各操作後に更新されること。
- **手順:**
  1. 未処理ジョブ 0 件の状態でヘッダーを確認する（バッジ非表示）。
  2. モーダルからファイルを 1 件アップロードする → バッジが「1」になることを確認。
  3. `/upload` ページのアップロードフォーム（モーダルでない経路）からもう 1 件アップロードする → バッジが「2」になることを確認。
  4. 片方を編集ダイアログから保存（commit）する → バッジが「1」に減ることを確認。
  5. 残りを破棄する → バッジが消えることを確認。
- **期待結果:** 各操作直後（ページリロードなし）にバッジ件数が追随する。0 件で非表示。
- **確認ポイント:** 手順 3 の `/upload` ページ経由（`UploadForm`）でも更新されること（モーダル経路だけでないこと）。アップロードボタンの `aria-label` に件数が含まれること（DevTools で確認）。

### 7. モーダル結果ビューからキューへの誘導

- **対応する受け入れ基準:** AC-5
- **目的:** `queued` ビューの「キュー画面を開く」リンクで `/upload` に遷移し、モーダルが閉じること。
- **手順:**
  1. アップロード後の `queued` ビューで「キュー画面を開く」を押す。
- **期待結果:** `/upload` に遷移し（URL から `#upload` ハッシュが落ち）、モーダルは閉じ、いまアップロードしたジョブがキューに見える。

### 8. spec・コピーの更新確認（ドキュメント）

- **対応する受け入れ基準:** AC-6
- **目的:** 方針転換がドキュメントに反映されていること。
- **手順:**
  1. `/upload` ページの説明文を画面で確認する。
  2. `spec/pages/index.md` の P13 セクション（170 行目付近）とヘッダー CTA の記述（18 行目付近）、`.issue/538/adr.md` ADR-004 を読む。
- **期待結果:** 「モーダルで完結」前提の記述が「投げっぱなし＋編集はキュー画面」に更新され、ADR-004 に `.issue/319` / `.issue/253` の supersede が記録されている。

## エッジケース・異常系

### 1. 複数アップロードの部分失敗

- **目的:** `queued` ビューが失敗ファイルを明示すること。
- **手順:** 受け付けられないファイル（拡張子不正・サイズ超過等、クライアント検証を通過してサーバーで失敗するもの）を含む複数件を送信する。
- **期待結果:** 「N 件をキューに追加しました（M 件失敗）」と失敗ファイル名リストが表示され、成功分はキューに積まれる。

### 2. 単一アップロードの失敗

- **目的:** 失敗時は `select` に戻りインラインエラーが出ること（旧 `failed` ビューは存在しない）。
- **手順:** サーバーで失敗するファイルを 1 件送信する。
- **期待結果:** ドロップゾーンに戻り、エラーメッセージがインライン表示される。再送信が可能。

### 3. 編集中にジョブが他で確定された場合（クロスタブ）

- **目的:** 競合がフォームのエラー表示で吸収されること。
- **手順:** タブ A で `previewing` の編集ダイアログを開いたまま、タブ B で同じジョブを保存（または破棄）する。タブ A で保存を試みる。
- **期待結果:** タブ A はフォーム内のエラー表示（conflict / not found 系）になるか、キューのポーリングで行ごと消えてダイアログが閉じる。アプリがクラッシュしない。
- **確認ポイント:** ダイアログが無言で閉じるのは行アンマウントによる既知の許容トレードオフ（adr.md ADR-001）。バグと混同しないこと。

### 4. バッジ取得失敗時

- **目的:** バッジ取得失敗が導線を塞がないこと。
- **手順:** 未ログイン状態（またはセッション失効後）でバッジが描画されるページを開く。
- **期待結果:** バッジは黙って非表示になり、ヘッダーのアップロードボタン自体は壊れない。

### 5. タブ放置後の visible 復帰

- **目的:** visibilitychange でバッジが再取得されること。
- **手順:** アップロード直後（pending）に別タブへ移り、ジョブが `previewing` になる頃に元タブへ戻る。
- **期待結果:** タブ復帰時にバッジが最新件数へ更新される（放置中に即時更新されないのは ADR-002 の許容トレードオフ）。

## 既存機能への影響確認

- **`/upload` キューの既存行アクション**: `previewing` 行の「ノートとして保存」（提案値のまま即時 commit）・再生成・破棄、`failed` 行の再試行が従来どおり動くこと。各操作後にバッジも更新されること。
- **`#upload` ハッシュ駆動のモーダル開閉**: ヘッダーのアップロードボタンでモーダルが開き、ESC / 閉じるで URL からハッシュが消えること（`UploadDialogMount` / `UploadButton` の契約は変更しないため回帰確認のみ）。
- **カスタムプロンプト accordion**: モーダルのアップロード時にカスタムプロンプトを指定でき、生成結果に反映されること（縮退で削除されていないこと）。
- **ノート一覧の更新**: アップロード → キューで保存後、`/upload` 表示中のキュー一覧やノート一覧（invalidate 対象）が古い状態のまま残らないこと。
- **自動テスト**: `pnpm typecheck && pnpm lint:fix && pnpm format`、`pnpm test:unit`、`pnpm test:integration` が通ること。
