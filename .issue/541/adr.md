# ADR — Issue #541: 領域2「取り込み・書き出し」(P13/P15/P16) のモック実装追従

## ADR-001: クライアント検証ヘルパーの置き場所

### Status
Proposed

### Context
P13 のクライアント検証（未対応形式 / サイズ超過）は、アップロードページ（`UploadForm.tsx`）とヘッダーのアップロードモーダル（`UploadDialog.tsx` の `SelectView`）の両方で必要になる。同じ判定を二重実装するとモックとの一致がずれやすく、サポート形式の判定基準も分散する。

### Decision
検証ヘルパーを `UploadForm.tsx` 内のローカル純関数として定義し、`UploadDialog.tsx` から import して共有する。サポート形式の判定は `IngestionService.detectKind(mimeType, fileName)`（I/O を持たない純ドメイン関数）を再利用する。新規ファイルを増やさず、import の取り回しが軽い方を採る。

### Consequences
- 良い点: サポート形式判定の SSOT がドメイン（`detectKind`）に残る。ページ/モーダルで検証挙動が一致する。新規ファイルを増やさない。
- トレードオフ: `UploadDialog.tsx` が `UploadForm.tsx` に依存する（同一 feature 内なので許容範囲）。

## ADR-002: サイズ上限値の出所

### Status
Proposed

### Context
モックは「上限 50 MB」固定表記。実サーバーは `IngestionLimits`（per-kind 可変・運用設定、`defaultMaxBytes: 50 * 1024 * 1024`）で最終判定する。クライアントで正確な per-kind 上限を知ろうとすると過剰結合になる。

### Decision
クライアントの UX ガードは `defaultMaxBytes`（= 50 MB）相当の単一の名前付き定数で「明らかな超過」のみ弾き、正確な最終判定はサーバーに委ねる二段構えとする。クライアント検証はあくまで UX 補助であり、トランスポート境界（serverAction の inputValidator）/ VO 構築の二点検証とは別レイヤー。

### Consequences
- 良い点: クライアントが運用設定に結合しない。明らかな超過を送信前に弾けて UX が向上。サーバー側の最終検証は温存され安全性を損なわない。
- トレードオフ: per-kind で 50 MB 未満の上限がある形式では、クライアントで弾けずサーバーで弾かれるケースが残る（許容 — 最終判定はサーバーが正）。

## ADR-003: P15 推奨バナーの発火条件

### Status
Proposed

### Context
モック文言は「選択中の N 件 + メディア埋め込みで容量増 → 非同期ジョブを推奨」。推定サイズ（モック「約 28 MB」）は実データ無しに正確化できない。単一（single）エクスポートは即時 DL の文脈で推奨が不要。

### Decision
発火条件は「bulk（`noteId === null`）かつ **対象 1 件以上**（`bulkCount > 0`）かつ（件数 > 即時上限(50) または `embedMedia` が ON）」とする。`bulkCount > 0` は実装時に追加した妥当なガード — 対象ゼロ件で推奨を出すのは無意味なため（ブラウザ検証 TC-004 で確認）。single 文脈では出さない。文言の可変部は件数のみ実装し、推定サイズは含めない（または定性表現に留める）。バナーは推奨表示のみで送信を阻害しない。

### Consequences
- 良い点: 実データ無しでも安定して導出できる条件。モックの意図（大量件数 / メディア埋め込みで非同期推奨）を満たす。
- トレードオフ: 推定サイズを出さないためモック文言と完全一致はしない（実装可能性を優先）。

## ADR-004: アップロードモーダルへの検証バナー追加（SSOT 逸脱の明示）

### Status
Proposed

### Context
P13 のクライアント検証バナー（`.alert-error` / `.alert-warning`）は、SSOT であるモック上ではページ側 `P13-upload.html` にのみ描かれており、モーダルモック（`P13-upload-modal.html` / `P13a-upload-modal.html`）には「箱」が存在しない（dropzone のみ。P13a にあるのは汎用解析エラーの `.inline-alert`）。一方で #539 連携メモは委譲対象を「P13 アップロード（`UploadDialog.tsx` / `UploadForm.tsx`）」と両方明記している。「モックに無い UI をモーダルに足す」判断を黙示にすると、スコープ逸脱と見分けがつかない。

### Decision
モーダル（`UploadDialog.tsx` の `SelectView`）にもページと同じ検証バナーを追加する。根拠は (1) #539 委譲メモが `UploadDialog.tsx` を明示的に委譲対象に含めること、(2) ADR-001 のページ/モーダル挙動一致原則（同じドロップゾーン体験を両所で一致させる）。これはモック外 UI の意図的な追加であり、本 ADR でその逸脱を明示的に記録する。

### Consequences
- 良い点: ページ・モーダルでアップロード検証体験が一致する。#539 委譲意図（両コンポーネント）を満たす。
- トレードオフ: モックに図示されていない UI を足すため、厳密なモック準拠からは逸脱する。逸脱を本 ADR で明示することで説明責任を果たす。

## ADR-005: P15 推奨バナーから「メール」文言を削除

### Status
Accepted（実装時に確認）

### Context
モック（`P15-export.html` L728）の info バナー本文は「完了通知はメールと `エクスポートジョブ一覧` に送られます」と記載。plan.md ステップ4は「エクスポート完了のメール通知が実装に実在するか確認し、未実装なら『メール』を落とす」と指示。

### Decision
実装を grep で確認した結果、エクスポート完了のメール通知機能は存在しない（`app/core/domain/export` / `app/core/application/export` に notification/mail ポートやイベント送信は無く、`email` の出現は identity 認証のユーザーメールアドレスのみ）。未実装機能を約束する UI にしないため、「メール」を文言から削除し「完了したら `エクスポートジョブ一覧` から確認できます。」に変更した。

### Consequences
- 良い点: 実装に存在しない通知経路をユーザーに約束しない。
- トレードオフ: モック文言と完全一致はしない。将来メール通知が実装されたら文言を戻す。
- 加えて ADR-003 の通り推定サイズ「約 28 MB」も実データ無しでは導出できないため文言から省き「容量が増えるため」とした。
