# レビュー round-1 — Issue #583 計画（視点: 要件カバレッジ・スコープ整合性）

対象: `.issue/583/plan.md` / `.issue/583/adr.md`
レビュー観点: (1) Issue 要件が受け入れ基準に漏れなく落ちているか / (2) 各基準が検証可能か / (3) 基準と実装ステップの紐づけ / (4) スコープ外混入

---

#### 問題点（要修正）

- **[P-001]** 手動保存（フル保存）後にフラグが clear されず、保存済みノートで警告が残留する。AC-3 の「保存成功でクリア」が autosave 限定になっている。
  - 理由: 計画の AC-3・ステップ2 は「`dirtyKeys` が空に戻る＝autosave 成功」を唯一の clear 契機にしている。しかし実コードを確認すると、`dirtyKeys` を `EMPTY_DIRTY` にリセットする reducer アクションは `autosaveSuccess` **だけ**で（`editorState.ts:497-503`）、保存ボタン経由のフル保存（`NoteEditor.tsx:319` `saveNote` → `:330` で detail へ navigate）は `dirtyKeys` をリセットしない。つまりユーザーが「編集 → 保存ボタンを押して即 detail へ遷移 → 公開設定を開く」という最も自然な保存フローを取ると、`dirtyKeys` は非空のまま遷移直前に最後の sync effect が走り、sessionStorage には dirty=true が残る。結果、**正しく保存したのに「未保存の変更があります」が出る**。これは AC-5（保存済みでは警告が出ない）に正面から反する誤検知であり、しかも主ユースケースで高頻度に発生する。計画は「過剰検知＝タブが落ちた時だけの稀なケースで安全側」とリスク欄に書いているが、実際にはタブ落ちではなく通常の手動保存で恒常的に発生する。
  - 提案: 手動保存の成功時にもフラグを clear する経路を明示する。最小修正は `NoteEditor.tsx` の `saveNote` 成功直後（navigate 前）に `clearNoteUnsaved(props.noteId)` を直接呼ぶこと（edit モードのみ）。`onSubmit` の成功分岐は usecase を経ない純クライアント処理を足してよい箇所なので、sync effect 任せにせず明示 clear するのが確実。ステップ2 に「手動保存成功時の clear」を追記し、AC-3 を「autosave 成功 **または** 手動保存成功で clear される」と書き換えること。テスト方針にも手動保存→clear のケースを追加する。

- **[P-002]** ステップ2 の sync effect は「dirty 非空→set / 空→clear」だが、autosave 成功直後の clear と「再編集で再 dirty」の整合が曖昧で、検証手順が AC に紐づいていない。
  - 理由: AC-3 は「autosave 成功で `dirtyKeys` が空に戻るとクリア」とあるが、ステップ2 の `useEffect([dirtyKeys])` は「`size>0`→set, `===0`→clear」という素朴なミラーで、これ自体は AC-3 を満たす。ただし P-001 で挙げた手動保存と異なり、autosave 成功は `dirtyKeys` を空にするので effect が clear を呼ぶ — ここは設計として整合している。問題は AC-3 の検証可能性で、現状の文言「autosave が成功して dirtyKeys が空に戻ると」は実装内部状態を前提にしており、**ブラックボックスで検証できる受け入れ条件になっていない**。手動確認手順（テスト方針）も autosave 完了の観測手段（AutosaveIndicator が「保存しました」になるのを待つ等）に触れていない。
  - 提案: AC-3 を「編集後 autosave 完了（AutosaveIndicator が保存済み表示）を待ってから公開設定を開くと警告が出ない」のように観測可能な外形で書き直す。テスト方針の手動確認にも autosave 完了の待ち方を明記する。

#### 改善提案（検討推奨）

- **[S-001]** Issue 本文のモック行番号（`:717-746`）と計画／ADR の行番号（`:963-973`, `:955-975`）が食い違っている点を一言補足するとよい。
  - 理由: 実ファイルを確認すると `.safety-check` の実体は `:963-973`（plan/ADR が正しい）で、Issue 本文の `:717-746` は CSS 定義側の古い参照とみられる。文言・`role="status"`・本文テキストは plan の転記とモック実体が verbatim 一致しており実害はないが、レビュー時の混乱を避けるため plan 調査結果に「Issue 本文の行番号は旧版、SSOT は `:963-973`」と注記しておくと親切。

- **[S-002]** AC-2 の「FrontMatter・タグ・ディレクトリのいずれかを編集すると未保存フラグが立つ」の検証は、各 setter が `withDirty` を通ることに依存している。タグの「draft 入力のみ（未確定）」は dirty にしない仕様（`editorState.ts:setTagDraft`）なので、AC-2 の検証手順では「タグを確定（Enter/追加）した場合」に限ること明示すると、実装と AC のズレを防げる。
  - 理由: 未確定 draft では dirty が立たない既存仕様があり、AC-2 を「タグを入力したら」と素朴に検証すると誤って fail 判定する恐れがある。

#### 良い点

- ADR-001 の案2 却下理由が秀逸。`publishedAt`（公開操作ごとに再スタンプ／private で null）と `updatedAt`（全編集保存で進む）が別クロックで dirty を構造的に表せない、という分析は実コード（`publication/entity.ts`, `dto/note.ts`）の確認に裏打ちされており、「誤検知リスク」どころか「要件を満たせない」と一段踏み込んだ正しい結論を出している。Issue が提示した2案の評価として模範的。
- 案1 を Context ではなく `sessionStorage` で実装する判断が、edit/detail が別 RSC ツリー（別ルート・別 server fn）で Context 橋渡し不可という実コード制約から正しく導かれている。`localStorage` でなく `sessionStorage` を選ぶ理由（揮発性・別タブ/翌日誤検知回避）も `displayPreference` との性質差を踏まえて明快。
- スコープ外（ナビゲーションガード useBlocker/beforeunload、案2 の DTO 比較、複数タブ同期）が各々「なぜ外すか」付きで明示され、Issue が求めていない作業の混入がない。スコープ整合性は良好。
- AC-1〜AC-6 が Issue チェックリスト3項目（ADR 化 / 供給実装 / モック追従）を過不足なく分解しており、各 AC に由来と対応ステップが紐づいている。モック文言（タイトル・本文・`role="status"`）の verbatim 転記方針も明記済み。
- dirty 判定ロジックを新設せず既存 `dirtyKeys` にミラーするだけ、という最小介入の方針が、レイヤー内側（domain/usecase/DTO）への影響ゼロという ADR の主張と一貫している。

#### スコープ・カバレッジ総評

Issue チェックリストの3項目は AC に漏れなく落ちており、スコープ外混入もない。ただし AC-3／AC-5 の「保存済みでは警告が出ない」が **手動フル保存パスを取りこぼしており（P-001）**、主ユースケースで誤検知する。ここが最重要の要修正点。P-002 は AC の検証可能性、S-001/S-002 は精度向上。
