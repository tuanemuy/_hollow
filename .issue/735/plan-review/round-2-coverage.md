- **[S-001]（AC-6 の退避時終端条件の曖昧さ）→ 妥当に反映。** AC-6 が「PoC 成立時／不成立時」の二分岐で再定義され、不成立時は「本実装に進まず ADR-001 (D) へ退避、未解決事項として `.issue/735` に記録、AC-1〜5 は持ち越し（未達）として Issue を close せず open のまま据え置く」と終端条件が固定された。ステップ1の判定基準・リスク欄とも整合。完了判定がぶれない。
- **[S-002]（AC-4 head 回帰の検証手段未具体化）→ 妥当に反映。** AC 表に「AC-4 検証注記」を追加し「(a) `head.test.ts` 等が緑、または (b) 正常系 curl 本文に `<title>`/OG/JSON-LD が従来どおり含まれることを grep で確認」と二択で具体化。ステップ5・テスト方針にも反映済みで、検証可能性を満たす。
- **[S-003]（PoC で二重取得回数を実測）→ 妥当に反映。** ステップ1 の検証項目 3 に「正常系の curl 時に `getPublicNote` の実行回数をログ／カウンタで実測（1回か2回か）」を追加。後続の最適化要否判断の材料を PoC で同時取得する設計になった。

## 新規確認（Round 2 での再検証）

- **公開系3ルートのカバレッジは引き続き完全。** `$noteId`(byId) / `$noteSlug`(bySlug、共通 `PublicNoteDetail`) / `$username`(profile) が AC-1/AC-2/AC-3 と1対1で対応。Round 1 から修正対象の増減なし。
- **Issue「あるべき動作」3項（ノート→410 / ユーザー→404 / 正常系 200）に AC-1〜AC-4 が正対。** 列挙耐性要請は AC-5 + ADR-003 で固定。確実性評価の要請（Issue「考えられるアプローチ」の確実性・保守性・二重レンダリングコスト評価）は ADR-001 の方式比較・リスク欄・PoC で網羅。
- **スコープ外混入なし。** P-003 反映で新設された共通ヘルパー `publicStatusBridge`（純 `.ts`、コールバック DI）は、本 Issue の「ステータス付与を presentation に閉じる」目的に必要な最小限の抽象であり、スコープ逸脱ではない。`HTTP_STATUS_BY_KIND` への 410 追加回避・ドメイン/usecase 無改変・方式(d) 温存・SPA 除外・認証系除外はすべて「やらない理由」付きで維持。
- **plan ↔ adr の整合維持。** Round 1 で arch-risk 側 P-002（二重取得が構造上必発）を反映した記述が plan リスク欄・ADR-001 Decision/Consequences の双方に一貫して入っており、coverage 観点で AC-4（正常系回帰なし）とも矛盾しない。

## 改善提案（検討推奨）

- **[S-001]** AC-5 の「対応ステップ」が `1, 2, 3` でステップ5（手動検証）を含まないが、AC-5 の列挙耐性のうち「ステータスで存在有無を区別しない（ノート一律 410 / ユーザー一律 404）」は最終的に実機 curl（ステップ5）で観測して初めて検証できる。
  - 理由: ステップ5 の手動検証項目には既に「存在しない id → 410」「非公開ノートの id でも 410」「存在しないユーザー → 404」が列挙されており、これはまさに AC-5 の「存在しない／非公開／deleted/suspended をステータスで区別しない」を実機で裏取りする内容。AC-1〜3 はステップ5を対応ステップに含むのに、それらの列挙耐性を束ねる AC-5 だけステップ5を含まないのは紐づけの軽微な非対称。AC-5 の TOCTOU 例外（画面 410/404・HTTP 200 許容）も含め、検証は実装段（ステップ2/3）の設計意図とステップ5の観測で担保される。
  - 提案: AC-5 の対応ステップに `5` を加えて `1, 2, 3, 5` とする（実機で「非公開も存在しないも同一ステータス」を観測する点を明示）。または AC-5 の検証は AC-1〜3 のステップ5観測に内包される旨を1行注記する。いずれも軽微で、必須ではない。

## 良い点

- **Round 1 指摘の反映が忠実かつ過不足ない。** 5 件すべてが提案趣旨どおりに反映され、AC 表・スコープ節・ステップ・テスト方針・adr が横断的に整合更新されている。反映に伴うスコープ拡大や新たな不整合の混入も無い。
- **PoC ゲートの終端条件が完全に閉じている。** PoC 不成立時に「本実装に進まず ADR-001 (D) へ退避し Issue を open 据え置き」という撤退条件が AC-6・ステップ1判定基準・リスク欄の3箇所で一貫。要件未達のまま誤って close する事故を構造的に防いでいる。
- **認証系スコープ除外の根拠が Issue 本文と完全整合。** Issue「影響範囲」での同根本言及と「あるべき動作」の公開系3ルート限定の差を明示的に橋渡しし、横展開を別 Issue として切る判断が読み手に追える。
- **検証可能性が全 AC で担保されている。** AC-4 の head 回帰（test 緑 or curl grep）、AC-6 の二分岐終端条件、二重取得の PoC 実測まで、各 AC が「何をもって満たしたとみなすか」を具体的な手段で定義している。
