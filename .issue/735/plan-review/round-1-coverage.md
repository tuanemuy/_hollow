# Plan Review (Round 1) — Issue #735 / 視点: 要件カバレッジ・スコープ整合性

レビュー対象: `.issue/735/plan.md` / `.issue/735/adr.md`
レビュー視点: Issue の要件カバレッジ・スコープ整合性
結論: **問題点 1 / 改善提案 4**。受け入れ基準と公開系3ルートのカバレッジ、PoC フォールバック設計はおおむね妥当。要件と AC の紐づけに 1 点の漏れ（AC-2 のステップ紐づけ）がある。

- 公開系3ルートの実コードを確認: `app/routes/notes/public/$noteId.tsx`（`renderPublicNoteById`）/ `app/routes/u/$username/$noteSlug.tsx`（`renderPublicNote`、共通 `PublicNoteDetail` を bySlug で使用）/ `app/routes/u/$username/index.tsx`（`renderUserPublicTop`）。3ルートすべてが plan の修正対象に列挙されており、カバレッジに漏れなし。
- plan/adr が依拠する既存パターンを実コードで裏取り: `errorResponseMiddleware`（`isRedirect||isNotFound` 素通し → 他は `setResponseStatus(httpStatusFor(...))`）、`errorResponse.ts`（`HTTP_STATUS_BY_KIND` に 410/gone エントリ無し、notFound=404）、`publicNoteMeta.ts`（usecase 直接呼び・NotFound→null の前段分離先行例）、meta loader（`loadProfileMeta` が `getPublicProfile` を直接呼ぶ）。いずれも plan の記述と一致。
- usecase シグネチャを確認: `getPublicNote`/`getPublicProfile` は `ServiceArgs<T>`（`{ container, input }`）。plan 擬似コードの呼び出し形と一致。`getPublicNote` の入力は `{kind:"byId",noteId}` / `{kind:"bySlug",username,slug}` で plan と一致。
- テストパターン裏取り: `app/core/presentation/__tests__/csrfMiddleware.test.ts` が実在し `setResponseStatus` を使う。plan ステップ4の「既存パターンに倣う」根拠は妥当。
- コンポーネント側 #599 方式(d) の温存対象: `UserPublicTop.tsx:123-125` で `isNotFoundError`→`ErrorPage kind="notFound"` を確認。二重防御として温存する plan の前提は実在。

## 問題点（要修正）

- **[P-001]** AC-2（`/u/$username/$noteSlug` が 410）の「対応ステップ」が `2, 5` となっているが、ステップ1（PoC）への紐づけが欠落している。
  - 理由: PoC（ステップ1）は `/notes/public/$noteId` 1ルートでのみ `setResponseStatus` の SSR 反映可否を実機検証する設計。だが AC-2 の対象は `$noteSlug` ルート（別ルート・別 server fn `renderPublicNote`）。PoC が成立するか否か（=本 Issue の成否を分ける唯一の不確実点）は AC-1/AC-2/AC-3 すべての前提条件であり、PoC が失敗すれば AC-2 も達成不能で「未解決事項へ退避」になる。受け入れ基準表は「どの基準がどの検証で担保されるか」を示すものなので、成否を握るステップ1が AC-2（および AC-3）の由来列・対応ステップに現れないのは紐づけの不整合。AC-1 のみ `1` が入っており、AC-2/AC-3 に入っていないのは「PoC は $noteId だけ通れば全ルートに一般化できる」という暗黙の前提を表記していないことに起因する。
  - 提案: (a) AC-2 / AC-3 の対応ステップにも `1` を加える（PoC の成立が全 AC の前提であることを表に反映）、または (b) plan の「実装ステップ」側に「ステップ1の PoC 結果は3ルートに一般化できる（同一の `renderServerComponent`/`setResponseStatus` 経路のため）」という前提を1行明記し、AC 表との関係を読み手が追えるようにする。どちらかで紐づけの一貫性を確保する。

## 改善提案（検討推奨）

- **[S-001]** AC-6 と plan ステップ4/5 で「PoC が成立しない場合は手動検証手順が存在する」と「フレームワーク待ちへ退避（ADR-001 D）」が併存しており、退避時の AC 達成状態が曖昧。
  - 理由: PoC（ステップ1）失敗時は本実装に進まず ADR-001 (D) に切り替えると明記されている。その場合 AC-1〜AC-5（HTTP ステータスの実現）は **達成されない**まま Issue がクローズまたは保留になる。AC-6 の「PoC が成立しない場合は手動検証手順」という but は、ステータス自体が出ないのに何を手動検証するのか読み取りにくい。退避が「計画として妥当」であることは認めるが、受け入れ基準としては「PoC 失敗時は本 Issue を未解決として記録し close せず据え置く（または別 Issue 化する）」という終端条件を AC（または「スコープ／未解決事項」節）に1行で固定しておくと、レビュアー・実装者間で完了判定がぶれない。
  - 提案: AC-6 を「PoC 成立時: 自動テスト＋curl 手動検証手順が存在」と「PoC 不成立時: ADR-001 (D) へ退避し未解決事項として `.issue/735` に記録、AC-1〜5 は持ち越し」の二分岐で明記する。

- **[S-002]** 「正常系 200 / `head`（meta・JSON-LD）が回帰しない」（AC-4）の検証が、curl のステータス行確認（ステップ5）に寄っており、`head` の回帰チェック手段が具体化されていない。
  - 理由: Issue の「正常系は 200 のまま」は満たすが、plan は AC-4 に「画面・`head`（meta/JSON-LD）が回帰しない」まで含めている。前段に `getPublicNote`/`getPublicProfile` 呼び出しを挿す変更は loader 経路に手を入れるため、`head`（別 server fn の meta loader）への直接影響は小さいとはいえ、AC-4 が「回帰しない」を謳う以上、検証方法を curl の本文/meta タグ目視まで踏み込むか、既存のメタ関連テスト（`head.test.ts` が実在）が緑であることを完了条件に含めると、基準が検証可能性を完全に満たす。
  - 提案: ステップ5の手動検証に「正常系レスポンスの `<title>`/OG/JSON-LD が従来通り出力されること（curl 本文 grep もしくは既存 `head.test.ts` 緑）」を1項追加。

- **[S-003]** 二重取得コスト（正常系で `getPublicNote`/`getPublicProfile` が前段＋本体で最大2回）について、plan は「許容範囲／メモ化が効けば回避」と評価しているが、これが受け入れ基準に表れていない。
  - 理由: スコープ整合性の観点では、これはスコープ外作業の混入ではなく**許容トレードオフ**として正しく整理されている（最適化はスコープ外と明記済みで妥当）。ただし「正常系で usecase が2回走り得る」のは観測可能な挙動変化であり、レビュー時に「これは意図か」が問われやすい。AC ではなく「リスクと注意点」に既に記載済みなので必須ではないが、ステップ1 PoC で正常系を curl する際に `getPublicNote` の実行回数（ログ等）を軽く観測しておくと、メモ化が効くか否かの実測（plan が「実測する」と書いた点）が PoC で同時に取れる。
  - 提案: ステップ1の PoC 検証項目に「正常系で前段＋本体の二重取得が起きるか（ログ等で1〜2回を確認）」を加え、後続の最適化要否判断の材料を PoC で同時取得する。

- **[S-004]** スコープ「含まれないもの」の認証系除外の根拠付けは妥当だが、Issue 本文「影響範囲」が認証系エラーページ（ADR-004 同根本）を明示的に挙げている点との整合をもう一段明記すると親切。
  - 理由: Issue「影響範囲」は「公開系エラーページ全般 / 認証系エラーページ（ADR-004 で同方式）も同根本」と書く。plan は認証系を明確にスコープ外とし「横展開は別 Issue 相当」とした。これは Issue タイトル・本文「あるべき動作」（公開系3ルートのみ列挙）と整合し、スコープ判断として妥当。問題ではないが、「Issue 影響範囲に認証系の言及があるが、本 Issue の『あるべき動作』は公開系3ルート限定のため認証系は対象外（別 Issue）」と1行明示しておくと、後続レビューで「影響範囲に書いてあるのに未対応では？」という指摘を未然に潰せる。
  - 提案: スコープ「含まれないもの」の認証系項に「Issue『影響範囲』で同根本として言及はあるが、『あるべき動作』は公開系3ルート限定」の一文を補う（ヘルパーを横展開可能に設計する方針は既述で良い）。

## 良い点

- **公開系3ルートのカバレッジが完全**。`$noteId`（byId）/ `$noteSlug`（bySlug、共通 `PublicNoteDetail`）/ `$username`（profile）すべてを修正対象に列挙し、AC-1/AC-2/AC-3 に1対1で割り当てている。共通コンポーネント `PublicNoteDetail` が2ルートから使われる事実を踏まえ「前段チェックはルートのハンドラ側に置くのでルート単位で独立に配線」と整理している点も正確（実コードと一致）。
- **PoC ファーストの設計が秀逸**。本 Issue の唯一かつ最大の不確実点（`setResponseStatus` の初回 SSR ドキュメントへの反映可否、Cloudflare ランタイム依存）をステップ1に隔離し、「通らなければ本実装に進まず ADR-001 (D) フレームワーク待ちへ退避」という撤退条件を明示。これは Issue「考えられるアプローチ」の案2（フレームワーク待ち）を正規のフォールバックとして計画に組み込んだもので、スコープ・リスク管理として妥当。
- **列挙耐性の維持が AC-5 と ADR-003 で明示的に固定**されている。ノート一律 410 / ユーザー一律 404、`getPublicNote`/`getPublicProfile` 無改変という #599 の不変条件を、ステータス経由でも破らないことを基準化している。Issue「やること」の列挙耐性要請に正対。
- **スコープ外作業の混入なし**。`HTTP_STATUS_BY_KIND` への 410 追加回避（notFound 全般への副作用回避）、ドメイン/usecase 無改変、コンポーネント #599 方式(d) 温存、最適化の見送り、SPA ナビゲーション除外、認証系除外——いずれも「やらない理由」付きで整理され、ADR-002/003 と整合。過剰実装の兆候は見当たらない。
- **既存パターンへの忠実さ**。meta loader（usecase 直接呼び＋`errorResponseMiddleware`）という確立済み前段分離パターンに乗せる方針で、`csrfMiddleware.test.ts` の `setResponseStatus` モックパターンをテストに流用。新規抽象を増やさず、実コードに存在する経路だけを使う（裏取り済み）。
