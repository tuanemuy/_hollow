# 動作確認計画 — Issue #735: 公開系エラーページのHTTPステータスが200のまま（RSC内notFoundで404/410を返せない）

**Issue:** #735
**作成日:** 2026-06-21

---

## 確認環境

このIssueの変更を確認するために必要な手順のみ記載（プロジェクト全体のセットアップは省略）。本Issueの本質は **HTTP レスポンスステータス**であり、画面だけでなく `curl -i` で実ステータス行を観測することが必須。

### 検証環境の起動

本Issueは「初回SSRドキュメントのHTTPステータス」を扱うため、**dev と 本番相当ランタイムの両方**で確認する（`setResponseStatus` のSSR反映可否がランタイム依存のため。plan.md PoCゲート / ADR-001/002 参照）。

- **dev（Vite + workerd）:**
  ```bash
  pnpm db:migrate    # ローカル D1 へマイグレーション適用（初回 / スキーマ変更時）
  pnpm dev           # http://localhost:3000
  ```
- **本番相当（wrangler dev、ビルド出力を実行 = Cloudflare Workers ランタイムに最も近い）:**
  ```bash
  pnpm build         # vite build（Cloudflare 向け）
  pnpm start         # wrangler dev → http://localhost:8787
  ```
  本番相当での確認が**必須ゲート**。dev で 410/404 が出ても本番相当で出なければ本方式は不成立（plan.md ステップ1/5）。

### シードデータの準備

確認には「実在する公開ノート」「実在ユーザー」と「存在しない／非公開」の対象が必要。

- 実在の公開ノート・実在ユーザー: ローカルでサインアップ → ノート作成 → 公開設定にして、その `noteId` / `username` / `noteSlug` を控える。
- 存在しないノート: 実在しない `noteId`（例: ランダムなULID/UUID）を URL に使う。
- 非公開ノート: 上記で作ったノートを非公開（下書き）状態にして使う。
- 存在しないユーザー: 実在しない `username` を URL に使う。

### デプロイ方法

なし（検証環境のみで確認できる。HTTPステータスはローカルの dev / 本番相当ランタイムで観測可能）。

## 確認項目

### 1. 存在しない／非公開ノートで HTTP 410（byId 経路）

- **対応する受け入れ基準:** AC-1, AC-5
- **目的:** `/notes/public/$noteId` で存在しない／非公開ノートへ初回SSRアクセスすると HTTP 410 を返すこと。
- **手順:**
  1. サーバを起動する（dev と本番相当の両方で実施）。
  2. `curl -i http://localhost:3000/notes/public/<存在しないnoteId>`（本番相当は `http://localhost:8787/...`）。
  3. 非公開ノートの `noteId` でも同じく `curl -i`。
- **期待結果:** ステータス行が `HTTP/1.1 410` 系。レスポンス本文に `ErrorPage kind="gone"` 相当（「このノートは公開されていません」等の文言）が含まれる。
- **確認ポイント:** ステータスが 200 でないこと。存在しないノートと非公開ノートで**同じ 410**（列挙耐性 / AC-5）。

### 2. 存在しない／非公開ノートで HTTP 410（bySlug 経路）

- **対応する受け入れ基準:** AC-2, AC-5
- **目的:** `/u/$username/$noteSlug` で存在しない／非公開ノートへアクセスすると HTTP 410 を返すこと。
- **手順:**
  1. `curl -i http://localhost:3000/u/<実在ユーザー>/<存在しないslug>`（本番相当も同様）。
  2. 非公開ノートの slug でも `curl -i`。
- **期待結果:** ステータス行が `HTTP/1.1 410` 系。本文に gone 相当の文言。
- **確認ポイント:** byId 経路（項目1）と一貫した 410。存在/非公開でステータス差なし。

### 3. 存在しないユーザーで HTTP 404

- **対応する受け入れ基準:** AC-3, AC-5
- **目的:** `/u/$username` で存在しない（または deleted/suspended）ユーザーへアクセスすると HTTP 404 を返すこと。
- **手順:**
  1. `curl -i http://localhost:3000/u/<存在しないusername>`（本番相当も同様）。
- **期待結果:** ステータス行が `HTTP/1.1 404` 系。本文に `ErrorPage kind="notFound"` 相当の文言。
- **確認ポイント:** ノート系の 410 とユーザー系の 404 が正しく出し分いていること。存在しないユーザーは一律 404（AC-5）。

### 4. 正常系は 200 のまま（回帰確認）

- **対応する受け入れ基準:** AC-4
- **目的:** 実在の公開ノート・実在ユーザーは HTTP 200 のまま、画面・`head`（meta/JSON-LD）が回帰しないこと。
- **手順:**
  1. `curl -i http://localhost:3000/notes/public/<実在の公開noteId>` → 200 を確認。
  2. `curl -i http://localhost:3000/u/<実在ユーザー>` → 200 を確認。
  3. `curl -s http://localhost:3000/u/<実在ユーザー>/<実在slug> | grep -i 'application/ld+json\|<meta'` で meta/JSON-LD が本文に含まれることを確認（または既存の head 関連テストが緑であること）。
  4. ブラウザで各正常系ページを開き、表示が崩れていないことを目視確認。
- **期待結果:** すべて 200。meta/JSON-LD が従来どおり出力される。画面に回帰なし。
- **確認ポイント:** 前段の存在チェック追加で正常系のレンダリングや head が壊れていないか。

### 5. 正常系での usecase 呼び出し回数の実測（二重取得の実態把握）

- **対応する受け入れ基準:** （参考。AC ではなく ADR-001 のトレードオフ確認）
- **目的:** 前段存在チェックにより、正常系で `getPublicNote` / `getPublicProfile` が何回走るかを把握する（二重取得は構造上必発の想定。read-only な単一行取得で許容範囲かを確認）。
- **手順:**
  1. 一時的に該当 usecase 呼び出し箇所にログ（`console.log` 等）を仕込むか、D1 クエリログ/カウンタで観測する。
  2. 正常系ページを1回 SSR で開き、呼び出し回数を数える。
  3. 確認後、仕込んだログは除去する（コミットに含めない）。
- **期待結果:** 1〜2回（前段チェック + RSC内本体取得）。2回でも read-only O(1) 取得で許容。
- **確認ポイント:** 想定外の回数（3回以上）になっていないか。

## エッジケース・異常系

### 1. NotFound 以外の例外は従来どおり 500（system）

- **目的:** 前段チェックが NotFoundError 以外の例外を握り潰さず、`errorResponseMiddleware` 経由で 500 + system 画面に倒れること（列挙耐性・既存挙動維持）。
- **手順:**
  1. （可能なら）DB を一時的に到達不能にする等で usecase が NotFound 以外のエラーを投げる状況を作り、公開系ルートへアクセスする。
  2. 困難なら、ユニットテスト（`new Error("boom")` を reject させ re-throw を検証）で代替する。
- **期待結果:** 410/404 ではなく 500 系。本文は system エラー画面。NotFound へ誤分類されない。

## 既存機能への影響確認

- **#599 で対応済みの画面表示（gone/notFound の ErrorPage）** が、前段チェック追加後も SPA クライアントナビゲーション・初回SSR の両方で従来どおり出ること。
- **公開系の正常系ページ全般**（一覧・タグ・バックリンク・関連ノート）が回帰しないこと（項目4の延長で目視）。
- **認証系エラーページ**（`_app/...`）は本Issueのスコープ外。挙動が変わっていないこと（変更を加えていないので原則影響なしだが念のため確認）。
