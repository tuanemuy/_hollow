## コードとの照合（plan の前提が実態と合っているか）

要件カバレッジの妥当性は「plan が前提とする既存実装の挙動」が正しいことに依存するため、主要な前提を実コードで検証した。すべて plan の記述どおりだった。

- `EditorMode` 型に `"wysiwyg"` が既に存在し、`setMode` は任意モードを受け付ける（editorState.ts L48, L450-453）→ plan「レンダリング側は追加実装ほぼ不要」は正しい。
- `NoteEditor.tsx` の `state.mode === "wysiwyg"` 分岐（L408-428）は surface 非依存で、`mode="edit"` でも `state.mode` が `wysiwyg` になればペインがレンダリングされる → AC-1 の実現性は確認済み。
- `EditorModeSwitch` の `TABS_EDIT`（L38-42）に `wysiwyg` が無く、`surface === "new"` 分岐（L49）は独立 → タブ追加が AC-6 を壊さない、は正しい。
- `detectUnsupportedTags()` は SSR/Worker でも動く純関数で `<section>` 等を非対応として返す（wysiwygUnsupportedTags.ts）→ 切り替え前判定への再利用（AC-2/3/5）は妥当。
- `ConfirmDialog` は `subject` 未指定なら「削除対象」ラベルが出ず、confirm ボタンは danger 固定（ConfirmDialog.tsx L128-154, L174-182）→ ADR-001 の前提どおり。
- `ConfirmDialog` 内 `<form>` は submit を `stopPropagation`（L105-115）→ 外側フォーム誤送信回避の前提どおり。AC-8 / リスク欄の主張を裏付ける。
- 自動保存ゲート `shouldFlushAutosave` は WYSIWYG かつ未承認時のみ停止、HTML モードは非ゲート（useAutosave.ts L143-149）→ ADR-002 の「二重同意回避」「HTML は止めない」記述と一致。
- `wysiwygUnsupportedDetected` は latch（空配列 no-op、同一集合は ack 維持。editorState.ts L547-564）→ ADR-002 の「`wysiwygUnsupportedAck` 先行発行が `onCreate` 再検出で消えない」主張は正しい。
- `spec/pages/index.md` P12 に「WYSIWYG モード（新規 + 既存）」と明記（L158）→ plan「仕様が元々想定していた姿」「機能の解禁」は正しく、本変更は仕様準拠方向。スコープ拡大ではない。

#### 問題点（要修正）

問題点ゼロ。

Issue 本文の合意要件はすべて検証可能な AC に落ちており、各 AC は実装ステップに紐づき、plan が前提とする既存挙動はコードと一致し、スコープ外作業の混入も確認できなかった。要件カバレッジ・スコープ整合性の観点で要修正の指摘は無い。

#### 改善提案（検討推奨）

- **[S-001]** AC-7 の検証可能性をもう一段具体化する余地がある。
  - 理由: AC-7 は「未保存確認と装飾消失警告が二重ダイアログにならず、どちらの同意も尊重される」と書かれているが、「二重ダイアログにならない」は字面どおりだと『同時に 2 つ出ない』とも『連続して 2 つ出ない』とも読める。一方で ADR-002 の Decision／Consequences は「未保存(`window.confirm`) → 装飾(`ConfirmDialog`) が**連続で出る**（2 ダイアログ）。ただし関心が別なので二重『装飾』同意ではない」と明示しており、AC-7 の表現と ADR-002 の意図にニュアンスの差がある。テスト方針には「`window.confirm` の後に `ConfirmDialog` が出る順序・二重にならないこと」とあり ADR 側の意図が正。AC-7 の文言を「未保存 + 非対応タグの両方がある場合、`window.confirm`（未保存）→ `ConfirmDialog`（装飾）の順で発火し、装飾喪失について**二重に同意を求めない**（`wysiwygUnsupportedAck` 併発でペイン内バナーが再同意を要求しない）」のように、ADR-002 の確定事項に揃えて書き直すと、基準・ADR・テストの三者が一字一句整合する。要件カバレッジ自体に欠落は無いため修正ではなく改善提案。

- **[S-002]** AC-8 の「齟齬が出ない」の合格条件を観測可能な形に言い換える余地がある。
  - 理由: AC-8 は Issue 本文「実装方針（案）」由来で、検討タスクとしては妥当だが「齟齬が出ない」という否定形は単独では合否判定の基準が曖昧。plan の設計4-5・テスト方針には「WYSIWYG 切替は `setMode` のみで `contentHtml` を書き換えない」「既存 in-flight cancel テストと整合」という具体が既にあるので、AC 表のセルに「WYSIWYG への切り替え自体は `contentHtml` を変更せず、既存の in-flight saveDraft cancel テストが green のまま」程度の観測条件を添えると、検証可能性が AC レベルで完結する。これも内容の欠落ではなく表現の精緻化。

- **[S-003]**（情報提供）AC-5「失われる要素が一覧で確認できる」の検証はダイアログ本文の文言に依存する。plan の設計4では `description` に `<code><${tag}></code>` リストを描画するとあり、テスト方針でも `<section>` 表示を assert する。要件としては満たされているが、ラベル文言（「次の要素は WYSIWYG モードでは保持されません」）は ADR/テストでハードコード文字列に依存するため、実装時にテストの期待文字列と本文を一致させること。指摘というより実装時の注意点。

#### 良い点

- **要件トレーサビリティが明示的**: 受け入れ基準表が「由来（Issue 本文の該当箇所）」列と「対応ステップ」列を持ち、各 AC が Issue のどの合意点から来てどのステップで実装されるかが一覧化されている。要件カバレッジのレビューが表だけで完結できる構成。
- **受け入れ条件6項目の完全カバー＋検討点の AC 化**: Issue の明示的な受け入れ条件だけでなく、「実装方針（案）」に書かれた検討タスク（二重ダイアログ・自動保存整合）まで AC-7/AC-8 として基準化しており、レビュー段階で「検討で終わっていないか」を追える。
- **スコープ境界が明確で、非スコープが Issue の意図と一致**: 「含まれないもの」節で『非対応タグの保持（TipTap スキーマ拡張）』『編集画面の初期モード変更』『新規作成画面の挙動変更』『既存バナーの撤去・再設計』を明確に除外。これは Issue 本文の「本 Issue は『失う前に同意を得る』ことが目的であり、装飾の保全は対象外」という意図と完全に一致しており、スコープ膨張の混入は無い。
- **仕様（spec P12）への参照で「機能解禁」と位置づけている**: `spec/pages/index.md` P12「WYSIWYG モード（新規 + 既存）」を引き、本変更が仕様逸脱ではなく暫定状態（Issue #233 ADR-001 で new 専用化）の解消であることを根拠づけている。これによりスコープ整合性の判断材料が plan 内で自己完結。
- **既存テストへの影響を事前に特定**: `noteEditorModeChange.test.tsx` が `tabByLabel("HTML")` 経由で confirm 条件を pin している事実を調査済みで、WYSIWYG タブ追加・ダイアログ導入が既存テストを壊さないか確認するステップ4が用意されている。実際にコードを確認した限り、HTML タブ経路にはダイアログを挟まないため既存ケースは壊れない見込みで、plan の見立ては妥当。
