## 確認項目

### 1. アップロードモーダルの failed view に「再試行」が表示され、押すと再ポーリングに戻る

- **目的:** B1 異常系の owner 向け再試行が、アップロードモーダル内で動くこと。
- **手順:**
  1. ログインしてアップロードダイアログを開く
  2. LLM 構造化が失敗するファイル（例: 内容が空に近い／LLM がエラーを返す状況を再現できるファイル。再現が難しい場合は確認項目 5 の手動 failed 化を使う）を 1 件アップロードする
  3. モーダル内が failed view に切り替わることを確認
  4. failed view に「再試行」「キュー画面で詳細を見る」「破棄」の 3 アクションが並ぶことを確認
  5. 「再試行」を押す
- **期待結果:** waiting view（推論待ちスケルトン）に戻り、`getIngestionJobFn` のポーリングが再開する。LLM が成功すれば editing view（プレビュー編集）へ遷移する。
- **確認ポイント:** 再試行押下後に DevTools Network で `ownerRetryIngestionJobFn` が 1 回だけ発火し、その後 getJob ポーリングが再開すること。pending 中はボタンが disable され多重発火しないこと。

### 2. キュー画面（P13）の failed カードに「再試行」動線がある

- **目的:** 複数ファイル経路（キュー画面）からも owner retry できること。
- **手順:**
  1. failed 状態のジョブが 1 件以上ある状態でキュー画面を開く
  2. failed カードに「再試行」ボタン（破棄の前）が表示されることを確認
  3. 「再試行」を押す
- **期待結果:** カードの状態が待機中（pending）に戻り、ルーターの invalidate でカード表示が更新される。バックグラウンドで再処理され、成功すればプレビュー可能（previewing）に遷移する。
- **確認ポイント:** retry 押下中は同カードの破棄/再試行ボタンが disable されること。

### 3. 再試行後にノート登録まで通しで完了できる

- **目的:** retry → previewing → 登録の一連が破綻しないこと。
- **手順:**
  1. 確認項目 1 で failed → 再試行 → editing に到達する
  2. タイトル等を確認して「登録」を押す
- **期待結果:** モーダルが閉じてノート詳細画面に遷移する。
- **確認ポイント:** retry 経由でも通常アップロードと同じ commit フローが効くこと。

## エッジケース・異常系

### 1. 他ユーザーの failed ジョブは再試行できない（403）

- **目的:** owner 認可が効き、他人のジョブを retry できないこと。
- **手順:**
  1. ユーザー A で failed ジョブを作る
  2. ユーザー B でログインし、（URL 直叩き等で）A のジョブに対して retry を試みる
- **期待結果:** ForbiddenError（403 相当）になり、ユーザー向けエラー表示が出る。ジョブの状態は変化しない。

### 2. temp storage を失った failed ジョブの再試行

- **目的:** 再試行に必要な元データが無いときの文言表示。
- **手順:**
  1. temp storage key が無い failed ジョブ（discard 済みデータなど）に対して再試行を試みる
- **期待結果:** 「再試行に必要なデータが見つかりません。再度アップロードしてください」というユーザー向け文言がインライン表示される（内部の `ingestion_no_temp_storage_for_retry` は露出しない）。

## 既存機能への影響確認

- **admin Jobs 画面の retry**: P46 admin dashboard の retry（`retryIngestionJobFn`）が従来どおり動作すること（本 Issue では admin retry usecase を変更しないが、リグレッション確認）。
- **再生成（regenerate）**: editing view の「再生成」がこれまで通り動くこと（FailedView への onRetried 配線追加で `onRegenerated` 経路に副作用が出ていないこと）。
