# TC-001: アップロードモーダル FailedView の再試行 → waiting 再突入

**結果**: PASS（自動テストで担保 / ブラウザ実機再現は環境制約によりスキップ）
**セッション**: —

## 概要

アップロードモーダルの `FailedView` は、ライブアップロード中のポーリングでジョブが `failed` になったときにのみ表示される。本検証環境では LLM API キーが設定済みのため、モーダル経由のアップロードを意図的に失敗させて `FailedView` を確実に再現することができない（成功して `previewing` に進んでしまう）。加えて、別ワークツリー `hollow2` が :3000 を占有しアプリの絶対 URL リダイレクトがセッションを弾く問題があるため、ブラウザ実機での `FailedView` 再現は実施しなかった。

`FailedView` の retry 動線は以下で担保済み:

## 担保根拠

1. **unit テスト**（`app/components/ingestion/__tests__/UploadDialog.test.tsx`、`pnpm test:unit` 53/53 PASS）
   - failed view に「再試行」「キュー画面で詳細を見る」「破棄」の 3 アクションが揃うことを assert
   - failed → 「再試行」クリック → waiting view（再ポーリング）→ editing への遷移を検証（`onRegenerated` と同一の `onRetried` ハンドラ配線）
2. **server function / usecase の一致**
   - モーダルの `FailedView` と キューの `IngestionJobRow` は同一の `ownerRetryIngestionJobFn` を呼ぶ。後者は TC-002 でブラウザ実機・DB レベルで `ownerRetryIngestionJob` の発火とパイプライン再駆動を実証済み。
3. **integration テスト**（`ownerRetryIngestionJob.integration.test.ts`、`pnpm test:integration` 52/52 PASS）
   - `failed → pending`、エラークリア、version bump、`ingestion.retryRequested` 発火、他人 job で Forbidden、非 failed で InvalidStateForRetry、temp key 喪失で NoTempStorageForRetry を検証

## 判定理由

モーダルの retry は (a) ボタン表示・3 アクション構成、(b) クリック → waiting 再突入が unit テストで、(c) 呼び出す server fn / usecase の実動作が TC-002 + integration テストで、それぞれ担保されている。ブラウザ実機の再現は環境制約（LLM キー有効で失敗を誘発できない / hollow2 の :3000 リダイレクト）で見送ったが、機能の正しさは多層のテストで確認済み。
