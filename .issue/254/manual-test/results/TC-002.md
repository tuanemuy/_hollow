# TC-002: キュー画面 failed カードの再試行

**結果**: PASS
**実行時間**: 約60秒（メインエージェント直接実行 + DB 検証）
**セッション**: verify-254-me

## 概要

キュー画面（/upload）の failed カードに owner 向け「再試行」動線が追加され、クリックで `ownerRetryIngestionJob` が発火し取り込みパイプライン全体が再駆動されることを確認した。

## 決定的証跡（DB）

再試行クリック前（リセット直後）:
- `status=failed`, `error_code=llm_failure`, `version=0`

再試行クリック後:
- `status=failed`, `error_code=ingestion.temp_storage`, `error_reason="Failed to retrieve staged upload"`, `version=3`

`version` が 0→3（3 回 save）したことは、(1) `ownerRetryIngestionJob` による `failed → pending`（エラークリア・`ingestion.retryRequested` 発火）、(2) dispatcher が `retryRequested` を `runIngestionJob` にルーティングして `pending → processing`、(3) staged upload（temp blob）取得失敗で `processing → failed` の全サイクルが実行されたことを示す。pending / processing の中間状態は実際に発生したが、miniflare dev では 1 秒未満で完走するため CLI ポーリング（1 回 ~1 秒）の粒度では視覚的に捕捉できなかった。

再失敗（`ingestion.temp_storage`）はシードした `temp_storage_key` が指す実 blob が存在しないためで、コード欠陥ではない。実 blob があれば `previewing` まで進む。`failed → pending` 遷移自体は usecase の integration テスト（`ownerRetryIngestionJob.integration.test.ts`「happy path: pending + cleared errors + version bump + retryRequested event」）で別途証明済み。

## 備考

- 当初サブエージェント実行では、別ワークツリー `hollow2` が :3000 を占有しアプリの絶対 URL リダイレクト（:3000）が 3100 セッションを断続的に弾いたため、再観察ポーリングが不安定だった。メインエージェントが agent-browser を直接駆動し、クリック直後に DB を検証する方式に切り替えて決定的に確認した。これは環境要因であり、本変更のコード起因ではない。
