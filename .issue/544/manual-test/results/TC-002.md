# TC-002: ロックアウト警告の .alert 案D

**結果**: FAIL（実装バグによりロックアウト状態に到達できない / UI 設計自体は案Dで正しい）

## 実行ログ

| 手順 | 操作 | 結果 |
| --- | --- | --- |
| 1 | `/share/test-share-passworded-0001` で誤パスワードを合計6回送信（Edge-1 の1回 + 追加5回） | 各回 `wait --load networkidle` 後、毎回インライン「パスワードが正しくありません。」のまま。ロックアウト警告に切り替わらない |
| 2 | 追加でもう1回（計7回相当）誤送信 | 同上。`role="status"` の案Dアラートは出ない |
| 3 | DB 直接確認（miniflare D1 sqlite） | `failed_attempts=0`, `locked_until=NULL`, `version=0`, `updated_at` 初期値のまま（複数回の誤送信が一切永続化されていない） |
| 4 | 対照確認: 正パスワード `test1234` を送信 | `/notes/public/01950000-0000-7000-8000-000000000020` へ遷移（=送信は確実にサーバへ到達し、成功パスはコミットされる） |

## 根本原因（実装バグ）

ロックアウトのしきい値計算・UI（案D）自体は正しいが、**失敗回数がDBに永続化されない**ため lockout に永遠に到達しない。

- `app/core/application/publication/resolveShareLink.ts`: パスワード不一致時、`shareLinkRepository.save(result.updatedLink, ...)`（failed_attempts インクリメント）を **pending batch に積んだ直後に** `throw new BusinessRuleError("share_link_password_invalid", ...)` する。
- `app/core/adapters/d1/unitOfWork.ts`（`D1UnitOfWorkProvider.run`）は遅延バッチ方式: `await fn(ctx)`（L206）が正常終了して初めて `db.batch(pending.build())`（L218）を実行する。`fn` が throw すると **バッチ flush に到達せず、積んだ書き込みは破棄される**。
- 結果、不一致のたびに increment はロールバックされ、`failed_attempts` は 0 のまま。`recordFailedAttempt`（entity.ts）の `nextAttempts >= maxAttempts` で `locked_until` を立てる仕組みも発火しない。

これは agent-browser の偽陽性ではない。送信はサーバへ到達しており（revoked エラー / password_invalid エラー / 正パスワードでの遷移をいずれも観測）、失敗パスのみ永続化されていないことをDBで直接確認した。

## UI 設計（案D）の確認（コード読解）

ロックアウト警告のマークアップ自体は仕様どおり実装されている（到達不能なだけ）。

- `app/components/public/ShareLinkGate/index.tsx` L132-141: `isLocked`（`share_link_locked`）時に `<div className={ALERT + ALERT_WARNING} role="status">` + `AlertTriangle` アイコン + 本文。
- `role` は **`status`**（`alert` ではない）— 仕様どおり。
- `ALERT`（styles.ts L282）= `bg-bg shadow-xs border border-[color-mix(... var(--alert-accent) 30% ...)]` + `ALERT_WARNING` で accent=warning。すなわち **白地 + 警告色のヘアライン枠 + shadow**。**塗りつぶし背景ではない**。
- 本文 `gateErrorMessage`（L201-203）= 「試行回数の上限に達しました。しばらく時間をおいて再度お試しください。」— 「あと N 分」のような固定値は含まれない。

## 判定

- ロックアウト到達: **不可（FAIL）** — 失敗カウンタ非永続化のバグ。
- 案Dの見た目・role・文言: コード上は **正しい**（白地+枠、role=status、固定値なし）。ただしブラウザ実機では観測できなかった。

## ブロッカー / 推奨対応

- `resolveShareLink` の失敗パスは、increment を永続化してから別経路でエラー応答する必要がある（例: UoW を成功終了させて結果に失敗を載せ、呼び出し側でエラー化する／失敗カウンタ更新を別UoWで先にコミットする 等）。現状は「save→throw 同一UoW」のため遅延バッチが捨てられる。
