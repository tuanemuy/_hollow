# 動作確認計画 — Issue #321: 内部リンクの後追い再解決

**Issue:** #321
**作成日:** 2026-05-29

---

## 確認環境

このIssueの変更を確認するために必要な手順のみ記載。

### 検証環境の起動

```bash
pnpm dev
```

ローカル開発サーバー（vite + Cloudflare Workers / workerd）が `http://localhost:3000` で起動する。

**重要（イベント駆動の前提）**: 本Issueの再解決はドメインイベント（`note.created` / `note.content_updated` / `note.renamed` / `note.trashed` / `note.restored`）を consumer が処理して実現する。`pnpm dev` では `InlineRelayTrigger`（`docs/runtime_cloudflare.md` 「Local dev outbox dispatch」）が、UoW commit ごとに同一 isolate 内で `processOutboxEvents` → `dispatchDomainEvent` を `waitUntil` で実行するため、**ノートの保存・改名・trash・restore 操作の直後にほぼゼロ遅延で再解決が走る**。`pnpm start`（`wrangler dev`）ではインライン経路が無効でイベントが処理されないため、動作確認は **`pnpm dev` を使うこと**。

ローカル D1 への SQL は別ターミナルから次の形で実行する（DB 名は `wrangler.toml` の binding 名 `hollow-local-d1`）:

```bash
wrangler d1 execute hollow-local-d1 --local --command "<SQL>"
```

DB が未セットアップの場合のみ、マイグレーション適用が必要（本Issueはスキーマ変更を含まないため新規マイグレーションは無い）:

```bash
pnpm db:migrate
```

### デプロイ方法

検証環境のみで確認可能。ステージング・本番へのデプロイは不要。

## 確認項目

### 1. 作成時バックフィル（未解決 title リンクがリンク先作成で解決される）

- **目的:** リンク先ノートが後から作成されたとき、既存の未解決 `[[タイトル]]` リンクの `resolved_note_id` がバックフィル解決されることを確認する。
- **手順:**
  1. `pnpm dev` 起動 → サインアップ / ログイン
  2. ノート B を作成し、本文に `[[未来のノート]]`（まだ存在しないタイトル）を入力して保存
  3. SQL で未解決を確認:
     ```bash
     wrangler d1 execute hollow-local-d1 --local --command "SELECT ref_kind, ref_target, resolved_note_id FROM note_internal_links WHERE ref_target = '未来のノート'"
     ```
     → `resolved_note_id IS NULL`（broken link）であること
  4. ノート A を **タイトル `未来のノート`** で新規作成して保存
  5. 同じ SQL を再実行
- **期待結果:** ノート B のリンク行の `resolved_note_id` が、作成したノート A の id（NOT NULL）に更新されている。
- **確認ポイント:** B を再保存していないのに、A の作成だけで B のリンクが解決されること。

### 2. バックリンクが作成後に出現する

- **目的:** 作成時バックフィルが backlink 表示（`findReferrers`）に反映されることを確認する。
- **手順:**
  1. 確認項目1の続きで、ノート A（`未来のノート`）を画面で開く
  2. バックリンク表示領域を確認する
- **期待結果:** A のバックリンクとして、`[[未来のノート]]` を含むノート B が表示される。
- **確認ポイント:** A 作成前は backlink 空、作成後に B が出現すること。

### 3. 改名時の解除＋再解決（エディタ保存でのタイトル変更経路）

- **目的:** リンク先ノートのタイトルを変えると、旧タイトルで解決していたリンクが解除され、新タイトルに一致する未解決リンクが解決されることを確認する。**エディタ保存（`note.content_updated`）でタイトルを変える経路**を対象とする。
- **手順:**
  1. ノート A（タイトル `旧タイトル`）と、本文に `[[旧タイトル]]` を持つノート B を用意（B のリンクが A に解決済みであることを SQL で確認）
  2. 本文に `[[新タイトル]]` を持つノート C を用意（C のリンクは未解決のはず）
  3. ノート A をエディタで開き、**タイトルを `新タイトル` に変更して保存**
  4. SQL で確認:
     ```bash
     wrangler d1 execute hollow-local-d1 --local --command "SELECT ref_target, resolved_note_id FROM note_internal_links WHERE ref_target IN ('旧タイトル','新タイトル')"
     ```
- **期待結果:** `旧タイトル` のリンク行（B）は `resolved_note_id` が NULL に解除され、`新タイトル` のリンク行（C）は A の id に解決される。
- **確認ポイント:** payload に旧タイトルが無くても、現タイトル不一致判定で旧リンクが解除されること。専用リネーム UI がある場合はそちらでも同様に確認する。

### 4. trash で解除、restore で再解決

- **目的:** ノートを trash（ゴミ箱へ）すると当該ノートを指すリンクが解除され、restore（復元）すると再解決されることを確認する。
- **手順:**
  1. ノート A と、A に解決済みの `[[Aのタイトル]]` を持つノート B を用意（SQL で resolved を確認）
  2. ノート A をゴミ箱に入れる（trash）
  3. SQL で B のリンク行を確認 → `resolved_note_id IS NULL` になっていること
  4. ノート A を復元（restore）する
  5. SQL で B のリンク行を再確認 → 再び A の id に解決されていること
- **期待結果:** trash で NULL、restore で NOT NULL（A の id）。
- **確認ポイント:** trash は論理削除で FK の set null が作動しないため、明示解除が効いていること。restore で id/title 両方が復活すること。

## エッジケース・異常系

### 1. 同名タイトル複数時の決定規則

- **目的:** 同名タイトルのノートが複数あるとき、`[[同名]]` リンクが決定規則（title asc, id asc 先頭）の1件に解決されることを確認する（#127 ADR-003 との整合）。
- **手順:**
  1. タイトル `重複` のノートを2つ（A1, A2）作成
  2. 本文に `[[重複]]` を持つノート B を保存
  3. SQL で `resolved_note_id` を確認し、どちらに解決されたか控える
  4. 解決先になっているノートを trash → B のリンクがもう片方に再解決されるか確認
- **期待結果:** 常に決定規則に従った1件に解決され、解決先を trash すると残った同名ノートに再選択される。

### 2. 自己参照は解決しない

- **目的:** ノート A が本文に `[[Aのタイトル]]` を書いても、自分自身には解決しないこと（#127 ADR-005）。
- **手順:**
  1. ノート A の本文に `[[Aのタイトル]]`（A 自身のタイトル）を入力して保存
  2. その後 A をエディタで再保存（content_updated 発火）
  3. SQL で A の from 行の `resolved_note_id` を確認
- **期待結果:** A 自身を指す解決にはならない（self は除外）。

### 3. 本文のみ編集（タイトル不変）は解決状態を壊さない

- **目的:** タイトルを変えずに本文だけ編集して保存しても、既に解決済みのリンクが誤って解除されないことを確認する。
- **手順:**
  1. 解決済みリンクを持つ状態を用意
  2. リンク先ノートのタイトルは変えず、本文だけ編集して保存（`note.content_updated` 発火）
  3. SQL で解決状態を確認
- **期待結果:** 解決済みリンクの `resolved_note_id` は変化しない（解除/解決クエリとも空集合 no-op）。

## 既存機能への影響確認

- **保存時点の解決（#127）**: リンク先が既に存在する状態で `[[タイトル]]` を保存したとき、従来どおり保存時点で解決されること（後追い再解決は既存挙動を壊さない）。
- **内部リンクサジェスト（`[[` 補完）**: 候補選択で `[[タイトル]]` が挿入される従来の挙動が維持されていること。
- **purge（完全削除）**: ノートを完全削除したとき、from 行は消え、当該ノートを指す resolved 行は FK の set null で NULL になること（handler 追加なしで従来どおり動くこと）。
- **検索インデックス更新**: 同一イベント（created/content_updated/renamed/restored）で走る search 再インデックスが、再解決 handler 追加後も従来どおり動くこと。
