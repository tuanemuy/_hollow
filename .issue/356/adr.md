# ADR — Issue #356: P11 ノート詳細: メタ情報パネルのレイアウト再構成

## ADR-001: 公開状態の置き場所

### Status
Proposed

### Context
Issue は「公開状態をメタ情報から独立させ、公開設定への導線をその場に含める」ことを求めている。P14（公開設定）はモーダルではなくページ route `/notes/$noteId/publish` で、既に `NoteActions.tsx` が `<Link to="/notes/$noteId/publish">公開設定</Link>` の導線を持つ。選択肢: (A) `NoteDetail` 上部に独立した `<PublishStatus>` コンポーネントを新設、(B) 既存の `NoteActions` 内「公開設定」リンクに状態チップを内包。

### Decision
(B) を採用。既存の P14 導線が `NoteActions` にあるため、公開状態表示と導線を同一要素に統合するのが導線整合の観点で最も自然で、表示と遷移の重複を生まない。新規モーダルやコンポーネントの発明を避ける（既存パターン再利用）。

### Consequences
- 良い点: 公開状態とその設定導線が1箇所に集約され、ユーザーの認知負荷が低い。新規コンポーネント数が増えない。
- トレードオフ: `NoteActions`（`"use client"`）の責務がやや増える。ただし状態は props 由来でクライアント状態追加は不要。

## ADR-002: パンくずのリンク粒度

### Status
Proposed

### Context
参考デザインは各ディレクトリセグメントをリンクにしている。しかし DTO の `directoryPath` は `/Research/論文メモ` のような **単一文字列**で、中間セグメントの `directoryId` を持たない。アプリ層に触れない原則のもとで、どこまでリンク化するかを決める必要がある。

### Decision
中間セグメントは非リンクのテキスト表示に留める。`note.directoryId` は `NoteDTO.directoryId`（branded `DirectoryId`、**常に非null**）で、全ノートは必ずディレクトリ（ルート直下ならルートディレクトリ）に属する。リンク化の出し分けは `directoryId` の null 判定ではなく **`directoryPath` のセグメント有無**で行う:
- セグメントが1つ以上ある（非ルート）場合のみ、葉セグメントを `<Link to="/" search={{ ...HOME_SEARCH, directoryId }}>` でホーム絞り込みリンク化
- `directoryPath === "/"`（ルート直下、セグメント空）の場合は葉リンクを出さない。ルートディレクトリ id を `directoryId` フィルタに渡すと一覧の挙動が未検証になるため、リンク自体を抑止する

中間セグメントのリンク化は `getNoteDetail` の DTO 拡張（`{id,name}[]` を返す）が必要で、アプリ層に踏み込むため本Issueのスコープ外（別Issue化）。

### Consequences
- 良い点: アプリ層不可侵を守りつつ「ディレクトリをパンくず化」要件を満たす。非ルートノートの葉へのナビゲーションは可能。型上も `DirectoryId` 非null前提で到達不能な null 分岐を作らない。
- トレードオフ: 中間ディレクトリへ直接飛べない。ルート直下ノートは葉リンクが出ない。Issue補足の「あるべき姿」には一歩届かないが、Issue範囲内での妥当な妥協点。フォローアップIssueで解消可能。

## ADR-003: 下部プロパティでの公開状態の非再掲

### Status
Proposed

### Context
公開状態を上部（`NoteActions`）に独立表示する。参考デザインの下部 `mobile-meta` / 右 `meta-rail` には公開状態も含まれており、下部プロパティに公開状態を再掲するか判断が必要。

### Decision
下部プロパティには公開状態を再掲しない。上部に独立表示する以上、下部での重複は情報の冗長になり「重要度に応じた配置」という Issue の意図に反する。下部は作成日 / 更新日 / タグ / バックリンクに絞る。

### Consequences
- 良い点: 公開状態の表示が1箇所に定まり、状態色・ラベルの単一情報源になる。
- トレードオフ: 参考デザインと厳密には一致しないが、Issue の情報設計意図（重要情報は上部・補助情報は下部）に忠実。

### 補足: 公開「状態」と公開「日」の区別
下部プロパティに再掲しないのは公開**状態チップ**（公開/限定公開/非公開のラベル + 状態色）のみ。`publishedAt`（公開**日**）は状態色を持たない単なる日付メタであり、作成日 / 更新日と同列の補助情報として下部プロパティに「公開日」行で残す。状態の単一情報源（上部チップ）と、日付メタ（下部）は役割が異なるため重複には当たらない。

## ADR-004: バックリンクの段階表示（件数の上部表示）の不採用

### Status
Proposed

### Context
Issue補足に「バックリンクは件数のみ上部・詳細は下部、など段階表示も検討可」とある（任意項目）。上部に件数だけ出し下部に一覧を置く段階表示を採るか判断が必要。

### Decision
採用しない。バックリンク（件数・一覧とも）は本文下部に集約する。Issue の本筋は「本文上部の占有を解消し、上部を最小限に保つ」ことであり、上部に件数を再掲すると上部要素が増えて意図に逆行する。

### Consequences
- 良い点: 上部がパンくず・タイトル・公開状態・アクションのみに保たれ、本文への視線を妨げない。
- トレードオフ: バックリンクの存在に上部で気づけない。ただし任意項目であり、下部集約で要件は満たす。
