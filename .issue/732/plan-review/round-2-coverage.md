## Round 1 指摘の解消確認

- **[P-001]（AC-4 が検証可能な「回数」基準として弱い）→ 解消**
  AC-4 が (a) `useAuthGuardEffect` の `useEffect` 発火条件・依存配列が変更前後で等価（不整合時のみ `appShellInvalidate` 1 回 / fresh・認証済みで 0 回）であることをユニットでピン留め、(b) 実 RPC 回数（初回 1・以降 0）と `staleTime: Infinity` 維持を手動ブラウザ検証（DevTools Network）で担保、の 2 分割に明文化された（plan AC 表 AC-4 / テスト方針 / レビュー履歴）。「invalidate 呼び出し回数」と「RPC 回数」が別事象である点も「純ユニットでは RPC 回数を直接数えにくいため invalidate 発火回数で代替担保」と明記され、提案どおりの是正。

- **[P-002]（AC-2 の自動検証欠落 = 最重要リスクが手動のみ）→ 解消**
  実装ステップ 5 が追加され、「不整合フラグ → 描画選択」マッピング（`true`→`null` / `false`→`LandingPage`）を純関数（`selectUnauthenticatedView`）に切り出してユニットでピン留めする方針が明記された。純関数化が困難な場合は手動テスト主担当に倒すフォールバックも明示。AC-2 表に検証手段①hook 戻り値ユニット ②分岐マッピングユニット ③手動の三段で紐づけられ、提案を満たす。

- **[S-001]（AC-5 の検証手段の所在を明確化）→ 解消**
  AC-5 表に「非同期収束であり手動テストが主担当」と明記され、加えてステップ 6 で `shellUserDto` user→null 再 render による hook 戻り値 `true→false` 遷移をユニットでピン留めし手動依存を低減。検証手段の所在が一意になった。

- **[S-002]（再受容 (D) への撤退条件）→ 解消**
  ADR-001 に「撤退条件（(D) 現状トレードオフ再受容へのフォールバック）」節が追加され、収束しない／レイアウトシフトが `null` 維持で解消できない場合に (D) へ退避し ADR Status を更新する基準が明記された。Issue 本文の二択（ゼロフレーム化 **または** 明示的再受容）の両方が基準化された。

Round 1 の P-001 / P-002 / S-001 / S-002 はすべて適切に反映済み。

#### 問題点（要修正）

問題点ゼロ。

#### 改善提案（検討推奨）

- **[S-001]** ステップ 5 の純関数 `selectUnauthenticatedView` が「困難なら見送り、AC-2 は手動主担当に倒す」と条件付きである点
  - 理由: AC-2 は plan 自身が「最重要リスク」と位置づけた要件であり、その自動検証可否が実装段階の判断（純関数化の難易度）に委ねられている。`selectUnauthenticatedView(isResolvingAuthMismatch): "placeholder" | "landing"` のような **引数 1 個・戻り値が描画選択 enum/識別子の純関数** は、`HomeRoute` 本体（server component / loader 依存）から切り離せば技術的にほぼ常に切り出せる（描画選択は `boolean → 識別子` の純写像で server component の都合と独立）。「困難なら見送り」を残すより、ステップ 5 を「原則として純関数化して自動ピン留めする（見送りは例外）」というトーンに固定したほうが、最重要リスクの自動担保が実装者の裁量で抜けにくい。要件カバレッジ上の欠落ではなく、自動検証の確実性を一段上げる提案。

#### 良い点

- Round 1 の 4 指摘（P-001 / P-002 / S-001 / S-002）をすべて取り込み、見送りゼロ。各是正が AC 表・実装ステップ・ADR・テスト方針に多重に反映されており、追跡可能性が高い。
- AC-4 の「invalidate 発火回数 ≠ RPC 回数」という Round 1 で指摘した概念上の混同を、検証手段を (a) ユニット代替担保 /(b) 手動 RPC 実測に分けることで正確に解きほぐしている。
- AC-5 の収束を「`appShellInvalidate` は `_app` のみ invalidate → leaf loader（`renderHome`）非再走 → `data.authenticated=false` 維持 → shell null 化 → フラグ `false` → `LandingPage`」という依存連鎖（設計「収束経路」節）で構造的に根拠づけ、単調収束で振動・無限ループが起きないことまで言及。検証可能性と設計妥当性が両立。
- ADR-001 の撤退条件が、優先度: 低の Issue が許す二択（ゼロフレーム化 or 再受容）を実装段階で一貫判断するためのガードになっている。スコープを広げずに着地点を明確化した点が良い。
- ソースコードの実態（hook の現状 `void` / 発火条件 / `_app/index.tsx` L166 の分岐）と plan の記述が完全一致しており、机上の計画と実装対象の乖離がない。
