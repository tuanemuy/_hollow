## AC 対応まとめ

- **AC-1（submit 後 dialog を閉じず進捗へ遷移 / 楽観的 close なし）**: PASS。submit→enqueue→jobId 設定→polling 完了で初めて `onClose`。enqueue 時点の楽観的削除は無し（ADR-005 コメント準拠）。
- **AC-2（determinate progressbar）**: PASS。`app/components/tag/MergeTagDialog.tsx` L162-171 に `role="progressbar"` の determinate バーを確認。
- **AC-3（aria-valuemin / aria-valuemax）**: PASS。L166 `aria-valuemin={0}`、L167 `aria-valuemax={total}`（total=6）。
- **AC-4（aria-valuenow / 100% 到達）**: PASS。L168 `aria-valuenow={processed}`。DB 上 `progress_processed=6 == progress_total=6`（100%）。完了で dialog が閉じる。
- **AC-5（完了後の一覧反映）**: PASS。再検証で `source-tag-ab` が一覧から消え `target-tag-cd` が残存（18→17 件）。

### progressbar マークアップ実値（source 由来 / `MergeTagDialog.tsx`）

```
role="progressbar"
aria-label="統合の進捗"
aria-valuemin={0}         // = 0
aria-valuemax={total}     // total = 6（progress_total）
aria-valuenow={processed} // processed = 6（完了時 = max, 100%）
```

注記: ローカル inline dev では mergeTagsFn enqueue 後、最初の poll が即座に `completed` を返すため、determinate progressbar の中間フレームが描画されずに close まで遷移する。task 許容事項「valuenow==valuemax(=6) に飛ぶ場合あり、最終 100% を確認できればよい」に該当。live snapshot での progressbar 要素キャプチャはできなかったが、(a) determinate マークアップの aria 属性が source で確認でき、(b) DB 上 progress=6/6（100%）かつ status=completed、(c) 完了で dialog が閉じ一覧が正しく更新、の 3 点で AC-2/3/4 を満たすと判定。

## 気づき

- 修正（デコーダ登録）により mergeTagsFn のレスポンスが正しくデコードされ、enqueue→jobId 設定→polling→完了 close の一連が機能している。前回 FAIL の原因は解消。
- inline relay が同期的に即完了するため、determinate progressbar の視覚的中間遷移はブラウザ snapshot では観測困難。進捗バナーの「中間フレーム」を E2E で確実に観測したい場合は relay を遅延させる検証モード（ジョブ完了前に poll を 1 回挟む）があると確実。現状は DB + source 検証で代替可能。
- 両持ち 1 件の no-op 重複なしも `target_notes=8` で裏取りでき、付け替えロジックは正しい。
