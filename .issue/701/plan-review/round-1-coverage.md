## 問題点（要修正）

- **[P-001]** AC-6「失敗が明示される」が、計画上は検証可能な確定形になっていない。
  - 理由: AC-6 の「失敗の明示」手段が ADR-005 で「`IngestionPreview` への失敗フラグ追加 **か** 本文HTML先頭への注記 のいずれか軽い方」と二択のまま未決定。事実確認の結果、`IngestionPreview`（`valueObject.ts`）には現在 failure フィールドが無く、失敗情報は `IngestionJob` 集約側（`FailedIngestionJob.errorCode/errorReason`）に持つ。ADR-005 の方針（`markFailed` 経路を使わず `previewing` に到達）を採ると、`IngestionJob` のエラーフィールドは埋まらないため、**「どこに失敗を記録し、UI のどこに何を表示するか」が宙に浮く**。受け入れ基準としては「失敗が明示される」が観測可能な対象（preview のどのフィールド／画面のどの要素）に落ちていないと、合否判定ができない。
  - 提案: AC-6 の「対応ステップ」を現状「5」のみだが、明示の実体（preview への持たせ方 + プレビュー画面での表示）まで含めて確定し、ステップ5（または専用サブステップ）に「失敗フラグの格納先を確定（`IngestionPreview` に optional な失敗情報フィールドを足す／本文HTML先頭に注記）」「プレビュー画面・録音UI のどの要素で失敗を提示するか」を明記する。少なくとも round-2 までに二択を1つに decide し、AC-6 を「プレビュー画面に文字起こし失敗の注記が表示され、空本文のまま保存できる」のような観測可能文に書き換えることを推奨。VO 変更を避ける注記方式を採るなら波及は小さい（事実確認では preview は commit/wire/component の10〜15箇所で消費されるため、フィールド追加は中規模波及）。

- **[P-002]** AC-1 のうち「接続テストが動く」の検証境界が、ADR-006 の probe 仕様と整合するか曖昧。
  - 理由: AC-1 は Issue 受け入れ条件1 をそのまま「接続テストが動く」と表現しているが、ADR-006 は接続テストを transcribe ではなく `GET /models/{model}`（or `/models`）の軽量 probe にすると決めている。これは妥当な設計判断（実音声不要）だが、**「接続テストが動く」の合格条件が「API キー/モデル名の妥当性確認まで」なのか「transcribe 経路の疎通まで」なのかが AC からは読めない**。ADR-006 自身が「transcribe 固有の障害は検出できない」と認めており、ここを AC で曖昧にすると「接続テストは通るのに実録音で失敗する」状態を合格と誤判定しうる。
  - 提案: AC-1 に「接続テストは provider のモデル存在/認証を probe で確認する（transcribe 実音声疎通は手動/ブラウザテストで担保）」と検証範囲を明記し、実音声疎通の担保を AC-3/手動テスト側に明確に割り当てる。スコープを狭める提案ではなく、**合格判定の境界を確定する**だけの修正。

## 改善提案（検討推奨）

- **[S-001]** AC-3 の「音声ファイルアップロード」導線が実装ステップに明示的に現れていない。
  - 理由: AC-3（ファイルアップロード→ノート化）は既存 `uploadFile`→`runIngestionJob`→commit フローで満たされる想定で、ステップ5,6,10,13 が紐づく。しかし「音声ファイルを選んでアップロードする UI 導線」自体は既存 DropZone が `audio/*` を受理する前提に依存しており、ステップ15（録音UI）は触れるがファイルアップロード経路の音声受理確認は明示が無い。`detectKind` が audio を分類する点は調査済みだが、DropZone の `accept` 属性や対応形式ラベルが音声を実際に受け入れる状態かをステップで一度確認する旨を足すと、AC-3 の「アップロード経由」が確実に検証される（plan は「対応形式ラベルは変更不要」と記すが、`accept` 制約の確認は別物）。

- **[S-002]** AC-5 を「既存挙動で満たす」と判断しているが、回帰確認の所在を AC 表に残すと安心。
  - 理由: AC-5（`MediaAsset(kind='source')` 保存・元ファイル行）は commit フローが format 非依存で音声も自動的に満たす、と事実確認でも裏付けられた（変更不要）。ただし「変更しないから満たされる」要件は、テスト方針・手動テストで明示的に確認対象に入れないと、録音由来 Blob（File 化）特有のメタデータ（MIME/拡張子）で `MediaAsset` の `mimeType`/`filename` が欠落する等の見落としが起きうる。plan のテスト方針「手動/ブラウザ: …元ファイル閲覧」で拾えてはいるが、AC-5 の対応に「（既存フロー合流）」だけでなく手動 TC への紐づけを明記すると漏れ防止になる。

## 良い点

- **受け入れ条件の網羅性が高い**。Issue の7条件が AC-1〜7 に1対1で写像され、各 AC に「由来（Issue 受け入れ条件N / A,B,C）」と「対応ステップ」が併記されていて、カバレッジ追跡が容易。レビューしやすい構造。
- **スコープ外の明示が徹底**。`UserSpeechOverride`、locale 可変化、第2プロバイダ、Workers AI 経由、話者分離/タイムスタンプを「含まれないもの」で根拠付き（Issue 明記 / ユーザー方針 / ポート契約）に列挙しており、**スコープ外作業の混入はゼロ**。特に「Workers AI 経由は後続最適化」と「第一段は REST `/audio/transcriptions`」の線引きは、調査メモが両論併記だった点を方針1に沿って正しく1つに絞れている。
- **ユーザー決定方針3点（OpenAI採用 / A+B+C 1本 / locale ja-JP固定）すべてが計画に正しく反映**され、調査メモの推奨ランキング・残課題（Gemini の webm 不確実性、Deepgram コスト）とも矛盾しない。
- **既存コードの現状認識が正確**で（前提検証で全項目一致）、「変更不要」と判断した箇所（detectKind / uploadFile / commit / ポート契約）が実際に変更不要であることを確認できた。過剰実装を避けた最小スコープ設計になっている。
- AC-6 の根拠を `spec/scenario/ingest.md` の既存方針「テキストが空でも保存可能」に明確に紐づけ、現挙動（`markFailed`）との乖離を「乖離3」として正面から扱っている点が誠実。

## 総評

要件カバレッジは7条件すべて AC に落ちており取りこぼしゼロ、スコープ外混入もゼロ、ユーザー決定方針3点とも完全整合。計画の現状認識は実コードと照合して正確。残る論点は **AC-6 の「失敗の明示」手段の未確定（P-001）** と **AC-1 の接続テスト検証境界の曖昧さ（P-002）** の2点で、いずれもスコープ拡大ではなく「合否を観測可能にする」ための確定作業。round-2 でこの2点を decide すれば、要件カバレッジ観点での懸念は解消する。
