S-002（coverage）は「optimistic と baseline が不一致の過渡状態」を前提にした提案だったが、その前提自体が成立しないことが arch 視点の P-002 で立証された。`FilterBar.tsx:107-108` の reducer を実コードで確認したところ、ディレクトリに対する optimistic アクションは `clearDirectory`（`directoryId: undefined` 化）のみで set 系が存在せず、ディレクトリ「選択」はツリー側 Link の通常 navigate を通る。よって `optimisticDirectoryId` が「`undefined` でも baseline でもない第三の値」になることはなく、過渡状態を AC 化する余地はない。提案を AC 追記ではなく「到達不能分岐の削除」で解決したのは正しい対応。

## 再整理後の AC の整合性検証

- AC-4 / AC-5 が排他かつ網羅であることを確認。`optimisticDirectoryId === undefined`（非表示）／`!== undefined` かつ segments 非空（パンくず）／`!== undefined` かつ segments 空（フォールバック）の3分岐で、`optimisticDirectoryId` の取りうる状態（undefined / baseline 確定値）を漏れなく被覆する。第三の値が存在しない前提（実コードで確認済み）と一致しており、新たな不整合は生じていない。
- AC-5 のフォールバック条件が「`optimisticDirectoryId !== undefined` かつ segments 空」に確定し、「空 `nav` は描画しない」という検証可能な負条件も明記された。前周 S-002（coverage 別案＝segments 空時フォールバックの AC 明示）に相当する内容が AC-5 に検証可能な形で正しく落ちている。
- AC ↔ 実装ステップの紐づけ（AC-1→1,3,4 / AC-2→3,4 / AC-3→4 / AC-4,5→4 / AC-6→1,4 / AC-7→4 / AC-8→4,5）に断絶や宙に浮いた AC はない。実装ステップ5（テスト）が AC-4/5/6/8 の検証手段を具体的に提供している。

#### 良い点
