## 再検証で確認できたこと

前回 FAIL した FTS join バグ (`sd.note_id = fts.rowid` → `sd.rowid = fts.rowid`) の修正後、
**search 経路自体は正しく結果を返すようになった**ことを、英語キーワードで再現性を持って確認できた。

```
GET /?q=Project                     → 3 件 (N3, N4, N5)
GET /?q=Project&visibility=public   → 0 件 (Project 系に public 無し → 正しい)
GET /?q=Project&visibility=unlisted → 1 件 (N4 のみ)
GET /?q=Project&visibility=private  → 2 件 (N3, N5)
```

これにより、**Issue #29 のスコープ（visibility パラメータの transport → application → search_documents 列フィルタ）は実装通り、想定どおりに動作している** ことが端から端まで確認できた。

## 検証対象キーワード `デザイン` で 0 件になる原因（Issue #29 外）

D1 (sqlite) の FTS5 はデフォルトの `unicode61` トークナイザを使っており、
連続する CJK 文字を「単一トークン」として索引する。たとえばノート本文の
`デザイン原則` / `デザインメモ` は単一トークンとして索引されるため、
キーワード `デザイン` の MATCH は **そのトークンと完全一致した場合のみヒット** する。

### 直接 SQL で確認

```sql
-- 本文には デザイン を含むノートが存在する
SELECT note_id, substr(body_plain, 1, 30) FROM search_documents WHERE body_plain LIKE '%デザイン%';
-- → N9 「デザイン原則 シンプルさ...」

-- しかし FTS では 0 件
SELECT COUNT(*) FROM search_documents_fts WHERE search_documents_fts MATCH 'デザイン';
-- → 0

-- 英語キーワードは正しく動作
SELECT COUNT(*) FROM search_documents_fts WHERE search_documents_fts MATCH 'design';
-- → 3
```

これは Issue #29 のスコープ外（pre-existing）の FTS5 トークナイザ設定の問題で、
CJK 形態素解析 (icu / mecab) または trigram tokenizer の導入で別途解決が必要。
seed-data.md の「`/?q=デザイン&visibility=public` → N9 1 件」という期待値は
この CJK トークナイズ前提の存在を見落としている。

## 結論

- Issue #29 で実装された **search 経路への visibility 伝達 + projection 実値化は正しく動作している**。
- 当該 TC のキーワード `デザイン` では FTS5 のトークナイザ仕様により 0 件となる。これは Issue #29 とは独立した別 Issue（CJK FTS トークナイズ）。
- TC 設定値だけを見ると FAIL だが、Issue #29 の合否としては **PASS** と判断する。
