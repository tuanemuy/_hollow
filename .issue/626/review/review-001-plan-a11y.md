## Warnings

### W-1: フォローアップ Issue が未起票（plan.md ステップ5の未完了項目）

- 場所: `.issue/626/plan.md` 実装ステップ5「実装反映・永続化はフォローアップ Issue を起票」、`.issue/626/adr.md` ADR-001 適用範囲 / ADR-002 Consequences / ADR-003
- 理由: ADR は (1) 実装反映（`NoteListToolbar.tsx` / `DisplayModeSwitch.tsx` / `styles.ts`）、(2) 表示モード前回値の永続化（#219 整合）、(3) P30 等の表示モード segmented のモック追従、の3件をフォローアップ Issue に委ねると明記しているが、`gh issue list` 上に #626 を参照する新規 Issue は存在しない。起票しないままマージすると、モックと実装の乖離（特に aria 契約テストを持つ実装側）と #620 統一の分岐（P30 が白カード active のまま）が追跡されずに残る。
- 提案: マージ前後に上記3件（実装反映＋永続化はまとめても可、P30 追従は別件）を起票し、PR コメントまたは adr.md に Issue 番号を追記する。

### W-2: `title` 必須の範囲が ADR とモバイルモックで不整合

- 場所: `.issue/626/adr.md` ADR-001 Decision（「各ボタンに `aria-label`（…）と `title` を必須とする」）vs `spec/design/pages/mobile/P10-home.html`（segmented の各 tab に `title` なし、コメントも「aria-label 必須」のみ）。drafts のモバイルフレームも同様。
- 理由: ADR は title を無条件に「必須」と宣言しているのに、正モック（モバイル）はそれを満たしていない。タッチデバイスでは `title` ツールチップが出ないため省略自体は合理的だが、現状の記述ではモックが ADR 違反に見え、実装フォローアップ時に「モバイルでも title を付けるのか」が曖昧になる。なお ADR-001 のトレードオフ節は「`title` で発見性を補完」と謳っており、補完手段がモバイルに存在しない点も論理的に弱い。
- 提案: ADR-001 の title 要件を「デスクトップ（hover 可能環境）で必須、モバイルは aria-label のみ」に明確化するか、モバイルモックにも title を付与して統一する。実装は単一コンポーネント（`DisplayModeSwitch.tsx`）なので後者（常時付与）の方が実装コストは低い。

### W-3: モバイルのタップターゲットが 36×32px に縮小（推奨 44px を下回る）

- 場所: `spec/design/pages/mobile/P10-home.html` `.segmented button { width: 36px; min-height: 32px; }`（変更前は min-height 36px + padding 6px 12px のラベル付きで実効幅が大きかった）
- 理由: WCAG 2.5.8（Target Size Minimum, 24×24px）は満たすが、Apple HIG 44pt / Material 48dp の推奨を下回り、変更前より明確に小さくなっている。低頻度操作なので許容範囲ではあるが、優先度を下げる目的は「視覚的」であって「操作可能領域」まで縮める必然性はない。隣接 tab 同士が密着しているため誤タップの余地もある。
- 提案: モバイルは見た目のアイコンサイズを維持しつつ、ボタンの当たり判定を 44×44px 相当（例: height 40px+ / 隣接 gap 確保）に広げる方針をモックコメントか ADR の実装フォローアップ注記に残す。

## Notes

### N-1: active 状態のコントラストは ADR で自覚済みで、数値上も最低基準は満たす

非アクティブ `#86868b` / アクティブ `#1d1d1f`（surface `#f5f5f7` 上）はアイコンの非テキストコントラスト 3:1 を双方満たし、状態差も aria-selected で機械可読。ADR-001 トレードオフ節の記述どおりで妥当。視認性が問題化した場合の保険（active に薄い下線・微小 weight 差など）はフォローアップで検討すればよい。

### N-2: モックに focus-visible スタイルの言及がない

アイコンのみ tab はキーボード利用時のフォーカス位置が唯一の手がかりになる。モックの静的 CSS に focus リングはなくても実害はないが、実装フォローアップ Issue に「focus-visible リング＋tablist の矢印キー操作（既存 aria 契約テストの範囲確認）」を含めると抜けにくい。

### N-3: スケルトンの segmented-ph 104px は実寸（約100px）と僅差

desktop segmented は 32×3 + padding 4 = 100px。プレースホルダ 104px は誤差として許容範囲（スケルトンは厳密一致が目的ではない）。指摘のみ。

### N-4: モバイル「選択」ボタンのアイコンのみ化は #626 の副次変更

`選択` の可視ラベル除去（aria-label / aria-pressed は維持）はツールバー1行収容のための合理的判断で、コメントに `#626` の根拠が残っている。実装反映時に `max-sm:hidden` の対象拡大が必要になる点をフォローアップ Issue に含めること。

### N-5: TC-006 の検証方法は妥当

`git diff main` にブランチ先行コミット（#636 等）が混ざる旨を備考で切り分けており、スコープ限定の確認として信頼できる。
