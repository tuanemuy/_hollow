- **[P-002] AC-3 の検証可能性** → 反映済み。AC-3 を「常時占有はトリガーバー1行 + ディレクトリ行のみ、本体はシート展開時のみ縦消費＝現状横スクロール1行と同等以下」と構造記述で具体化。手動確認（テスト方針）にも反映。
- **[S-001] dangling フォールバックチップと省スペースの局所衝突** → 反映済み。AC-7 注記 + AC-3 例外として「dangling 時のみ追加1行は許容」を明記。
- **[S-002] AC-6 の数え方** → 反映されたが**新たな不整合を導入**（下記 P-001）。「件数 = タグ選択数 + 期間(有=1) + 公開状態(有=1) + 内部リンク参照(有=1) + dangling ディレクトリ(有=1)」と数え方は明記されたが、`hasAnyFilter` との一致条件と矛盾する。
- **[S-003] タグ列 `max-sm:flex-nowrap` 残置の扱い** → 反映済み。Step 2 に「デスクトップ列 `max-sm:hidden` で無害化される依存」を明記。AC-1 の「横スクロール列がモバイルで描画されない」枝への依存も明示。

#### 問題点（要修正）

- **[P-001]** AC-6 / Step 1 の件数定義（dangling ディレクトリのみ +1）が、計画自身が要求する不変条件「`hasAnyFilter`（クリア× 表示判定）の真偽と件数>0 が常に一致」と矛盾しており、達成不能な基準になっている。
  - 理由: 既存 `hasAnyFilter`（`FilterBar.tsx:297-302`）はディレクトリについて `optimisticDirectoryId !== undefined`、すなわち **dangling かどうかに関わらず「ディレクトリが選択されていれば true」** で判定している。一方 AC-6 / Step 1 の件数式は「**dangling**（`segments.length === 0`）ディレクトリ(有=1)」とし、dangling のときだけ +1 する。両者は材料が同一でも predicate が異なるため、**非 dangling のディレクトリだけが選択されている状態**で乖離する: `hasAnyFilter = true`（クリア× が出る）なのに件数 = 0（バッジ非表示）。これは round-1 [S-002] が排除しようとした「バッジ0なのにクリア× が出る」不整合そのものであり、AC-6 が掲げる「`hasAnyFilter` の真偽と件数>0 が常に一致するよう同一材料から導出する」という不変条件を、件数式の側が満たせていない。AC-6 は「件数とブール判定の単一情報源化」を達成基準にしているので、この矛盾は基準として成立しない。
  - 提案: 件数のディレクトリ項を `hasAnyFilter` と同じ predicate に揃える。いずれか一方に統一すること:
    - (a) 件数も `optimisticDirectoryId !== undefined`（dangling 限定でなく選択有無）で +1 し、`hasAnyFilter = count > 0` を文字通り成立させる。ただしこの場合「現在地パンくず」として表示中の非 dangling ディレクトリも件数に乗るため、UX 上の意図（パンくずは件数に数えたくない？）を AC-6 で明示する。
    - (b) ディレクトリを件数からも `hasAnyFilter` からも外し、両者を「ディレクトリ非依存の同一材料」で揃える（ただし現状 `hasAnyFilter` がクリア× の表示にディレクトリを含めている挙動を変えることになり、AC-7「ディレクトリの挙動は退行しない」と衝突しうるので影響確認が必要）。
    - どちらにせよ「件数の predicate と `hasAnyFilter` の predicate がディレクトリ項で一致している」ことを AC-6 に1行で固定し、Step 1 の件数式とコメントを揃える。現状の「dangling のみ +1」は要修正。

#### 改善提案（検討推奨）

- **[S-001]** `filterBar` の行番号参照が plan 内で 102（受け入れ基準 AC 表周辺・現状欄）と 111（調査結果・Step 2）に割れている。
  - 理由: 実コードでは `export const filterBar` は `styles.ts:111`（102 行目は `filterLabel`）。Issue 本文が `styles.ts:102` を引いているためそれを踏襲した箇所が残っているが、実装者が 102 を見ると別定数に当たる。致命的ではないが、Step 2 の撤去対象を一意に指すため plan 内の参照を 111 に統一しておくと迷いがない。

- **[S-002]** AC-2 の「すべてのフィルターに到達できる」検証が、Step 6(c) の「フィルターコントロールが描画される」までで、**内部リンク参照のシート内到達性**が条件分岐（ネスト Dialog の検証結果次第で「シート内は適用中チップ + 解除のみ、新規選択は別動線」になりうる）に依存している点が AC として固定されていない。
  - 理由: Step 3 注意点の代替案(b)を採ると、モバイルのシート内からは内部リンク参照の**新規選択ができず**、別動線（デスクトップ同様）に寄せることになる。その場合「`max-sm` で横スクロールなしに内部リンク参照フィルターを新規適用できる」経路が成立するかは設計確定まで未定。AC-2 は「到達できる」だが、代替案(b)では「シート外の別動線で到達」になり、横スクロール回避（AC-1）と矛盾しない動線かを別途確認する必要がある。ネスト Dialog 検証の結論が出た時点で AC-2 に「内部リンク参照の新規適用動線（シート内 or 別動線）も横スクロールに依存しない」を一文追記すると、相反要件の取りこぼしを防げる。
  - 補足: スコープ拡大ではない。設計確定（Step 3）の結論を AC-2 に反映する確認のみ。

#### 良い点

- 前周の主要 2 問題（AC-4 の自己矛盾 P-001、AC-3 の検証不能 P-002）がいずれも検証可能な基準へ書き換えられ、Step 3/6 の確定タスク（`data-*` スコープ・ヘルパー限定）に正しく紐づいている。デスクトップ不変という最重要制約の達成判定が客観化された。
- レビュー履歴（plan 末尾）で前周指摘の各項を反映先（AC / Step / adr）と対応付けて記録しており、2周目のトレーサビリティが高い。
- スコープ「含まれないもの」は前周から不変で具体的（デスクトップ不変・適用ロジック/URL search/`useOptimistic`/ナビ層不変・#743 ADR-002 不変・新トークン不可・バックエンド不変・`spec/design` 同期は別途）。実装ステップもすべて提示層に閉じ、スコープ外作業の混入は無い。
- 相反要件（横スクロール回避 × 省スペース）を (A) 集約トリガー + (D) 既存 `Dialog` ボトムシートで両立する筋は妥当で、ADR-001 で (B)(C)(E) の却下理由（横スクロール再発・恣意的常時表示・トラップ欠如）まで明示。Issue 中核に正面から答えている。
- ネスト Dialog（シート内 `NotePickerDialog`）のリスクを Step 3 / ADR-001 で検証手順 + 代替案付きで先送りせず扱っており、a11y（AC-5）の落とし穴を計画段階で潰している。

**総括:** 前周の 5 指摘（P-001/P-002/S-001/S-002/S-003）はすべて反映され、デスクトップ不変・省スペースの検証可能性は確保された。ただし [S-002] の反映過程で導入された件数式（dangling ディレクトリのみ +1）が、計画自身の不変条件「`hasAnyFilter` の真偽 ⇔ 件数>0」と矛盾しており（非 dangling ディレクトリ選択時に乖離）、AC-6 が達成不能な基準になっている点が要修正（P-001）。S-001（行番号参照の揺れ）と S-002（内部リンク参照のシート内到達性の AC 固定）は精緻化の推奨。スコープ逸脱・カバレッジ漏れは P-001 を除き見当たらない。
