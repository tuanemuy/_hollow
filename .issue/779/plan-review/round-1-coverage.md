# Plan Review (Round 1) — Issue #779: 要件カバレッジ・スコープ整合性

レビュー視点: Issue の要件カバレッジとスコープ整合性。plan.md の AC-1〜AC-5 を起点に、
(1) 合意要件の落とし込み漏れ、(2) 各基準の検証可能性、(3) 基準と実装ステップの紐づけ、
(4) スコープ外作業の混入、を確認した。

## 検証済みの前提（コード照合）

- **AC-5 の前提は正確**: `app/components/note/loaders.ts:187-188` で自ノート検索パスが
  `title: hit.title` / `excerpt: hit.snippet` をマップし、`ListView.tsx:36`(`{note.title}`) /
  `:40`(`{note.excerpt}`) でプレーン描画している。よって
  - スニペットは現状すでに `<mark>` 生文字列が漏れている（#778 由来の既存事象）。
  - 共有アダプターで**タイトルを無条件ハイライトすると新規に**タイトルへ `<mark>` が漏れる。
  → AC-5 は「過剰拡張」ではなく**必須のリグレッション防止**。plan/ADR の判断は妥当。
- **新VOの必要性は実在する**: `SearchTitle`(cap 200, `valueObject.ts:18,93-105`) は
  `SearchDocument.title`（保存）と `SearchHit.title`（描画）で共用。`highlight()` 後は
  200+マーカーで cap 超過 → `toHit` が throw。`SearchBody`/`SearchSnippet` 分離の先例どおり
  描画用VO新設は妥当な粒度（過剰設計ではない）。
- **`SearchQuery.highlight` フラグの粒度は妥当**: `dateBasis`/`sort`(`valueObject.ts:354-364`)
  と同じ opt-in idiom。default `true` で既存3呼び出しは後方互換。
- **モック整合**: `P32-public-search.html` は `.result-title mark`(L511) を持ち、L984
  "Cloudflare Workers + D1 のパフォーマンス計測" はタイトル無マーク（本文のみ一致）→
  **AC-3 の「タイトル無ハイライト行が存在」は実在**。
- **`searchUserPublicNotes` の描画コンシューマはコードベースに存在しない**（grep で 0 件）。
  default true でも漏れる先がないため、現状は無害（plan の「未検出」判断は正しい）。

## 問題点（要修正）

- **[P-001]** 受け入れ基準表の「対応ステップ」紐づけで、ステップ3が誤った基準に割り当てられている。
  - 理由: AC-1（P32 結果カードのタイトルに `<mark>` が描画される）の対応ステップに「3」が
    含まれているが、ステップ3は `searchOwnNotes` に `highlight:false` を渡す**自ノートの opt-out**で、
    P32（`searchPublicNotes`、default `highlight:true`）のタイトル描画には一切寄与しない。
    逆に AC-5（他サーフェスへのマーカー漏れ防止）の対応ステップは「1,2,4,7」で、AC-5 を
    **実際に実装する中核であるステップ3が欠落**している。step↔AC のトレーサビリティが反転している。
  - 提案: AC-1 の対応ステップから「3」を外し「1,2,5,6」に。AC-5 の対応ステップに「3」を加え
    「1,2,3,4,7」にする。ステップ自体は正しく網羅されており、修正は表のクロスリファレンスのみ。

## 改善提案（検討推奨）

- **[S-001]** `searchUserPublicNotes` の扱いを「実装時に判断」で開いたままにせず、
  「コードベースに描画コンシューマが存在しないため default true は inert（漏れ先なし）」と
  確定的に記述するとよい。
  - 理由: 本レビューで grep 0 件を確認済み。plan.md L67/L128 と adr.md L67 の
    「UIコンシューマがあれば実装時に確認」という未決事項は、現時点では空振りであり、
    確定記述にすることで実装者の判断負荷と曖昧さを除ける。スコープは増えない。

- **[S-002]** AC-3 の「由来」を P32 モックの具体行（L984 のタイトル無マーク例）に紐づけると、
  検証時の参照が一意になり、テスト（本文のみ一致で `hit.title` に `<mark>` を含まない）の
  期待値根拠が明確になる。
  - 理由: 現状「P32モック」とだけ書かれており、どの行が無ハイライト例かが暗黙。検証可能性が上がる。

## 良い点

- **横断リグレッション分析が的確**: 共有ポート `query()` の3サーフェス利用と、自ノート
  loader の `hit.title`/`hit.snippet` プレーン描画を正しく捉え、AC-5 として明文化。
  コード実態と完全に一致しており、本Issue最大の落とし穴を初稿で押さえている。
- **新VO・新エラーコードの導入根拠が既存先例（`SearchBody`/`SearchSnippet`）と対称**で、
  cap=1024 の見積もり（原文≤200＋最悪マーカー≈650）まで定量的に示している。過剰設計ではない。
- **後方互換の担保**（`highlight` default true）と、`highlight()` 採用理由（アプリ側マッチ算出を
  排し FTS 一致セマンティクスに揃える、ADR-001）が明快。
- **Issue 本文の合意要件（P32 タイトルハイライト／モック整合／バックエンド FTS 変更／
  `highlightSnippet` 再利用）はすべて AC とステップに落ちており、漏れはない**。
- スコープ外（自ノートへの新規ハイライト追加、`highlightSnippet` の共有モジュール移設）を
  明示的に除外しており、スコープ境界が引かれている。副次効果（自ノートスニペット漏れの是正）も
  リスク欄で開示済み。
