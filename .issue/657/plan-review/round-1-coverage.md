# Plan Review — Issue #657 / Round 1（要件カバレッジ・スコープ整合性）

レビュー対象: `.issue/657/plan.md` / `.issue/657/adr.md`
レビュー観点: Issue 要件のカバレッジ、受け入れ基準の検証可能性、基準⇔ステップの紐づけ、スコープ整合性

## 要件トレース（Issue → 受け入れ基準）

| Issue の要件 | 対応 AC | 判定 |
|---|---|---|
| 問題点1: R2 バケット CORS 未設定によりブラウザ PUT が preflight 403 で失敗 | AC-1 | カバー（same-origin 化で preflight 自体を消す。検証可能） |
| 問題点2: presign 先（リモート R2）と finalize の head（ローカル binding）のストア不一致 | AC-2 | カバー（同一 binding 化 + finalize 200。検証可能） |

Issue にコメントはなし（`gh issue view 657` で確認）。本文の要件はすべて受け入れ基準に落ちている。AC-3（表示経路）・AC-4（署名セマンティクス維持）・AC-5（staging/production 不変）は Issue 本文に明文はないが、「フローを完走できる構成」「検証環境の構成変更」の合理的な含意であり、スコープ逸脱ではない。

主要な事実関係もコードと照合済み: `R2PresignConfig.endpoint` の存在と DI 未配線（`r2ObjectStorage.ts` / `serverCloudflare.ts`）、`/sitemap.xml` インターセプトの前例（`app/server.cloudflare.ts`）、`wrangler.toml` の LOCAL DEV ONLY 構成、`.issue/655/testing.md` の存在 — いずれも計画の記述どおり。

#### 問題点（要修正）

- **[P-001]** ステップ6 の「`pnpm dev` / `pnpm build && pnpm start` の両方でゼロ追加手順のままフローが完走する」という主張が、提示された構成値と矛盾する
  - 理由: `pnpm dev` は `vite dev`（`vite.config.cloudflare.ts` で `server.port: 3000`）で動く一方、計画は `wrangler.toml [vars]` に `R2_S3_ENDPOINT = "http://localhost:8787/dev/r2"` をハードコードする。`pnpm dev`（localhost:3000）から見ると presign 先は cross-origin になり、same-origin 化の前提（AC-1）が崩れる。さらに 8787 で wrangler dev が起動していなければ PUT 先自体が存在しない。Issue の要件（`pnpm build && pnpm start` での完走）は満たすが、計画文面が実際より広い保証を謳っている。
  - 提案: いずれかに修正する。(a) ステップ6 の主張を「`pnpm build && pnpm start`（wrangler dev, :8787）でゼロ追加手順」に絞り、`pnpm dev` でのポート差を「リスクと注意点」に明記する。(b) presign エンドポイントを絶対 URL の env ではなくリクエストオリジン（または `APP_URL`）から導出する設計に変える。Issue のスコープ的には (a) で十分。

#### 改善提案（検討推奨）

- **[S-001]** AC-4（不正署名・期限切れ → 403）の「検証可能な形」をステップ8 の手動 E2E に含めるか、ユニットテストのみで判定するかを明記する
  - 理由: AC-4 の対応ステップは 2, 3（実装 + ユニットテスト）だが、AC 表は「検証可能な形」を謳う一方、テスト方針の手動 E2E には AC-4 の確認項目がない。「ユニットテスト（verify 拒否ケース）の PASS をもって AC-4 充足とする」と一文書けば、検証時の判定基準が曖昧にならない。
- **[S-002]** AC-6 の判定条件に「maxNoteBytes 制限内のファイルを使う（または一時変更 + 復元）」の選択をどちらにするか事前に決めておく
  - 理由: リスク欄に両案が併記されたままだと、ステップ8 実行時の手順が確定せず、前回検証（27MB で 1 MiB 制限に衝突）と同じ手戻りが起きうる。determinate 進捗バーの観察には throttling 前提である程度のサイズが要るため、どちらを採るかで手順が変わる。
- **[S-003]** スコープ外宣言「testing.md 確認項目2・3 の再実行は不要（presentation 層に変更なし）」の根拠を AC-5 同様にテストで担保している旨をスコープ節からも参照する
  - 理由: 確認項目2・3 の非再実行は妥当だが、根拠の「コード上の不変性」は実際にはステップ5 の byte-identical テストと DI テスト（テスト方針に記載済み）が担保している。スコープ節から該当ステップへの参照があると、レビュー・検証時に根拠を追いやすい。

#### 良い点

- 受け入れ基準が表形式で「由来」と「対応ステップ」まで紐づいており、Issue の問題点1・2・やること2 が AC-1 / AC-2 / AC-6 に 1:1 でトレースできる。紐づけの誤りもない（各ステップの内容と AC の対応を個別に照合済み）。
- スコープ外（CORS 設定、remote bindings、#655 実装側変更、temp files presign）が Issue 本文の制約（PutBucketCors 権限なし等）を根拠に明示的に棄却されており、ADR-001 と整合している。
- 調査結果がコードの実態と一致している（`endpoint` オーバーライドの存在と DI 未配線、`presign()` のパス上書き問題、sitemap インターセプトの前例）。「既存の受け口を配線する」最小差分のアプローチで、Issue 要件に対する過剰実装がない。
- AC-5（本番不変）を「デフォルトエンドポイント出力の byte-identical テスト」という機械的に検証可能な形に落としている点が優れている。Issue #452 の署名順序不変条件への言及も回帰防止として的確。
- ADR-002（dev プロキシでも SigV4 検証）は一見スコープ拡大に見えるが、「presigned URL のセマンティクスを検証対象に残す」「無認証書き込み口を作らない」という根拠が明確で、ラウンドトリップテストによる検証ずれ対策まで含めて妥当。

## 結論

要件カバレッジに漏れなし。修正必須は P-001（`pnpm dev` での完走保証の過大記述）の1件のみで、計画の骨格（設計・ステップ・AC 構成）は変更不要。
