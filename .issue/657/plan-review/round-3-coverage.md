## 総評

**問題点（P-）はゼロ。**

Issue の2つの問題点（R2 CORS / presign-finalize ストア不一致）と「やること」2項目（構成整備 + testing.md 確認項目1 の再実行）は AC-1〜AC-6 で漏れなくカバーされており、各 AC は由来と対応ステップが紐づき、検証手段（ユニットテスト / 手動 E2E）も明示されている。1〜2周目の指摘（`pnpm dev` スコープ限定、AC-4 の充足判定方法、ファイルサイズ方針、byte-identical テストの時刻固定、ハンドラ配置）はすべて取り込み済みであることを確認した。

カバレッジ観点の個別確認結果:

- 問題点1（CORS）→ AC-1（same-origin 化で preflight 自体を消す）: 対応ステップ 1〜6 で実現経路が閉じている。
- 問題点2（ストア不一致）→ AC-2（binding 一本化 + finalize 200）: 同上。
- 「やること」後段（testing.md 確認項目1 再実行）→ AC-6 / ステップ8: `.issue/655/testing.md` の確認項目1 とその throttling 手順（同ファイル 46行目）の実在を確認。確認項目1 は「presign → PUT → finalize → HTML 挿入のフロー全体」の確認を兼ねる位置づけ（同 71行目）であり、AC-6 の再実行で Issue の意図する E2E 完走確認が成立する。
- AC-3（表示経路 / presigned GET）は Issue 本文に明示はないが「E2E 完走」の含意として妥当で、由来列にもその旨が明記されている。スコープの過大化ではない（GET ハンドラは PUT と同一機構の対称実装）。
- スコープ外宣言（`pnpm dev` :3000、リモート CORS 設定、remote bindings、#655 実装側、TEMP_FILES、確認項目2・3 非再実行）はいずれも根拠付きで、Issue 要件との矛盾なし。確認項目2・3 非再実行の代替担保（byte-identical テスト + DI テスト）も具体的。
- スコープ外混入なし: 全ステップ（1〜8）がいずれかの AC に対応づく。SigV4 プリミティブ抽出（ステップ1）は AC-4 実現の前提であり独立した機能追加ではない。

## 指摘

### S-001: AC-5 の対応ステップに 7（ドキュメント更新）が含まれるが、ドキュメントは検証手段ではない

- 理由: AC 表は「検証可能な形で」を掲げており、AC-5（staging/production 不変）の機械的な充足判定はステップ4 の DI テスト（env 未設定時に従来構成）とステップ5 の byte-identical テストで完結する。ステップ7 は知識の文書化であって AC-5 の充足を検証しない。AC-4 では充足判定方法（ユニットテスト PASS）を明記する形に揃えた経緯があるので、AC-5 だけ判定方法が暗黙なのはわずかに非対称。
- 提案: AC-5 の備考に「充足判定はステップ4 の DI テスト + ステップ5 の byte-identical テストの PASS、および staging/production の wrangler 設定に新規 env を追加しないことのレビュー確認をもって行う」と一文足す（対応ステップ列から 7 を外すか、7 は「周知」目的と注記する）。

### S-002: ステップ8 の検証結果の記録先・形式が未指定

- 理由: 「結果を `.issue/657/` 配下に記録する」とだけあり、#655 の流儀（`manual-test/results/TC-1.md`, `summary.md`）に合わせるのか自由形式かが決まっていない。AC-6 の PASS 判定のエビデンス形式が曖昧だと、後続レビュー（PR の Browser Verification セクション等）で参照しにくい。
- 提案: 「`.issue/657/manual-test/results/`（#655 と同形式）に記録する」のように記録先と形式を一行で確定する。
