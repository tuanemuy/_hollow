#### 問題点（要修正）

- **[P-001]** タグ削除 × の寸法統一（S5 / AC-4）が、SSOT である P12 モックと**矛盾**しており、乖離表の記述も事実と食い違う
  - 事実: モック `spec/design/pages/mobile/P12-editor.html` L642-651 の `.tag-chip .x` は `font-size: 13px; min-height: auto;` の**裸グリフ**で、現行実装 `tagChipRemove`（`styles.ts` L109 = `text-[13px]` 裸グリフ）と**同一**。つまりこの箇所は実装がモックに既に一致している。
  - 理由: 
    - plan.md L66 の乖離表は「タグ × 寸法統一（mock L642）／ text-[13px] 裸グリフ（styles L109）／ アドホック → S5」と書き、モック L642 を「統一済みの目標形」であるかのように提示しているが、L642 は現行実装と同じ裸グリフの定義であり、乖離は存在しない。むしろ S5 で `filterChipRemove` 相当のボックス化（`w-4 h-4 rounded-full`）に変えると、実装が**モックから乖離する**（逆方向）。
    - AC-4 の由来欄は「mock L591-620」を挙げるが、この範囲は `dir-dropdown-search`（L591-603）と `dir-tree-item`（L604-619）であって、タグ ×（L642）を含まない。タグ × 統一のモック根拠が誤って紐づけられている。
    - Issue 課題2 は「他のチップの × ボタンと寸法を統一する」（＝ `filterChipRemove` はボックス型）を求める一方、確定済みモックは裸グリフを維持しており、**Issue の意図とモックが食い違っている**。この矛盾を計画が解消しないまま S5 でボックス化に倒しているため、実装後にモック（SSOT）と実装が乖離した状態になる。
  - 提案: どちらの権威（Issue「他チップと統一」＝ボックス化 / モック＝裸グリフ）を採るかを計画で明記する。ボックス化を採るなら Phase 1（デザイン確定）で **P12 モックの `.tag-chip .x` をボックス型に更新するステップを明示**し、乖離表・AC-4 由来欄の誤記（L642 を「統一済み目標」と読める記述、L591-620 の誤引用）を修正する。裸グリフを維持するなら S5 を「変更不要（既にモック一致）」に改める。いずれにせよ「モックと実装を一致させる」責務（Issue の Phase 1 の主眼）を果たすこと。

- **[P-002]** Issue の Phase 1「デザイン（既存モックの確定）」がトークン確認のみに縮退しており、実装が意図的にモックから外れる箇所の**モック反映（SSOT 同期）ステップが欠落**
  - 理由: Issue は「デザイン（既存モックの確定・トークン整合）から実装まで」を一気通貫で求め、Phase 1 に「モックを最新実装と突き合わせ…仕様を確定」を掲げる。しかし plan.md の Phase 1 相当は L73-74 の「トークン確認（新規トークン不要）」のみで、モック本体を確定・更新する作業が計画に無い。その結果、計画が意図的にモックから外す次の 3 点が SSOT へ反映されない:
    1. タグ × のボックス化（P-001）。
    2. 下部固定バーへ save-status を複製しない（mock `.save-bar` L1026 は複製、実装は AutosaveIndicator 単一保持）。
    3. save-bar 内ボタンを `max-sm:[&>button]:flex-1` で等幅フル化（mock は save-status `flex:1` ＋ ボタン `flex-shrink:0`＋primary `padding:0 24px` の非等幅レイアウト。status 省略の帰結として妥当だがモックとは別レイアウト）。
  - 提案: Phase 1 に「P12 モックを確定実装に合わせて更新する（`.tag-chip .x`／`.save-bar` の save-status 省略とボタン等幅化を反映、もしくは差分を spec 側に注記）」ステップを追加する。2・3 は plan のリスク項で「意図的な差分」と記録済みなので、モックにも同趣旨の注記を入れれば SSOT の整合が保てる。少なくとも「モックを触らない」判断であれば、その旨と理由（differences are intentional, mock kept as-is）を計画に明記して、後続レビュー・実装者が乖離を欠陥と誤認しないようにする。

#### ヘッダー簡略タイトルのスコープ外化（ADR-001）— 重点検証の結論

**判定: 逃げではなく妥当。ただし論拠の一部が不正確で、S-001 で補強すべき。**

- 妥当と判断した根拠（いずれもコードで裏取り済み）:
  - `.header-doc` はモック L1042 で `aria-hidden="true"`。スクリーンリーダーからは隠された装飾扱いで、機能欠落ではない。
  - ヘッダーは `AppShellFrame`（`header={header}` prop）→ `AppShellDrawer` で全 `/_app` 共有に構築され、エディタ（`main` の children）とは疎結合。per-route のタイトルスロットが無く、実装には共有シェル横断の context/portal 配管が必要。ADR-001 が引き合いに出す `DrawerCtx`（`AppShellDrawer.tsx` L27）という同型の client-context 実績も確認でき、「(a) context 方式でフォローアップ可能」という引き継ぎは技術的に正確。
  - Issue 課題1 のヘッダー項目は「未実装」と述べるのみで、機能的な受け入れ条件を一切課していない。中核設計3項目のうち2項目（保存バー・メタ折りたたみ）は本 Issue で実装され、残る1項目は装飾かつ横断コスト大。フォローアップ Issue へ切り出し＋推奨実装方針の明記まで行っており、責任回避的な「単に落とす」処理ではない。
- ただし論拠に不正確さがある（→ S-001）: ADR-001 と plan L31 は「主要アクション到達性は下部固定保存バー（AC-1）が既に満たす」を除外理由に挙げるが、`.header-doc` の機能は「本文スクロール中に編集対象ノートのタイトルを見失わない**方向づけ（orientation）**」であって、アクション到達性ではない。保存バーはこの orientation を代替しない（タイトル入力はスクロールで画面外へ出る）。除外自体は上記理由で正当だが、「保存バーが満たすから不要」という論法は論点がずれている。

#### 改善提案（検討推奨）

- **[S-001]** ADR-001 / plan L31 の除外理由から「主要アクション到達性は保存バーが満たす」という論点ズレの一文を外し、正確に「`.header-doc` の機能は title orientation で本 Issue の機能要件ではない（Issue が AC を課していない）＋ aria-hidden の装飾＋横断配管コスト大」に絞る。「純粋な装飾要素」という表現も、視覚的には orientation の役割を持つため「a11y 上は装飾（aria-hidden）で機能要件化されていない」と精密化すると、除外判断の説得力が上がる。

- **[S-002]** 下部固定バーへ save-status（AutosaveIndicator）を複製しない判断（S2 / リスク項）は a11y 上妥当だが、副作用として「モバイルで本文を下方スクロール中は自動保存状態が視認できない」点を一言 AC もしくはリスクに明記しておくと、検証時の期待値が明確になる。モックが save-bar に status を置く狙い（スクロール中の保存状態可視）を実装が意図的に手放すことの記録になる。

- **[S-003]** 軽微な行番号ズレ: AC-1・乖離表が引く mock `.save-bar` は L1010 開始（plan は L1009）。実装可否には影響しないが、P-001 のモック引用修正とあわせて整えると参照精度が上がる。

#### スコープ整合性（スコープ外作業の混入チェック）

- **APP_MAIN の `max-sm:px-4`（S8 / ADR-002）** は編集画面を超えて全 `/_app` に波及するが、Issue 課題3 が `APP_MAIN` の `px-6` 過大を名指しで縮小要求しているため**スコープ内**。共有プリミティブ修正（SSOT）を選び、負マージンのローカル相殺（横スクロール要因化のリスク）を避けた判断は妥当で、波及リスクは ADR-002＋リスク項＋検証（他画面目視）で受け止められている。過剰なスコープ拡大ではない。
- コントロールサイズ統一（AC-4）は「全ビューポート共通の一貫性修正」でモバイル最適化を厳密には超えるが、Issue 課題2 が統一を求めており、かつ「既存デスクトップ寸法の意図を尊重し最小限」と自制している。スコープ creep とは言えない。
- その他、内側レイヤー（ドメイン/ユースケース/アダプター）への波及ゼロ、ルート（`edit.tsx`/`new.tsx`）変更不要の明言も適切。**不当なスコープ混入は見当たらない。**

#### 良い点

- 課題1〜4 の全項目を「基準化」か「理由付き除外」で漏れなく処理し、(検討)項目のうち本文 min-h を AC-7 に昇格・ツールバー/ダイアログは別 Issue と、粒度判断が一貫している。
- 受け入れ基準がすべて検証可能（`max-sm` 挙動・≤390px 横スクロール無し・44px タップ床・`sm` 以上の回帰無し・必須コマンド通過）で、基準↔ステップの紐づけに取り違えが無い。
- 確立済みプリミティブへの流用が的確: BulkActionBar の `max-sm:fixed inset-x-0 bottom-0`、ADR-005 の backdrop、`TOUCH_TARGET`、`filterChipRemove` 形状、`data-[open]:`。新規 CSS・新規トークンを増やさない方針が CLAUDE.md と一致。
- AC-4 の「操作対象**行**はタップ床44px」という語り口が、モックの明示方針（L159「44px 床は主要アクションに限定。チップは膨張させない」）と整合し、タグ ×（mock `min-height:auto`）を 44px 床の対象から正しく外している。細部の一貫性への目配りが効いている。
- 共有シェル横断リスク・`position:fixed` 含有ブロック・二重 aria-live・キャレット再配置を具体的にリスク列挙し、ADR-001〜003 で設計判断を明文化。判断の追跡可能性が高い。

---

#### 総括

要件カバレッジ自体は網羅的で、課題1〜4 の取りこぼしは無く、スコープ境界も適切。ヘッダー簡略タイトルの除外は逃げではなく妥当（ただし論拠を S-001 で精密化推奨）。要修正は「デザイン→実装」Issue でありながら Phase 1 のモック確定・同期が抜けている点に起因する 2 件（P-001: タグ × がモックと矛盾＋乖離表の事実誤認、P-002: モック反映ステップ欠落）。この 2 件を解消すれば、SSOT（モック）と実装の一致という本 Issue の中核要件まで満たせる。
