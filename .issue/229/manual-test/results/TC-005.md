# TC-005 (エッジ1): 他人のジョブが見えない

**結果: PASS**
**実行日時:** 2026-05-27
**セッション:** verify-tc-001-002-005

## シナリオ

UserB (`existing-new@example.com`) でログインしたとき、UserA のジョブ
（`previewing` / `discarded` ともに）が `/upload` のキューに表示されず、
UserB 自身の `previewing` ジョブのみが表示されることを確認する。
これにより、デフォルト除外条件の追加が所有者一致の認可フィルタを
壊していないことを担保する。

| 02 | `/login` で UserB の認証情報を入力しログイン | ログイン成功 | — |

## 確認結果（期待値との照合）

- 期待: UserB のキューに UserA のジョブが表示されない → **満たす**
- 期待: UserB の `previewing` ジョブ（`issue229-userB-previewing.md`）のみ表示 → **満たす**
- 期待: ヘッダーが UserB（`mailowner`）として描画されている → snapshot で `M` のアバターを確認

## 実行上のメモ

- セッション cookie (`__Host-session`) は HttpOnly のため、ブラウザ内 JS からは
  クリアできなかった。代わりに `agent-browser cookies clear` で context レベルの
  cookie を全消去してログアウトを実現した。
- アプリ UI 上にはセルフ・ログアウト導線が見つからなかった（ヘッダーのアバター
  `link "... のメニュー"` は実態としては `/` への `<Link>` で、ドロップダウンを
  開かない）。本検証では cookie 消去で代替したが、これは TC のスコープ外。

## 結論

所有者フィルタが維持されており、別ユーザーのジョブ（`previewing` / `discarded`
のいずれも）が見えないことを確認できた。Issue #229 のデフォルト除外条件は
所有者一致フィルタの上に重ねて適用されており、認可境界を侵食していない。
**PASS**
