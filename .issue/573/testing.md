## 確認環境

本 Issue は backend（パスワード再検証・削除影響集計 usecase・ポート/アダプター追加）と frontend（多段確認 UI）の両方に触れる。実機確認はローカル開発サーバで行う。スキーマ変更は無い（既存カラムの集計のみ）ため新規マイグレーションは不要。

### 検証環境の起動

```
pnpm db:apply:local
pnpm dev
```

`pnpm db:apply:local` でローカル D1 に既存マイグレーションを適用（未適用分があれば）。`pnpm dev`（`vite dev`・Cloudflare ランタイム）でローカルサーバが起動する。表示された URL をブラウザで開き、**ログイン済みユーザー**で `/settings/account-delete` を確認する。

確認には影響集計が意味を持つよう、以下を持つユーザーが望ましい:

- active なノートを複数持つ（うち 1 件以上を公開、1 件以上に限定公開リンクを発行済み）
- アップロード済みメディア（`attached` 状態）を持つ
- パスワードログインのユーザー（再認証確認用。本コードベースでは全ユーザーがパスワード設定済み）

開発用シードは `pnpm seed:dev-admin`（admin ユーザー）を利用できる。集計値の確認には、そのユーザーでノート作成・公開・リンク発行・メディアアップロードを事前に行っておく。

### デプロイ方法

なし（検証環境のみで確認できる）。ステージング反映が必要な場合は `pnpm deploy:staging`。

## 確認項目

### 1. 削除影響の実データ集計リスト表示（AC-4 / AC-5 / AC-8）

- **対応する受け入れ基準:** AC-4, AC-5, AC-8
- **目的:** `/settings/account-delete` を開くと、削除前に「何がどれだけ失われるか」が実データで表示される。
- **手順:**
  1. 事前に対象ユーザーで active ノート N 件（うち公開 P 件）・限定公開リンク L 本・`attached` メディア M 件（合計 B バイト）を用意する。
  2. `/settings/account-delete` を開く。
  3. 影響リスト（alert 領域）に、所有ノート数 / メディア件数・容量 / 公開ノート数（410 Gone 化対象）/ 失効する限定公開リンク数が表示されることを確認。
- **期待結果:** 各値が DB の実データと一致する（ノート＝active のみ、メディア＝`attached` のみ、公開ノート＝公開中のみ、リンク＝失効していない active リンクのみ）。
- **確認ポイント:** **虚偽表示禁止** — ノート本体・メディア実体は即時物理削除されないため「即座に消える」と断定せず「アクセスできなくなる/復元できません」系の表現になっていること。公開ノートの 410 Gone 化・限定公開リンク失効・進行中エクスポートのキャンセルは断定表現で良い。saved view / custom prompt は個別件数を出さず包括表現にとどまっていること。

### 2. 多段確認 UI の構成（AC-6）

- **対応する受け入れ基準:** AC-6
- **目的:** confirm-steps（①同意チェック → ②DELETE 入力 → ③ユーザー名 + パスワード）の多段構成がモック `P24-settings-account-delete.html` に準拠する。
- **手順:**
  1. `/settings/account-delete` を開く。
  2. 影響リストの下に、step-num 付きの 3 ステップ（同意 checkbox-row / 確認語 DELETE input / ユーザー名 + パスワード input）が順に並ぶことを確認。
- **期待結果:** モックの alert / confirm-steps / step-num / checkbox-row の構造・寸法・色（デザイントークン経由）に準拠している。
- **確認ポイント:** モック SSOT と並べて目視比較。トークン由来のユーティリティで寸法・色が当たっていること。

### 3. 削除ボタンの有効化ゲート（AC-3 / AC-7）

- **対応する受け入れ基準:** AC-3, AC-7
- **目的:** 全ステップを満たすまで「アカウントを完全に削除する」ボタンが disabled。
- **手順:**
  1. `/settings/account-delete` を開く（初期状態でボタンが disabled）。
  2. 同意チェックのみ → まだ disabled。
  3. 確認語に `delete`（小文字）や `DELET` など `DELETE` 以外を入力 → まだ disabled。
  4. 確認語 `DELETE` を入力 → まだ disabled（ユーザー名・パスワード未入力）。
  5. ユーザー名（自分の正しいユーザー名）+ パスワードを入力 → ボタンが有効化される。
- **期待結果:** 全条件（同意 && 確認語が厳密に `DELETE` && ユーザー名一致 && パスワード入力あり）を満たして初めて有効化される。
- **確認ポイント:** 確認語は大文字小文字を区別し `DELETE` のみ通る。

### 4. パスワード再検証（AC-1 / AC-2）

- **対応する受け入れ基準:** AC-1, AC-2
- **目的:** 削除実行時にパスワードが再検証され、不一致なら削除されずフォーム内にエラー表示。
- **手順:**
  1. ステップ 3 までを満たし、パスワード欄に**誤ったパスワード**を入力して削除を実行。
  2. エラー表示と、アカウントが削除されず画面遷移しないことを確認。
  3. 次に**正しいパスワード**を入力して削除を実行。
- **期待結果:** 誤パスワード時は `invalid_credentials` 由来のエラーがフォーム内に表示され画面遷移しない。username 不一致時は従来どおり `confirmation_mismatch`（client gating で通常到達しないが backend 契約は維持）。正パスワードで削除が完了する。
- **確認ポイント:** 検証順序は username → password。誤パスワードでアカウントが消えていないこと（再ログイン可能）。

### 5. 削除成功後の即時ログアウト・遷移（AC-7）

- **対応する受け入れ基準:** AC-7
- **目的:** 削除実行後に即時ログアウトされ `/` へ遷移する。
- **手順:**
  1. 正しい入力で削除を完了する。
  2. `/` へ遷移し、その後保護ルート（例 `/settings/profile`）に手動アクセスする。
- **期待結果:** 削除後 `/` へ遷移。保護ルート再訪で未認証として扱われリダイレクトされる（`clearAppShellCache` 経路を踏襲）。

## エッジケース・異常系

### 1. 集計値ゼロのユーザー

- **目的:** ノート・メディア・公開・リンクがすべて 0 のユーザーで集計が破綻しない。
- **手順:** まっさらなユーザーで `/settings/account-delete` を開く。
- **期待結果:** すべて 0 件として正しく表示され（`COALESCE` により容量 0 バイト）、UI が崩れない。

### 2. trashed ノートに紐づく限定公開リンク

- **目的:** 失効リンク数が trashed ノートのリンクも含む（実カスケードと一致）。
- **手順:** 公開リンク発行済みノートを 1 件ゴミ箱へ移動 → `/settings/account-delete` の失効リンク数を確認。
- **期待結果:** trashed ノートの active リンクも失効対象として数に含まれる（過小カウントにならない）。

### 3. 確認語の前後空白・大文字小文字

- **目的:** 確認語の厳密一致。
- **手順:** ` DELETE `（前後空白）や `Delete` を入力。
- **期待結果:** いずれも有効化されない（`DELETE` のみ通る。transport の `z.literal('DELETE')` でも担保）。

## 既存機能への影響確認

- **既存の削除カスケード**: パスワード再検証を追加した後も、削除成功時の全カスケード（User soft-delete → credentials purge → 公開ノート private 化＋リンク失効 → 進行中 export job キャンセル → 全セッション失効）が従来どおり動くこと。
- **`ConfirmDialog` 共通コンポーネント**: 本フォームから依存を撤去するが、他画面で `ConfirmDialog` を使う箇所（あれば）が壊れていないこと。
- **他の設定画面**: `/settings/profile`・`/settings/security`・`/settings/prompts` が #571/#572/#574 の実装を含め従来どおり表示・動作すること。
