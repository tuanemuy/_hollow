# 動作確認計画 — Issue #572: P22 アクティブセッション一覧（端末ごと表示・行単位ログアウト）

**Issue:** #572
**作成日:** 2026-06-09

---

## 確認環境

本 Issue は P22 セキュリティ画面（`/settings/security`）にアクティブセッション一覧 UI を追加し、backend にセッション一覧取得 usecase と id ベース行失効 usecase を新設する変更。`sessions` テーブルは既存で列も揃っているため新規マイグレーションは不要。実機確認はローカル開発サーバで行う。

### 検証環境の起動

```
pnpm dev
```

`vite dev`（Cloudflare ランタイム）でローカルサーバが起動する。表示された URL をブラウザで開く。確認には**同一ユーザーで複数のアクティブセッション**が必要なため、以下のいずれかで複数セッションを作る:

- 別ブラウザ / シークレットウィンドウ / 別デバイスから同じユーザーでログインする（推奨。userAgent / ipAddress が別行として並ぶ）。
- 同一ブラウザで一度ログアウト→再ログインを繰り返す（古いセッションが残っていれば複数行になる）。

ログイン済みユーザーで `/settings/security` を開き、「セッション」節の一覧を確認する。

### デプロイ方法

なし（検証環境のみで確認できる。ステージング反映が必要な場合は `pnpm deploy:staging`）。

## 確認項目

### 1. アクティブセッション一覧の表示

- **目的:** 端末ごとに行が表示され、表示値が backend 実データに一致する。
- **手順:**
  1. 2 つ以上の異なるブラウザ/シークレットウィンドウから同じユーザーでログインする。
  2. いずれかのセッションで `/settings/security` を開く。
  3. 「セッション」節に各セッションが行として並ぶことを確認。
  4. 各行の表示値（ipAddress、ログイン日時、userAgent ベースのタイトル）を確認。
- **期待結果:** ログイン中のセッション数だけ行が表示され、各値が実データに一致する。
- **確認ポイント:** モック `spec/design/pages/P22-settings-security.html` の `.session-list`/`.session-row`/`.session-meta` 構造に寄っているか。**地名・OS パース名・「最終アクセス（相対時刻）」など DB に無い捏造値が出ていないこと**（ADR-002/ADR-004）。時刻ラベルは「ログイン日時」相当で `createdAt` ベース。

### 2.「このセッション」バッジ（isCurrent 判定）

- **目的:** 現在開いているセッションの行だけに「このセッション」バッジが付く。
- **手順:**
  1. 確認項目1の状態で、ブラウザ A から `/settings/security` を開く。
  2. ブラウザ A の現在セッションに当たる行に「このセッション」pill が表示されることを確認。
  3. 他の行には pill が付かないことを確認。
  4. ブラウザ B で同じ画面を開き、B の行にだけ pill が付くことを確認（A 視点とは別の行になる）。
- **期待結果:** 開いているブラウザごとに、その現在セッションの行にだけバッジが付く。
- **確認ポイント:** 判定は server 側（token 比較）で行われ、client に session token が渡っていないこと（DevTools の Network/HTML で token 文字列が露出していないか確認）。

### 3. 行単位ログアウト（個別失効）

- **目的:** 「このセッション」以外の行をログアウトでき、対象セッションが失効する。
- **手順:**
  1. ブラウザ A の `/settings/security` で、他端末（ブラウザ B）の行の「ログアウト」ボタンを押す。
  2. 一覧が再検証され、B の行が消えることを確認。
  3. ブラウザ B をリロード（または保護ページへ遷移）し、ログアウト状態（再ログイン要求）になることを確認。
- **期待結果:** 対象セッションのみ失効し、A 自身のセッションは維持される。
- **確認ポイント:** client が POST するのは session token ではなく opaque な `sessionId` であること（Network タブで確認）。「このセッション」行には失効ボタンが出ない（モック準拠）。

### 4. 既存の一括失効ボタンとの共存

- **目的:** 「他のすべてのセッションをログアウト」一括失効ボタン（#543 で実装済み）が従来どおり動く。
- **手順:**
  1. `/settings/security` で一括失効ボタンを押す。
  2. 現在セッション以外がすべて失効し、一覧が現在セッション 1 行だけになることを確認。
- **期待結果:** 一括失効後、一覧に「このセッション」行のみ残る。
- **確認ポイント:** 行単位失効と一括失効が UI 上で破綻なく共存している。

## エッジケース・異常系

### 1. セッションが現在の 1 件のみ

- **目的:** 自分のセッションが現在の 1 つだけのとき、一覧が破綻しない。
- **手順:** 単一ブラウザのみでログインし `/settings/security` を開く。
- **期待結果:** 現在セッション 1 行のみ表示され「このセッション」pill が付く。失効ボタンは出ない。空表示崩れがない。

### 2. 他ユーザー / 不在の sessionId を投機 POST

- **目的:** 所有者スコープ失効が他人のセッションを失効できないこと（冪等 no-op）。
- **手順:** DevTools で `revokeSessionFn` の POST を複製し、`sessionId` を他ユーザーのもの・存在しない値に差し替えて送る。
- **期待結果:** 自分以外のセッションは失効されず（no-op）、エラーで落ちず一覧も変化しない。実 D1 結合テストでも同等のケースを担保する。

### 3. 期限切れセッションの除外

- **目的:** 期限切れ（`expiresAt <= now`）のセッションは一覧に出ない。
- **手順:** （結合テストで担保）期限切れ行を投入し `listForUser` が返さないことを確認。
- **期待結果:** 一覧は未期限切れのセッションのみ。

## 既存機能への影響確認

- **SecurityForm の他セクション**: パスワード変更・メール変更・一括失効が props 追加（`sessions`）で壊れていないこと。
- **ログイン/ログアウトフロー**: セッション発行（`issue`）・解決（`resolve`）・token ベース `revoke` が不変であること（本 Issue は新メソッド追加のみで既存 port メソッドは変更しない）。
- **SessionService port 拡張**: `D1SessionService` 以外の実装は無いため型波及なし（追加メソッド実装で解消）。
