# 実装計画 — Issue #500: デザインモック(spec/design/pages)と現状実装の乖離を解消する（モック⇄実装の突き合わせ）

**Issue:** #500
**作成日:** 2026-06-05
**複雑度:** 中〜大規模

---

## 目的

デザイン改善の土台として、デザインモック（`spec/design/pages/*.html`）と現状の React 実装デザインを一致させる。モックは Phase 3 で作られた後 React 実装が独立進化して乖離が生じているため、モックを「設計の単一の真実（SSOT）」に戻すべく、ズレを棚卸しして解消する。

### 突き合わせのルール（優先順位）

1. **基本は「今の実装」を正とする** — 実装側で意図的に調整・改善された見た目／挙動は、モック側を実装に合わせて更新する（モックを書き換える）。
2. **明らかに未実装の部分はモックを正とする** — モックにあるが実装されていない UI/状態/バリアントは、モックを残し（書き換えず）、実装側のフォローアップ対象として記録する。
3. **判断に迷う差分は潰さず、要判断として列挙**し、本 Issue のコメントへ投稿して別途判断する。

## スコープ

### 含まれるもの

- `spec/design/pages/` 配下の全 36 ファイル（P13系が3枚あるため実数36）の突き合わせ。
- 各ページについて対応する `app/routes/` / `app/components/` の現状実装と、レイアウト・コンポーネント構成・トークン適用・状態バリアントの4観点で差分を洗い出す。
- 方針1の差分はモック HTML を実装の見た目に書き換える。
- 方針2（実装フォローアップ）・方針3（要判断）を一覧化し、Issue コメントへ投稿する。

### 含まれないもの

- **実装コード（`app/`）の変更**。未実装フォローアップは記録に留め、別 Issue に切り出す。
- デザインそのものの良し悪しの議論（=改善）。改善案は後続 Issue へ。
- `spec/design/review/00x.md`（モック単体の品質レビュー）の観点 — 本 Issue とは別物。混同しない。

## 実装ステップ

### 1. 準備とブランチ作成

- **変更内容:** main から `issue/500/mock-impl-reconcile` ブランチを作成。`.issue/500/diffs/` 成果物ディレクトリを作る（既存 `manual-test`/`review` は別物なので触らない）。`.issue/500/mapping.md` に36モック→route/component 対応表とチェックリストを確定。
- **理由:** 突き合わせの起点と進捗管理。

### 2. 領域分割（5バッチ・並列）

35ページ（実数36ファイル）を5領域に割り、領域単位でサブエージェントに並列割り当て。各サブエージェントは担当ページを1枚ずつ独立に突き合わせる:

- **A. 未ログイン/auth（9）**: P01, P01b, P02, P03, P04, P05, P06, P07, P34
- **B. 個人ノート系（11ファイル）**: P10, P11, P12, P13-upload, P13-upload-modal, P13a-upload-modal, P14, P15, P16, P17, P18
- **C. ビュー/設定（5）**: P20, P21, P22, P23, P24
- **D. 公開（4）**: P30, P31, P32, P33
- **E. 管理者（7）**: P40, P41, P42, P43, P44, P45, P46

共通シェル（layout）は領域横断の差分源なので、**バッチB担当が代表ページ(P10)でシェル差分を一次判定し、他バッチは同シェル部分は P10 判定に従う**。`mapping.md` に明記して二重作業を避ける。ただし P10 シェル判定が及ぶのは **P10〜P24 の認証済みページのみ**。未ログイン領域（バッチA）の `auth/AuthHeader` は認証済みシェルと別物なので P10 判定を流用しないこと（`mapping.md` にも範囲を転記する）。

### 3. 各ページの突き合わせ手順（サブエージェント共通プロトコル）

1. モック HTML をブラウザ/読み込みで開いて見た目・構造・状態バリアントを把握。
2. 対応する route/component と `styles.ts` を読み、Tailwind ユーティリティが再現する見た目を読み取る。
3. 「レイアウト／コンポーネント構成／トークン適用／状態バリアント」の4観点で差分を列挙。
4. 各差分を3分類に振り分ける。判断は方針1→方針2→方針3の順で適用。迷ったら必ず C（要判断）へ。
5. `.issue/500/diffs/{Pxx}.md` に記録（1ページ1ファイル）。

```

## B. 実装フォローアップ（モックを正に残す＝未実装）
```

### 5. モック修正の実施（方針1の差分のみ書き換え）

`Edit` で `spec/design/pages/{Pxx}.html` を実装の見た目に合わせて書き換える。指針:

- トークンは `tokens.md` を正とし、`:root` のトークン名（`--color-accent` 等）参照を崩さない。色・寸法・角丸・余白は実装の効果値に対応するトークンへ置換（任意値の直書きを増やさない）。
- 既存モックの CSS 記法・class 命名（`.input`/`.btn-primary` 等のセマンティック class + `<style>` 内定義）に**合わせる**。React/Tailwind の utility 文字列をそのまま貼らない（モックは静的 HTML/CSS で同じ見た目を再現する技術なので、既存モックの書き方に翻訳する）。
- 状態バリアントの差分は、モックの該当バリアントブロックを実装の挙動に合わせて更新。
- モック内の設計意図コメントが実装ファイルを名指ししている場合、書き換え後も参照整合を保つ（食い違っていたらコメントも実装に合わせて更新）。

### 6. フォローアップ・要判断の集約

全ページの B/C を2ファイルに集約:

- `.issue/500/followups.md`: 実装フォローアップ一覧（未実装、モックを正に残す）。ページ・観点・モック該当箇所・別Issue化候補としてテーブル化。
- `.issue/500/decisions-pending.md`: 要判断一覧（判断待ち）。論点を明示。

両ファイルの要点を **Issue #500 のコメント**に投稿（`gh issue comment 500`）し、フォローアップ対象・要判断が判断待ちであることを明示（受け入れ条件3・4）。

## 設計判断

- **実装コードは変えない** — Issue はモックを実装に寄せる修正のみを求める。未実装フォローアップは記録に留め別Issue化。
- **共通シェルの一括判定** — 重複転記されたヘッダー/サイドバー/ドロワーを代表ページ(P10)で一次判定し横展開（作業量・判定ブレ低減）。
- **3分類フォーマットの統一** — ページ間で記録形式を揃え、followups/decisions への集約とIssueコメント生成を機械的に行えるようにする。
- **既存 `.issue/500/review`・`manual-test` には触れない** — 本Issue成果物は `diffs/`, `mapping.md`, `followups.md`, `decisions-pending.md` に分離。

## リスクと注意点

- **静的HTML ⇄ React の翻訳ミス** — Tailwind ユーティリティの効果（fluidサイズ、`data-*` バリアント、`@theme inline` 経由のトークン橋渡し）をモックのセマンティック class + CSS へ正しく翻訳する。字面コピー禁止。`styles.ts` の定数を tokens に逆引きしてからモックCSSへ反映。
- **px 直値 ⇄ fluid トークンの値変化（非自明ケース）** — モックは多くのプロパティをリテラル px（例 P10 `.pill-btn { font-size: 14px }`）で書くが、実装は `text-sm`＝`var(--text-sm)`（clamp、デスクトップ実効13px）を使う。#461 ADR-001 が `text-[13px]→text-sm` を意図的に駆動しているため、実装に寄せるとモックの `font-size: 14px` は実効13px へ**値ごと**変わる。「px が合っているから差分なし」と誤判定しないこと。fluid トークンに置換すると実効値が変わる点に注意。
- **分類の誤判定** — 「実装が意図的に改善した差分」と「実装が未実装で退化した差分」の区別は文脈依存。迷ったら潰さず C（要判断）へ。関連Issue（#461寸法、#497 FilterBar、#292 ボタン形態、#231 空状態、#221 フィードバック 等）の設計判断と矛盾しないか参照。
- **公開側の空状態スコープ差（#231 既知論点）** — index.md §7.1 は「空状態アイキャッチは認証済み `EMPTY_STATE` が対象、公開側 `EMPTY_LIST` は #231 スコープ外」と明記。P30/P32 等のモックがアイコン付き空状態を描いている場合、公開側実装のアイコン無しは**意図的**であり「未実装（方針2）」ではなく意図的スコープ差。バッチ D 担当が誤って方針2に倒さないよう decisions-pending の既知論点として先回り登録する。
- **設計意図コメントの陳腐化** — モック内コメントが実装ファイルを名指しする箇所は書き換え時に参照整合を保つ。
- **モック数** — 実ファイルは36枚（P13系3枚）。36ファイル全数を対象（漏れ防止）。
- **対応なしページ** — `admin/metrics.tsx`（モックなし）や逆にモックはあるが実装が薄いページは、対応関係を `mapping.md` と followups に記録。

## テスト方針

- **モックの目視確認** — 静的HTMLなのでブラウザで直接開く。書き換え後も単一ファイルで崩れず開けることを確認（index.md §9 の制約維持）。
- **実装の見た目確認** — `docs/test.md` の手順でローカルサーバ起動。認証済みルートはシード+cookie注入。各ページを表示しモックとの一致を4観点で突き合わせる。スクリーンショットを証跡に。
- **コード非変更** — `pnpm typecheck/lint/test` は影響なし。
