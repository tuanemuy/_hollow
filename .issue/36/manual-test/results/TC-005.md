# TC-005 — マウスクリックで候補を選択（onMouseDown 罠回避 / ADR-003）

**Result:** PASS (with note on test harness)
**Session:** `verify-tc-005`
**Date:** 2026-05-19

## Steps

1. Login, open note D, switch to WYSIWYG.
2. Type `[[Hel`. Popup shows 2 options.
3. Dispatch real `mousedown` + `mouseup` + `click` event sequence on the `Helsinki` option.

## Observations

- After the mouse-event sequence, the editor contains `[[Helsinki]] ` (with trailing space) — same insertion result as the keyboard path.
- Plain `el.click()` and even agent-browser's high-level `click` command did NOT trigger the selection because the implementation listens to `mousedown` (not `click`) to avoid the focus/blur race documented in ADR-003. A click-only synthesised event therefore does nothing — which is exactly the behaviour the ADR was protecting against in the opposite direction (real-user mousedown wins, programmatic click that doesn't include mousedown is ignored).
- With a full `mousedown`+`mouseup`+`click` event sequence (i.e. real mouse interaction equivalent), the option is selected and text inserted. Editor does NOT blur prematurely.

## Test-harness note

`agent-browser click` appears to use only DOM `.click()` (or focus + click) which bypasses `mousedown`. Real user interaction always emits `mousedown` first, so this is a property of the test harness, not a regression. The DOM sequence test above closely simulates real user click and confirms the production code path works.
