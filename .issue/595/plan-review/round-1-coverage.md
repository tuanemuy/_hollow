## 結論サマリー

Issue 本文の 2 大要件（24h チャート / 最近のアクティビティ）と「虚偽表示禁止」鉄則は、AC・スコープ・ADR の三層でよく落とし込まれている。要件の取りこぼしは見当たらない。一方、**既存 LLM scalar metric の扱いがチャート系列の縮退判断と矛盾しうる点**、および**AC-4 の「バックアップ」行が実際には永続化されない可能性**という、Issue の意図（実データに一致させる）に直接関わるカバレッジ上の論点が残っている。要修正 2 件・改善提案 3 件。

---

#### 問題点（要修正）

- **[P-001]** AC-2 の LLM 系列縮退判断が、既存 scalar metric「LLM 呼び出し (24h)」との整合を AC として明文化していない
  - 理由: 本 Issue で「LLM 呼び出しの hourly 系列はデータ源が無いので描かない」(AC-2 / ADR-002) と判断する場合、**既に `Dashboard/index.tsx` に存在する scalar の「LLM 呼び出し (24h)」metric-card も同じデータ源不在の対象**である。実際にコードを確認したところ、`usageMetricsProvider.ts` には production 実装が無く `NullUsageMetricsProvider` のみが wire されており（`serverCloudflare.ts:740`）、`llmCallsToday` は常に `null`（UI 上「取得失敗」表示）である。つまり「LLM の hourly 系列は虚偽になるので描かない」と判断する一方で、隣の scalar カードは「取得失敗」を出し続ける、という状態が残る。スコープ節は「既存 scalar metrics の挙動変更はしない（#545 で一致済み）」としており方針自体は妥当だが、AC-2 のリスク説明（「記録源の有無を Step 1 で確定」）が scalar 側に言及しないため、レビュー時に「LLM の Step 1 確定結果を scalar カードにも反映すべきでは？」という齟齬判断が AC から検証できない。
  - 提案: AC-2 もしくはスコープ節に一文追加する。例「Step 1 で LLM 記録源が無いと確定した場合、hourly 系列を描かないのに加え、既存 scalar『LLM 呼び出し (24h)』カードの扱い（現状『取得失敗』表示の維持 / 文言調整）も本 Issue で判断対象とする。ただし scalar の挙動変更は #545 一致のとおり行わず、表示の整合のみ確認する」。これにより「LLM 系列を描かない」判断が UI 全体で一貫しているかを AC から検証可能にする。

- **[P-002]** AC-4 が「バックアップ」を活動行に含めると断定しているが、`export.job.completed` が実際に emit・projection される保証が AC/ステップから読み取れず、虚偽表示禁止に抵触しうる
  - 理由: AC-4 は活動行に「バックアップ」を含むと列挙し、Step 8 で `handleExportJobCompletedEvent` を新設するとある。ADR-003 は「バックアップ種別は実在の `export.job.completed` に意味を寄せる」と決めている。コード確認では `ExportEvents.completed` は `domain/export/entity.ts` で生成され `runExportJob.ts` が `completed` 遷移を行うため、イベント自体は実在・emit されうる。ただし (a) これは**管理者起点のインスタンスエクスポートではなく per-owner エクスポート**であり（スコープ節も明記）、(b) 管理ダッシュボードの「最近のアクティビティ」に per-owner のユーザーエクスポート完了を「バックアップ完了」として出すことが、運用者にとって実態に合うラベルになるかは ADR-003 の「ラベル文言は実態に合わせる」に委ねられたまま AC に落ちていない。最悪の場合、AC-4 を字面どおり満たすために「バックアップ完了」ラベルで per-owner エクスポートを出し、これがモックの「D1 / nightly」を連想させる誤読（リスク節が指摘する懸念そのもの）を招く。
  - 提案: AC-4/AC-5 の「バックアップ」を、検証可能かつ虚偽でない形に締める。例「『バックアップ』種別は per-owner エクスポート完了（`export.job.completed`）に限り、ラベルは実態（例『エクスポート完了』）とし、存在しない D1 nightly backup は出さない。該当イベントが運用上ほぼ発生しないなら、本 Issue では種別を縮退（出さない）してもよい」。「含む」と断定せず、実データが無ければ出さない縮退余地を AC に持たせることで、他種別（user_created 等）と同じ虚偽表示禁止の扱いに揃う。

#### 改善提案（検討推奨）

- **[S-001]** AC-7 の冪等性が、既存 consumer の `idempotencyStore`（`handlers.ts:153/173` の `hasProcessed`/`markProcessed`）と二重防御になる点を明記すると、検証範囲が明確になる
  - 理由: コード上、consumer は `eventId` 単位で `hasProcessed`→skip / `markProcessed` を行い、再配信は dispatch 前に弾かれる。一方 `dispatchDomainEvent` は 1 イベントを複数ハンドラへ fan-out する設計のため、activity projection 側の `insertIfAbsent`（event_id unique）は「同一 eventId が複数の projection 経路を通る／idempotencyStore が lapse する」ケースへの二重防御になる。AC-7 のテスト方針（同一 eventId 二重配信で行が増えない）は妥当だが、「idempotencyStore があるのになぜ projection 側でも冪等化が要るか」を一言補足すると、レビュー時に AC-7 のテストが冗長か必須かの判断がぶれない。

- **[S-002]** AC-5 の「対象」「詳細」列の実データ取得元（特に user の表示名 / target の組み立て）が AC・ステップから追えない
  - 理由: モックは「@haru_morisaki」「メール確認完了 · ja」のように、対象=ユーザーハンドル、詳細=イベント固有の補足を出す。projection 行（`activity_log`）は `target` text / `detail` text を持つとあるが、`user.created` 等のイベント payload にハンドル名や locale が含まれるか（含まれなければ projection 時に別 repo を引く必要がある）が計画から読めない。AC-5 を「4 列に分類される」だけで検証可能としているが、各列の中身が実データで埋まるかは payload 依存。Step 8/9 のイベント payload 設計時に「activity 行に必要なフィールドが payload に揃っているか」を確認する旨を一文足すと、AC-5 が空文字や ID 直書きで形式的にしか満たされないリスクを避けられる。

- **[S-003]** 「大量アップロード」集約（ADR-005）の閾値未確定が、AC-4/AC-5 の検証可能性を弱めている
  - 理由: ADR-005 は閾値・窓幅を「実装時に運用観点で決める（暫定: 5 分・N 件）」とする。これは設計判断として妥当だが、AC-4「行はすべて実イベントに一致」/ AC-5 の「大量アップロード」分類は、閾値が決まらないと「何件で 1 行になるか」をテストで固定できない。Step 14 のテスト方針は「閾値前後」を挙げており方針は良い。AC かテスト方針側に「暫定閾値を定数化し、その値での境界テストを置く（閾値自体の妥当性チューニングは別途）」と明記すると、未確定パラメータでも AC を検証可能な状態に保てる。

#### 良い点

- **虚偽表示禁止の鉄則が AC・スコープ・ADR の三層に一貫して反映されている。** AC-2（LLM 系列データ源無しなら描かない）/ AC-8（導線が無ければリンクを描かない）/ スコープ節（存在しない D1 nightly backup を写さない）/ ADR-002・003・004 がいずれも #540〜545 の鉄則に明示的に紐付き、派生元 #545 ADR-001 の「データ源が無いので描かない」判断と完全に整合している。Issue の最重要要件である「実データに一致」が形骸化していない。

- **スコープ外の切り出しが Issue の意図と矛盾しない。** 「期間を変更」=任意レンジ集計、「すべて見る」=全件一覧ページ、システムバックアップ subsystem 新設、遡及バックフィルを明確に範囲外とし、それぞれ別 Issue / 別 provider 拡張へ送る判断は、Issue 本文「直近 24h hourly のみ」「チャートと活動は別 PR 可」と一致する。スコープ過大な作業の紛れ込みは見当たらない。

- **「データ源不在」要件を Step 1（LLM 記録源確定）として最初に固定する順序設計が正しい。** 虚偽表示の可否は記録源の有無に依存するため、これを設計前提として先頭ステップに置き、結果を ADR-002 に記録する流れは、後段の実装が虚偽系列を描かないことを構造的に担保する。実際コード確認でも LLM 専用ログテーブルは存在せず（scalar も Null provider）、この Step 1 の必要性は裏付けられる。

- **AC とステップの紐づけ表が概ね正確で追跡可能。** AC-1〜9 に「対応ステップ」列があり、PR-A（チャート: Step 1-4,12）/ PR-B（活動: Step 5-13）の分割境界とも整合する。設定変更イベント新設（AC-6 ↔ Step 9,10）、冪等（AC-7 ↔ Step 6,8,11）の対応も実在コードの欠落（`domain/adminSettings/events.ts` 不在・adminSettings usecase が `collectEvents` 未呼び出し）と一致しており、調査結果が実態に基づいている。

- **event-sourced projection 採用（ADR-001）が既存先例に正しく整合。** `search/handleNoteSavedEvent` 等の確立パターンに乗せ、活動ログを read-model として扱う判断は、ドメインに活動ログ概念を持ち込まない点で関心分離が正しく、Issue の「ドメイン/ユースケース/アダプターの設計から着手」とも噛み合う。
