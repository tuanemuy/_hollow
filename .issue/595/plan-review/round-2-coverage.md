## 結論サマリー

1周目の P-001（LLM scalar 整合）・P-002（バックアップ行のラベル/縮退）はいずれも AC-2 / AC-4 に正確に落ち込み、虚偽表示禁止の鉄則が AC・スコープ・ADR の三層で一貫している。改善提案 S-001〜S-003 も AC-7 / AC-5 / テスト方針へ反映済み。Issue 本文の 2 大要件・スコープ外切り出しに新たな取りこぼし・スコープ過大は見当たらない。要修正はゼロ。検証可能性をさらに高める軽微な改善提案を 2 件のみ挙げる。

#### 問題点（要修正）

**問題点ゼロ。**

1周目指摘の反映を個別に確認した結果:

- **[P-001 反映: 妥当]** AC-2 に「LLM 記録源無しと確定した場合、既存 scalar『LLM 呼び出し (24h)』カードも同じデータ源不在で現状『取得失敗』表示のままだが、scalar の挙動は #545 一致のとおり変更せず表示整合のみ確認する（hourly を描かない判断が UI 全体で一貫する）」が追記され、提案文言とほぼ一致。ADR-002 Decision 末尾・Consequences・ステップ A-1・リスク節にも一貫して反映。「LLM 系列を描かない判断が UI 全体で一貫しているか」が AC から検証可能になった。**過剰反映や矛盾なし。**
- **[P-002 反映: 妥当]** AC-4 が「『バックアップ』種別は per-owner エクスポート完了（`export.job.completed`）に限り、ラベルは実態（例『エクスポート完了』）とする。存在しない D1 nightly backup は出さない。該当イベントが運用上ほぼ発生しないなら本 Issue では種別を縮退（出さない）してよい（他種別と同じ虚偽表示禁止の扱い）」と締められ、「含む」断定から「縮退余地付き」へ正しく変更。ADR-003・スコープ節・ステップ B-4・リスク節とも整合。コード確認でも `export.job.completed` は `domain/export/events.ts:21` / `entity.ts:285` で実在・emit されることを確認済みで、「実在イベントに意味を寄せる」前提が裏付けられている。**虚偽表示禁止の扱いが他種別と揃った。**
- **[S-001 反映]** AC-7 に二重防御（consumer の `idempotencyStore` 主防御 + projection `insertIfAbsent` 二重防御 + 非冪等操作禁止）が明記。ADR-001 Decision にも責務分担が記述。
- **[S-002 反映]** AC-5 に「対象」「詳細」に必要な payload フィールドの有無を Step B-4/B-5 で確認し、空文字や ID 直書きを避ける旨を追記。
- **[S-003 反映]** 閾値定数化（`LARGE_UPLOAD_THRESHOLD` / `LARGE_UPLOAD_WINDOW_MINUTES`）と境界テストが ADR-005・C-1・テスト方針に明記。

#### 改善提案（検討推奨）

- **[S-001]** AC-4 の設定変更種別の網羅範囲が、実在する全 adminSettings usecase と突き合わせて検証できない
  - 理由: AC-4 の設定変更（`instance_settings.updated`）は「登録制御・LLM・プロンプト・限度・トークン等」と例示し、ADR-003 の `settingKind` ユニオンも `"registration_policy" | "llm_config" | "prompt_template" | "instance_limits" | "design_tokens" | ...`（末尾 `...`）と開いている。一方、実在する変更系 usecase を確認すると `toggleRegistrationPolicy` / `updateLLMConfig` / `updatePromptTemplate` / `updateInstanceLimits` / `updateDesignTokens` / `updateSpeechConfig` / `resetPromptTemplate` / `resetAllPromptTemplates` / `resetDesignTokens` / `reencryptApiKey` / `updateUserPromptOverride` 等が存在する。ステップ B-6 の対象列挙も「`{...,}`」で開いており、「どの usecase に `collectEvents` を足すか」が AC からは確定しない。AC-6 は「設定変更（登録制御・LLM・プロンプト・限度・トークン等）が実行されると活動行として記録される」とあるが、`updateSpeechConfig`（音声）や各種 `reset*`（リセットも実質的な設定変更）を含めるか否かが曖昧で、「設定変更が記録される」の検証境界がぶれる。
  - これは要修正ではない（設計判断として実装時に既存パターンへ寄せる方針が ADR-006 注記で明示済み）。ただし B-6 または AC-6 に「対象 usecase は実装時に変更系 adminSettings usecase を棚卸しして確定する（音声・各種 reset を含むか/含まないかを明示）」と一行足すと、`settingKind` ユニオンの最終形と AC の検証範囲が一致し、「一部 usecase だけイベント emit して他は漏れる」取りこぼしを構造的に防げる。

- **[S-002]** AC-8 の「描かない」判断が AC として検証可能だが、「すべて見る」が活動空状態時にどう振る舞うかまでは AC から読めない
  - 理由: ADR-004 / AC-8 で「遷移先が無ければ導線を描かない」は明確。一方、B-8 で活動空状態（バックフィル無しでリリース直後は空）の honest filler を出すとあるが、空状態のときに「すべて見る」リンク（実装しない前提なので元から非表示）と空状態メッセージが二重に出ないか、空状態 UI と導線非表示の関係は AC からは追えない。実害は小さい（どちらも「正直に出す/出さない」方針内）が、テスト方針に「活動空状態 + 導線非表示の共存」を 1 ケース挙げると、空状態時の UI 整合が検証可能になる。これは検証可能性の補強であり、要件漏れではない。

#### 良い点

- **1周目 P-001/P-002 が提案文言に忠実に AC へ落ち、かつ ADR・スコープ・ステップ・リスクの全層に波及反映されている。** 部分的な「AC だけ直してADR が古いまま」のような不整合が無く、虚偽表示禁止の判断が文書全体で一貫している。特に AC-2 の「hourly を描かない判断が scalar カードと UI 全体で一貫する」という追記は、1周目が指摘した「UI 全体での一貫性が AC から検証できない」という核心を正確に解消している。

- **虚偽表示禁止の鉄則が依然として三層（AC / スコープ / ADR）で一貫。** AC-2（LLM データ源無しなら描かない + scalar 整合）/ AC-3（実データ 0 と取得失敗 null の区別）/ AC-4（縮退余地付きバックアップ）/ AC-8（導線非表示）/ スコープ節（D1 nightly 写さない・バックフィル無し）/ ADR-002・003・004・005 がいずれも #540〜545 の鉄則に紐付き、派生元 #545 ADR-001 と完全整合。

- **AC ↔ ステップの紐づけが PR 分割（A-n / B-n / C-1）の連番付け直し後も正確。** 1周目 S-002 の指摘どおり接頭辞付き番号に振り直され、AC 表の「対応ステップ」列も追従。AC-1〜9 すべてに対応ステップが付き、PR-A（チャート）/ PR-B（活動）の境界とも矛盾しない。

- **スコープ外の切り出しが Issue 意図と矛盾せず、スコープ過大の紛れ込みも無い。** D1 nightly backup subsystem 新設・任意レンジ集計・全件一覧ページ・遡及バックフィル・既存 scalar metrics 挙動変更をすべて明確に範囲外とし、Issue 本文「直近 24h hourly のみ」「チャートと活動は別 PR 可」と一致。`D1UsageMetricsProvider` の scalar を `null` 固定にして「既存 4 metric-card 不変」を成立させる判断（ADR-002 / リスク節）は、スコープ膨張回避として的確。

- **「実データ 0」と「取得失敗 null」の区別（1周目改善提案）が AC-3・A-5・テスト方針に明確化され、チャートの honest 描画基準が検証可能。** 0 埋め 24 バケットと null degrade の区別はカバレッジ上重要で、テストケース（空テーブルで 24 本 0 / 1 メトリクス失敗で系列のみ null）まで落ちている。
