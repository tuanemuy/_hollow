# TC-05 — trashed-but-public / published_at NULL の listing 除外

Status: PASS (listing path); see observation on profile hero count.

## Seed
- `trashed-note` (a5): `notes.status='trashed'` but `publication_states.visibility='public'`, `published_at` non-null (relay-lag scenario).
- `null-pub-note` (a6): `visibility='public'` but `published_at IS NULL` (anomaly).

## Observations
- On `/u/alice` listing (default + updatedAt sort + tag-filtered views), neither
  `Trashed Ghost Note` nor `Null Pub Note` ever appears.
- Listing renders exactly 4 notes; no "total=N but N-1 shown" gap in the list.
- Verified at the SQL level too: `listPublicNoteIdsByOwnerSorted` joins
  `notes.status='active'` AND `published_at IS NOT NULL`, so count and page run
  over the same active population (matches adapter source lines 212-217).

## Observation (NOT a #605 regression)
The profile hero count ("公開ノート") shows **5**, one more than the 4 listed.
That count is sourced from `getPublicProfile` → `findPublicByOwner`, a separate
profile-level aggregate that is **outside #605's scope**. `findPublicByOwner`
filters `published_at IS NOT NULL` but does NOT join `notes.status='active'`, so
the trashed-but-public row (a5) is counted there. The null-pub row (a6) is
excluded by the `isNotNull` filter.

This is a pre-existing minor inconsistency in the profile hero aggregate, not
in the #605 listing/total path (which correctly excludes both). #605's
acceptance criterion — that the trashed/null rows do not leak into the
**listing items or its pagination total** — is satisfied. Not raised as a #605
defect; noted for the team.
