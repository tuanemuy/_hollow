# TC-04 — P32 期間ファセット/検索が published_at 基準で絞り込む

Status: PASS

## Steps
1. Open `/search?q=zorptest`, wait networkidle (6 public hits).
2. Click「フィルター」to open the drawer; read the period facet counts.
3. Select「過去 7 日」(radio) and observe narrowed results.
4. Open `/search?q=zorptest&period=1y` and confirm the >1yr note is excluded.

## Seed timeline (now = 2026-06-09); published_at vs date_for_calendar diverge
| note | published_at | date_for_calendar |
|---|---|---|
| apple  | 2026-06-08 (1d) | 2024-06-09 (2yr) |
| bob    | 2026-05-20 (~20d) | — |
| alicia | 2026-05-20 (~20d) | — |
| banana | 2026-05-01 (~39d) | 2026-05-01 |
| cherry | 2026-01-15 (~5mo) | 2026-01-15 |
| date   | 2025-04-01 (>1yr) | 2026-06-01 (8d) |

## Observations
- Facet counts in the drawer: 過去7日=**1**, 過去30日=**3**, 過去1年=**5**, すべて=**6**.
  These match the published_at windowing exactly:
  - 7d = {apple} = 1
  - 30d = {apple, bob, alicia} = 3
  - 1y = {apple, bob, alicia, banana, cherry} = 5
  - all = +{date} = 6
- Selecting「過去 7 日」(`?period=7d`): result list narrows to exactly **1**
  (Apple) — matching the facet count.
- `?period=1y`: exactly **5** results; **Date Note is excluded** despite its
  recent date_for_calendar (2026-06-01), because its published_at (2025-04-01)
  is >1yr ago.
- The facet count and the actual filtered result count agree in every window.

## Discrimination (decisive)
If the windows used `date_for_calendar` instead of `published_at`:
- Apple (cal 2024-06-09) would NOT be in 7d, and
- Date (cal 2026-06-01) WOULD be in 30d.
Neither happened → the facet/search period filter is published_at-based per #605.

## MATCH vs LIKE note
`zorptest` (>3 chars) drives the FTS5 trigram MATCH path. The LIKE-fallback
path is for keywords shorter than the trigram minimum; that branch's identical
period-window behavior is covered by the integration tests
(`countPublicSearchFacets.integration.test.ts` / adapter tests) rather than
re-derived in the browser. UI wiring confirmed on the MATCH path.
