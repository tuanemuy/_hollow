# Round 1 レビュー — 要件カバレッジ・スコープ整合性（Issue #689）

レビュアー視点: Issue の受け入れ条件カバレッジ・スコープ整合性
対象: `.issue/689/plan.md` / `.issue/689/adr.md`

## サマリー

- 問題点: 1 / 改善提案: 3
- `[P-001]` ディレクトリ行ラベルがモックの「場所」と AC-4・ステップ記述で不一致（実装でラベルを取り違えるリスク）
- `[S-001]` AC-6（ADR 記録）の ADR-001〜004 を AC との対応で明示すると検証性が上がる
- `[S-002]` 「新規ディレクトリ作成導線」が AC-4 文言に明示的に列挙されていない
- `[S-003]` 未確定 tagDraft の確定ルールを AC-2 に検証文として昇格すると回帰防止が強まる

---

#### 問題点（要修正）

- **[P-001]** ディレクトリ行のラベル文言がモックと計画で食い違っている
  - 理由: モック `spec/design/pages/P12-editor.html:985` は `<span class="dir-label">場所</span>` であり、ラベルは「**場所**」。一方で AC-4（plan.md:20）は「ディレクトリ行がモックの単一 pill トリガー…」とだけ書き、ステップ 6b（plan.md:143）の `label` 既定値は「場所」と正しく書かれているが、ADR-003（adr.md:60, 89）やステップ記述には「`場所` ラベル」「ディレクトリ行」「`場所` を選択」と表記が混在している。現実装 `DirectoryPicker.tsx:177` は `ディレクトリ` というラベルを描画しているため、完全移行で「モック準拠」を謳いながらラベルだけ現状の「ディレクトリ」を引き継ぐ取り違えが起きやすい。Issue 本文も「ラベルは『**場所**』（『ディレクトリ』ではない）」と明示的に注意喚起している（Issue 残存乖離3の記述）。
  - 提案: AC-4 に「pill トリガーのラベルはモック準拠で『場所』にする（現状の『ディレクトリ』から変更）」を検証可能な形で1文追記する。ステップ 6b の `label`（既定「場所」）はそのままで良いが、AC とステップで「場所」を SSOT として一貫させ、実装時にラベル変更が漏れない形にする。

#### 改善提案（検討推奨）

- **[S-001]** AC-6（ADR 記録）を ADR-001〜004 と紐づけて検証可能にする
  - 理由: AC-6（plan.md:22）は「方針判断が adr.md に ADR として記録されている」とだけ書かれ、対応ステップが「—」。実際には ADR-001〜004 が記録済み（タグ化・TagsInput 新設・ディレクトリ完全移行・本文枠線）。AC-6 に「ADR-001（タグ）/ ADR-002（TagsInput）/ ADR-003（ディレクトリ完全移行）/ ADR-004（本文枠線・padding/focus 温存）の4件が記録されていること」と列挙すると、4 受け入れ条件すべてに ADR が対応していることが一目で検証でき、漏れ確認が機械的になる。

- **[S-002]** AC-4 に「新規ディレクトリ作成導線」の保持を検証項目として明示する
  - 理由: AC-4 本文（plan.md:20）は「『新規ディレクトリを作成…』導線を備え」と含んでおり実質カバーされているが、これは現行 `variant="row"` の新規名 input（`DirectoryPicker.tsx:182-187`）からの機能移植であり、退行リスクが ADR-003 でも「本Issue最大の退行リスク」と指摘されている核心機能。AC-2（タグ保存契約）と同格で「pendingDirectoryName 経由の新規作成→保存で実体化」を独立した検証文として AC-4 から切り出すか太字化すると、テスト方針（plan.md:194, 196）との対応がより明確になる。スコープ的には既にカバー済みなので必須ではない。

- **[S-003]** 未確定 tagDraft の submit/autosave 時確定ルールを AC-2 の検証文に昇格する
  - 理由: ADR-001（adr.md:23）とリスク（plan.md:178）で「submit/autosave 時に非空 draft を確定してから送る」と確定済みだが、AC-2（plan.md:18）の文言は「追加・削除・保存・autosave が従来どおり機能し、tagNames が正しく構成される（重複排除・trim・順序保持）」までで、**draft 未確定分の救済**が AC レベルに現れていない。現行 `parseTagInput(state.tagInput)`（NoteEditor.tsx:240 / useAutosave.ts:186-192）は「テキスト全体」を常にトークナイズするため、配列ベースへ移行した後に draft の取りこぼしが起きると最も気づきにくい回帰になる。AC-2 に「入力途中（Enter 未押下）の draft が非空のまま submit/autosave した場合も当該タグが tagNames に含まれる」を1文追加すると、二層化リファクタの保存契約破壊（重点視点6）を AC で直接ガードできる。

#### 良い点

- 4 受け入れ条件（タグ/タイトル/ディレクトリ/本文枠線）＋ ADR 記録＋品質ゲートが AC-1〜AC-7 に**漏れなく**落ちている。AC↔Issue 受け入れ条件↔対応ステップの3列マッピングは追跡性が高い。
- ユーザー確定判断（タグ**チップ化**・ディレクトリ**完全移行**）が AC-1 / AC-4 と ADR-001 / ADR-003 に正しく反映され、却下された「差分許容」案を蒸し返していない。ADR-003 は #669 ADR-002 を明示的に supersede しており方針の連続性も担保されている。
- スコープ外（#688 最大幅・#692 フォーカス表現）の除外が「スコープ/含まれないもの」節（plan.md:29-32）と ADR-004 の双方で明記され、特に ④ 枠線撤去が #692 のフォーカス表現と同一 className を触る連動リスクを「border/rounded の撤去のみに厳密限定」とリスク節（plan.md:180）まで一貫して扱っている。スコープ境界の混入なし。
- AC-2 が「タグ state 再設計が submit/autosave の保存契約を壊さない」を独立 AC として立て、reducer 純粋関数テスト（ステップ2・テスト方針）で回帰を担保する設計になっている。重点視点6 の懸念は計画レベルで適切に手当てされている。
- ディレクトリ完全移行で `DirectoryPicker` の props 契約・`variant="fieldset"`（Ingestion）を不変に保ち、影響を `row` に閉じ込める設計（ADR-003 / ステップ 6c）は、選択契約（directoryId XOR pendingDirectoryName）と submit/autosave を壊さない筋の良い分割。Ingestion 非回帰も AC-4 末尾とテスト方針（plan.md:195）でカバー。
- 各 AC が概ね検証可能な具体性（`leading-[1.12]`・`border-hairline`/`rounded-md` 除去・`mb-5`・listbox/option a11y 等）で書かれている。
