## 確認項目

### 1. 単一ファイルでの新フロー: 選択 → 推論待ち → プレビュー編集 → 登録

- **目的:** Issue 完了条件①「ファイル選択 → 推論待ち → 提案表示 → 登録／破棄 がひとつのモーダル／ドロワー内で完結」が単一ファイル時に成立すること
- **手順:**
  1. サインイン後、ヘッダー or サイドバーの「アップロード」ボタンを押下
  2. モーダルが開く（URL の hash が `#upload` になる）
  3. ドロップゾーンに対応形式のファイル（例: `.md` / `.txt`）を 1 件ドロップ or 選択
  4. モーダル内の表示が「LLM がタイトルとメタデータを提案中…」のスケルトンに切り替わる
  5. 数秒〜数十秒待つと、プレビュー編集フォームに遷移する
  6. タイトル・保存先ディレクトリ・タグ・Front Matter (JSON) の各フィールドが preview の初期値で埋まっていることを確認
  7. 各フィールドを編集してみる
  8. 「登録」を押下
- **期待結果:**
  - モーダルが閉じてノート詳細画面に遷移
  - 編集した内容（タイトル、保存先、タグ、Front Matter）がノートに反映されている
  - ヘッダー / サイドバー / ノート一覧ツールバーから操作した場合いずれもモーダルが正しく開く
- **確認ポイント:**
  - スケルトン表示中はキャンセル不可ではなく、モーダル右上の閉じるボタンで離脱可能
  - ステートが切り替わる際に画面のチラつきがないか

### 2. プレビュー編集中の「破棄」アクション

- **目的:** 完了条件①の「破棄」がモーダル内で完結する
- **手順:**
  1. 確認項目 1 と同じ手順でプレビュー編集フォームまで進む
  2. 「破棄」ボタンを押下
  3. Confirm ダイアログで確定する
- **期待結果:**
  - モーダルが閉じる
  - `/upload` ページに移動してもキューに該当ジョブが見えない（discarded は既定除外）

### 3. プレビュー編集中の「キャンセル」アクション

- **目的:** モーダルを閉じてもジョブはキューに残ること
- **手順:**
  1. 確認項目 1 と同じ手順でプレビュー編集フォームまで進む
  2. 「キャンセル」ボタンまたはモーダル右上の閉じるボタンを押下
- **期待結果:**
  - モーダルが閉じる
  - `/upload` ページに移動すると `previewing` ジョブとしてキューに残っており、`IngestionJobRow` カードから commit / discard を続行できる

### 4. 複数ファイル一括投入

- **目的:** ADR-003 の判断（複数ファイル時は全件キューに積み、キュー画面誘導）が成立する
- **手順:**
  1. アップロードモーダルを開く
  2. ドロップゾーンに 3 件以上のファイルを同時ドロップ
- **期待結果:**
  - モーダル内に「N 件をキューに追加しました。準備ができたものから順にキュー画面で編集できます」のような通知が表示される
  - キュー画面（`/upload`）に移動すると、投入されたジョブがすべて並んでいる
  - 各ジョブカード（`IngestionJobRow`）から commit / discard が動作する

### 5. Front Matter の raw JSON 編集

- **目的:** 完了条件①「Front Matter を編集可能」を MVP の raw JSON 編集で満たす
- **手順:**
  1. プレビュー編集フォームに進む
  2. Front Matter フィールド (raw JSON textarea) を編集して保存
- **期待結果:**
  - 編集した Front Matter がノートに反映される
  - 不正な JSON を入力して「登録」を押すと、エラーメッセージ（`FRONT_MATTER_JSON_INVALID` 相当）がインラインで表示される
  - エラー時に他のフィールド入力値は失われない

### 6. `/upload` ページの位置付け再整理

- **目的:** Issue 完了条件②「取り込みキュー画面の位置付け再整理」
- **手順:**
  1. `/upload` に直接アクセス
  2. ページ冒頭の説明文を確認
  3. 既存のキュー一覧（previewing / failed / processing のジョブ）が表示されていることを確認
- **期待結果:**
  - 説明文が「裏で進行中・失敗・プレビュー保留のアップロードを管理する画面」相当の文言になっている
  - `IngestionJobRow` カードから commit / discard が動作する（previewing で）
  - `UploadForm` 直接設置のフォールバックも引き続き使える

### 7. spec/design への反映

- **目的:** Issue 完了条件③「spec/design 配下のページ設計に新フロー反映」
- **手順:**
  1. `spec/pages/index.md` の P13 節を確認
  2. `spec/scenario/ingest.md` の B1 / B2 / B4 節を確認
  3. `spec/design/pages/P13a-upload-modal.html` を新規追加して 3 ステート + モバイル幅サンプルが表現されていることを確認
  4. 既存 `spec/design/pages/P13-upload.html` が `/upload`（キュー閲覧）として維持されていることを確認
- **期待結果:**
  - すべてのドキュメントで新フロー（モーダル内完結）が記述されている
  - フォローアップ Issue 化（本文 HTML 編集、再生成、failed retry）の方針も spec で「将来対応」として明示されている

## エッジケース・異常系

### 1. LLM 推論が長時間かかる場合（180 秒タイムアウト）

- **目的:** ADR-001 のポーリング戦略でタイムアウトに到達したときのフォールバック確認
- **手順:**
  - 開発時に `getIngestionJob` のレスポンスを「常に processing を返す」モックに差し替えて 180 秒待つ
  - もしくは大きめのファイル（PDF / 音声）で実機実行
- **期待結果:**
  - 「処理が長引いています。キュー画面で続きを確認できます」のメッセージが表示される
  - モーダルが閉じる、または「キュー画面へ」リンクが表示される
  - `/upload` でジョブが継続して見える

### 2. LLM 呼び出しが失敗した場合（job.status === "failed"）

- **目的:** ADR-007 で failed view のアクションを「破棄」「キュー画面で詳細を見る」に絞った挙動の確認
- **手順:**
  - LLM プロバイダー側で失敗を発生させる（モック注入か、無効な API キーで一時的に発生させる）
  - もしくは既存の failed ジョブを再現する手順がドキュメントにあればそれを利用
- **期待結果:**
  - モーダル内に失敗メッセージが表示される
  - 「破棄」「キュー画面で詳細を見る」の 2 アクションのみ
  - 「再試行」ボタンは表示されない

### 3. ポーリング中の権限エラー（他者所有ジョブを参照）

- **目的:** ステップ 4 のポーリング失敗時の挙動（Business 系エラーで即停止 → failed view）の確認
- **手順:**
  - 通常のユーザー操作では発生しないため、開発時に jobId を他者のものに改ざんしてポーリングを発火させる
- **期待結果:**
  - `ForbiddenError` / `NotFoundError` でポーリングが即停止
  - failed view に遷移する

### 4. 不正な Front Matter JSON

- **目的:** 確認項目 5 の異常系
- **手順:**
  - Front Matter テキストエリアに `{not: "valid"` 等の不正 JSON、または `[]` / 文字列リテラルなど Record でないものを入力して登録
- **期待結果:**
  - `BusinessRuleError("FRONT_MATTER_JSON_INVALID")` 相当のエラーメッセージがインラインで表示される
  - 他フィールドの入力は保たれる

## 既存機能への影響確認

- **`/upload` ページの既存挙動**: 説明文書き換え後も `UploadForm` でファイル投入できることを確認（フォールバック動線）
- **`IngestionJobRow` の既存ボタン**: previewing カード上の commit / discard / regenerate が引き続き動作（regenerate は既知の LLM 再駆動なし問題があるが本 Issue では現状維持）
- **`commitIngestionPreviewFn` の既存利用**: `IngestionJobRow` から呼ばれる commit が引き続き動作（`frontMatterJson` 未指定でも壊れない）
- **`getIngestionJobs` の挙動**: discarded ジョブが既定除外される挙動が維持
- **`AppShell` の同期性**: 認証ルート全体でレンダリングに遅延が出ないこと（`getDirectoryTreeFn` は AppShell 同期 I/O ではなくモーダル内で client lazy load）
