# ドメイン設計レビュー 001

## 観点別チェック結果

### 実装可能性
- [問題1] `note.md` の `Note.updateContent` は `editLock` のチェックを要するが、引数の `expectedLockHolder` を「ロックを取得していない場合（書き込みのみ）」と「自分のロックで書き込む場合」のどちらも扱う設計か曖昧。意図と挙動を明示すべき
- [問題2] `ingestion.md` の `IngestionService.process` は依存が多い（11個）。ファクトリ的に分割するか、`deps` 型を `IngestionDeps` として明示すべき
- [問題3] `search.md` の `SearchDocument.update` は `NoteSnapshot` 型に依存しているが、`NoteSnapshot` 型の定義がない。値オブジェクト or 型エイリアスとして定義する必要
- [問題4] `view.md` の `BrokenConditionMarker` の `id` フィールドが `string` で型がゆるい。`TagId | DirectoryId | NoteId` のユニオンにすべき

### アーキテクチャ適合性
- [問題5] `tag.md` の `TagService.mergeInto` は `NoteRepository` に依存しており、tag → note の参照を作る。`index.md` の依存方向（note → tag）と矛盾。Tag のマージに伴う Note 側の更新はユースケース（あるいは別の Orchestrator）が責任を持つべき
- [問題6] `search.md` の `SearchService.applyIndexJob` が `NoteRepository / DirectoryRepository / TagRepository / PublicationStateRepository` を直接参照している。Search → Note 等の方向は許容済みだが、複数ドメインのリポジトリをサービス内部で扱うのはオーケストレーション過剰。Snapshot は Note の SaveNoteUseCase が Outbox イベントに含めて流し、Search 側は SearchDocument だけを受け取る設計に寄せたい
- [問題7] `publication.md` の `PublicationService.revokeAllLinks` は `ShareLinkRepository` だけを使うので OK。一方、`PublicationState.changeVisibility` の遷移時に link revoke を「DomainService が連動」と書いたが、エンティティの振る舞いの説明と DomainService の責任が混線。エンティティ振る舞いから連動責任の記述を外し、Service 側に集約する

### ビジネスロジック網羅
- [問題8] `identity.md` の `User` に「メールアドレス変更時の旧アドレス通知」が振る舞いとして現れない。これは `EmailSender` ポート経由でユースケースが担うが、`changeEmail` の前後でどの通知を送るかをドメイン設計でフックポイントを明確にしておくべき（具体は usecase）
- [問題9] `media.md` の `MediaAsset.decrementRef` が `refCount === 0` で `orphan` に遷移するが、`status === 'attached' → 'orphan'` 以外の遷移（例: `pending → orphan`）について明示なし。`pending` から始まり一度も `attached` にならず参照が外れたケースの扱いを書く
- [問題10] `note.md` で `Note.duplicate` 相当の振る舞いが明示されていない。P11 で「複製」操作が定義されているのに、ドメイン層に存在しない。`NoteService.duplicateFrom(source: Note, deps): Note` として書く
- [問題11] `directory.md` の `Directory.deleteCascade` がポート側に書かれている（リポジトリのメソッドとして）。これはドメインサービスとして書くべき。ポートは永続化操作のみ
- [問題12] `export.md` の `ExportJob` で「公開ノートを訪問者が個別エクスポートする」シナリオの権限制御が明示なし。`ExportService.assertCanAccess(job, requestingUser: User | null, noteVisibility: Visibility): void` を加えるべき

### トレーサビリティ
- 各シナリオ A〜I を順に各ドメインのユースケース概要と突き合わせ、漏れがないかチェック:
  - A1〜A6: Identity でカバー
  - B1〜B5: Ingestion でカバー
  - C1〜C6: Note + Ingestion + Media でカバー
  - D1〜D6: Directory + Tag + Note でカバー
  - E1〜E5: Note + Search + View でカバー
  - F1〜F5: Publication + Search でカバー
  - G1〜G3: Export でカバー
  - H1〜H4: Note + Media でカバー
  - I1〜I5: AdminSettings でカバー

## 修正方針

- A: `note.md` の `updateContent` の引数を `actorUserId: UserId, requireLock: boolean` に整理
- B: `ingestion.md` に `IngestionDeps` 型を定義
- C: `search.md` に `NoteSnapshot` 型を定義
- D: `view.md` の `BrokenConditionMarker.id` をユニオン型に変更
- E: `tag.md` の `TagService.mergeInto` から `NoteRepository` 依存を外し、`computeMergeOps(source, target): { fromTagId: TagId; toTagId: TagId }` のみ返す。Note 側の更新はユースケースが行う
- F: `search.md` の `applyIndexJob` を「Note 側のユースケースが NoteSnapshot を構築して SearchDocument を作る」設計へ変更。SearchService は SearchDocument を受け取ってインデックスに反映するだけにする
- G: `publication.md` の `PublicationState.changeVisibility` 振る舞い説明から「ShareLink 連動」を外し、`PublicationService.changeVisibilityAndCascade(state, ...)` に集約
- H: `identity.md` の `changeEmail` 説明に「ユースケース層で旧アドレス通知の発火が必要」と注意書きを追記
- I: `media.md` の `MediaAsset.decrementRef` に「`pending` → `orphan` も可」と明記
- J: `note.md` に `NoteService.duplicate(source: Note, now: Instant, idGen: IdGenerator, repo: NoteRepository): Promise<Note>` を追加
- K: `directory.md` の `DirectoryRepository.deleteCascade` を削除し、`DirectoryService.deleteSubtree(dir, deps): Promise<void>` を新設
- L: `export.md` に `ExportService.assertCanAccess(job, viewerOwnerId: UserId | null, noteVisibilityMap: Map<NoteId, Visibility>): void` を追加
