# DB設計レビュー 001

## 観点別チェック結果

### エンティティ・値オブジェクトの永続化網羅
- Identity: users (User 集約) / accounts (CredentialStore plumbing) / sessions (SessionService plumbing) / verifications (VerificationChallenge plumbing) ✓ — スキーマは better-auth 規約に準拠 (アダプタ実装の都合)
- Directory: directories ✓（ルートはユーザー作成時に同テーブルに作成）
- Note: notes / note_tags / note_internal_links / note_media_refs ✓
- Tag: tags / tag_blacklist ✓
- Publication: publication_states / share_links ✓
- Ingestion: ingestion_jobs ✓（preview は JSON で保持）
- Media: media_assets ✓
- Export: export_jobs ✓
- Search: search_documents / search_documents_fts / index_jobs ✓
- View: saved_views ✓
- AdminSettings: instance_settings / user_prompt_overrides ✓
- Outbox: outbox_events ✓

### カラム型・制約とドメインモデルの整合
- [問題1] `notes.front_matter_json` のサイズ上限が DB レベルで強制されていない。SQLite は TEXT 長制限が緩いため、value object の validation で 64 KiB に制限する旨をドメイン側で担保しているが、巨大な値が入る恐れあり。アプリ層で BYTE 数チェックを行うことを明示
- [問題2] `notes.content_html` も 1 MiB 上限がドメイン側のみ。同上
- [問題3] `directories` のルート一意制約（`parent_id IS NULL` で 1 オーナー 1 行）は SQLite の部分 UNIQUE インデックスで表現可能（`CREATE UNIQUE INDEX uniq_directories_owner_root ON directories(owner_id) WHERE parent_id IS NULL`）。表現していないため追加が必要
- [問題4] **解消済み**: ドメインの `User` 集約から credential を切り離し、`CredentialStore` ポート裏に分離した結果、パスワードハッシュは `users.password_hash` ではなく `accounts.password` (provider_id='credential' の行) に格納される構造になった。`User` は credential を所有しないため `users` 表に credential 用 NULL 制約問題は存在しない。SSO / Magic Link / Passkey 等の追加時は `accounts` に新しい provider_id 行を追加するだけでドメイン側無変更で対応可能 (Credential を集約化していない設計判断のメリットが効く)
- [問題4-a] **better-auth 規約準拠の再評価**: スキーマが better-auth 規約に全面置換されたので、Identity 関連の他項目も同前提で再評価する:
  - `users.email_verified` / `banned` / `ban_reason` / `ban_expires` は better-auth が書き込み主体。アダプタの `userRepo.save` 実装が `User.suspend` で `banned=1` / 関連列 NULL を書く方針は `database/index.md` の users 注記で明示済み (better-auth の自動 unban に依存しない)
  - インデックス `idx_users_role_banned` (role, banned) は管理者一覧クエリ (admin が member 一覧から banned ユーザーを除外 / 含める切替) に最適。旧設計 `idx_users_status_role` から置換した結果、`deleted_at` での絞り込みは `idx_users_deleted_at` で対応 (active ユーザー一覧用)
  - `accounts.user_id` の FK は `ON DELETE CASCADE` だが、アダプタの論理削除方針 (deleted_at 立て) では物理削除されないので発火しない。`User.markDeleted` のアダプタが `accounts` 行を明示的にクリーンアップする必要あり (`database/index.md` users 注記参照)
  - `sessions.user_id` の FK も同様。論理削除時は `sessionService.revokeAllForUser` で revoke する (物理削除は CASCADE に頼らない)
- [問題5] `note_internal_links` の `ref_target` の型サイズ。`ref_kind='title'` のときは最大 200 字、`ref_kind='id'` のときは UUID 36 字。CHECK 制約で長さを縛れる
- [問題6] `share_links.locked_until` を inequality 検索で使うため `idx_share_links_locked_until` を追加すると失敗ロック中の判定が速い

### 正規化
- 大量更新が発生する `tags.note_count` を導出値として持つかは設計判断。集約整合のためエンティティとして持つ方針なら維持。重要な操作（Tag のリネーム / マージ）でこの値が正しく増減することは usecase で担保
- 内部リンク・タグ参照は join テーブルで正規化済み

### パフォーマンス
- [問題7] `notes` の検索（`findByOwner with tagIds`）のインデックスがない。`note_tags(tag_id, note_id)` で逆引き可能だが、複数タグ AND 検索は join 多発する。MVP では Search ドメイン経由（FTS）に寄せる方針を明示
- [問題8] `outbox_events` のディスパッチ済みエントリは増え続ける。一定期間で物理削除するパージワーカが必要 → アプリ側（pruner）で対応する旨を database.md にも明記

### データ整合性
- 外部キーの ON DELETE 戦略を統一: ユーザー削除で CASCADE、ノート参照で RESTRICT / SET NULL を場合分けして適用済み
- [問題9] `note_media_refs.media_id` を `ON DELETE RESTRICT` にしているが、note 側カスケード削除で note_media_refs の行が消えれば OK。ただし media_assets を物理削除する側からは note_media_refs が残っていると消せないため、`MediaService.purge` の前に note_media_refs を確認する必要があると明記

## 修正方針

- A: `notes.front_matter_json` `notes.content_html` の長さチェックはアプリ層で行う旨を脚注に明示
- B: directories のルート部分 UNIQUE インデックスを追加
- C: ~~users.password_hash の MVP 制約を明示~~ → ドメイン分離により解消 (User 集約は credential を持たず、CredentialStore ポート裏で provider 別管理)
- D: `note_internal_links.ref_target` に長さ CHECK を追加（または最大値を明示）
- E: `share_links` に `idx_share_links_locked_until` を追加
- F: notes のタグ AND 検索は FTS（search_documents）経由を推奨と明示
- G: outbox_events のパージワーカ運用を database.md に明記
- H: media_assets 物理削除前提条件を脚注に追加
