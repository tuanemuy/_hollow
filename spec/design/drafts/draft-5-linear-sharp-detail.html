Hexagonal Architecture を Cloudflare Workers で実装する

Created2026-04-22
Updated2026-05-16 14:02
DirProjects/Hollow
Tags architecture cf
PublishPublished

このノートは Hollow のバックエンドで採用しているヘキサゴナルアーキテクチャを、 Cloudflare Workers + D1 + Queues の制約のもとでどう実装したかをまとめる。 関連: Outbox パターン Unit of Work

1. 依存方向の規律

レイヤーは内向きに依存する。 presentation → application → domain。 アダプターはそれぞれが依存するポート (=インターフェース) よりも一段内側に定義された型に従う。 つまり app/core/adapters/d1/ は app/core/domain/ および app/core/application/ の型に依存するが、 その逆は起きない。

Make illegal states unrepresentable. ランタイムチェックに頼る前に、まず型で表現できないかを考える。

1.1 ポートとアダプター

ドメインは NoteRepository のような純粋なインターフェースを定義する。 アダプター層 (D1NoteRepository) はそれを実装するが、ドメインからは見えない。 DI は serverCloudflare.ts でのみ行う。

// app/core/domain/note/repository.ts
export type NoteRepository = {
  findById(id: NoteId): Promise<Note | null>;
  save(note: Note): Promise<void>;
};

2. Unit of Work と Outbox

状態変更を伴うユースケースは必ず UnitOfWorkProvider.run(fn) の中で実行する。 ドメインイベントは UoW の中で ctx.events.publish(event) を介して収集され、 トランザクション内で outbox テーブルに永続化される。

  • UoW は 必要なリポジトリだけ を ctx.repos 経由で公開する
  • ドメインイベントは UoW の外では 発火不可能 (静的に)
  • Relay worker は lease 付きで行を claim する
  • クラッシュした worker の claim は lease lapse 後に再取得可能

2.1 配信保証

配信は at-least-once、順序保証なし。consumer は冪等でなければならない。 これは NOTE-0098 の運用ルールに従う。

4. 移行とリリース手順

  • ドメインモデルを純粋関数として再実装
  • D1 アダプターを drizzle-orm で実装
  • Outbox relay worker をデプロイ (cron 30s)
  • DLQ consumer の再試行戦略を確定
  • 統合テストを miniflare で完備する
