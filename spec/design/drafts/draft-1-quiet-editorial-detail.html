戦略メモ: Hollow のポジショニング再考

Hollow は「個人の文章・素材を、整理されたまま静かに保管する場所」をつくる試み。Notion でも Obsidian でもなく、アップロード起点で素材を集めて、HTML ノートに正規化し、必要なものだけ自分のドメインで公開できる。検索より「整理されている状態」を売る。

背景

文章・PDF・スライド・音声メモが、Drive / iCloud / ローカル / ブラウザのブックマークに分散している。あとから読める状態にあるものはほぼない。一方で書き散らした下書きは GitHub Gist や Notion に残るが、検索はできても「眺める」ことができない。

"The bottleneck is not storage, it is the work of arrangement." — 自分用に書き写したメモから

素材は十分にある。整理されていないだけだ。

現状の問題

  1. 取り込み口（upload, drag & drop, 音声録音）がツール毎に分断されている。
  2. 取り込んだ後の 正規化 ステップがどこにもない。PDF は PDF のまま、画像は画像のまま。
  3. 公開／非公開の境界がツール側の都合で決まっている。

方針

次の [[Q2 ロードマップ]] と [[Hollow MVP 範囲]] はこの方針に従う。

  • 取り込みは PDF / Office / Markdown / HTML / 画像 / 音声を等価に扱う。
  • 取り込み後、サーバー側で HTML ノートに変換し、すべての素材を同じレンダリングで読めるようにする。
  • ノートはディレクトリツリーで整理する。タグはセカンダリ。
  • 公開は「非公開 / リンク共有 / 完全公開」の 3 段階。デフォルトは非公開。

MVP に含めるもの

  • ファイルアップロードと HTML ノート化（PDF / Markdown / 画像）
  • ディレクトリツリーとタグ
  • ノート間リンク（[[note]] 構文）と簡易バックリンク
  • リンク共有による限定公開
  • 独自ドメインへの公開（custom domain）

競合との位置取り

整理コストと公開コストの 2 軸で見ると、Hollow は 整理コスト：中・公開コスト：低 の象限に置く。Notion の database 機能や Obsidian のグラフは意図的に持たない。

ツール 取り込みの軽さ 整理 公開
Notion中強い（DB）中（notion.site）
Obsidian低（手動）強い（graph）弱い（plugin 依存）
Bear / Apple Notes高弱いなし
Hollow高（upload 起点）中（tree + tags）強い（独自ドメイン）

非機能要件のメモ

Cloudflare Workers + D1 + Queues 上で動かす想定。アップロードした素材の HTML 化は Queue 経由でバックグラウンド処理。失敗時のリトライは Outbox パターンで吸収する。 

// app/worker/cloudflare/relay.ts
export const relay = async (env: Env) => {
  const rows = await claimOutbox(env.DB, { limit: 32, lease: 60_000 });
  for (const row of rows) {
    try {
      await env.QUEUE.send(row.payload);
      await markDelivered(env.DB, row.id);
    } catch (err) {
      await releaseLease(env.DB, row.id);
      // 連続失敗は DLQ に流す
    }
  }
};

残課題

  • 音声の文字起こしを Workers AI で完結させるか、外部サービスを併用するか。
  • 独自ドメイン公開のドメイン検証 UX。
  • 取り込み元別のメタデータ正規化（撮影日時、PDF のページ単位など）。
