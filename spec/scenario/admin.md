# I. 管理者設定

## I0: 初期管理者の登録（Setup Token）

参照: [ADR 007](../adr/007-admin-setup-token.md)

### 正常系
1. 運用者がデプロイ時に `wrangler secret put ADMIN_SETUP_TOKEN` で十分なエントロピー（32 字以上）のトークンを設定する
2. 運用者（初期 admin になる本人）が `/setup` を開く
3. ユーザー名 / メール / パスワード / 表示名（任意）/ Setup Token を入力する
4. 登録が完了し、確認メールが送られる
5. メール内の確認リンクを開くと `VerifyEmail` ユースケースが実行されアカウントが有効化され、通常 SignUp と同じく自動ログインが試みられる（成功するとホームへ遷移）。本ステップの挙動は通常 SignUp と共通で、admin 固有の差異は作成時の `role=admin` のみ
6. 初期 admin の登録が済んだら、運用者は `wrangler secret delete ADMIN_SETUP_TOKEN` で env をクリアして Setup Token を無効化することが推奨される（追加 admin を作る必要がない場合）

### 異常系
- `ADMIN_SETUP_TOKEN` が未設定: `/setup` ページは 404 を返し、API 側も `AuthenticationError('setup_token_disabled')` を返す
- Setup Token 不一致: 「Setup Token が正しくありません」を表示（列挙対策で「未設定」と「不一致」は UI 文言を区別しない方針も検討余地あり）
- ユーザー名 / メール衝突 / パスワード強度不足: 通常 SignUp と同じエラー UI
- `registration.open === false` の状態: それでも実行可能（Setup Token 検証が通れば、登録停止中でも admin を作れる）
- 確認メールのリンク期限切れ: 通常 SignUp と同じく再送導線を表示
- 自動ログイン失敗（`VerifyEmail` 内で `SessionService.issue` が失敗、`ExternalServiceError(service: 'session')`）: アカウントは既に `active` 化済み。「メール確認は完了しました。ログイン画面からサインインしてください」を表示し、手動 LogIn で復帰可能（通常 SignUp と共通の挙動）

### 補足
- 2 人目以降の admin を増やすには (a) Setup Token を共有して `/setup` から登録する、(b) 既存 admin が `PromoteUserToAdmin` で member を昇格させる、の 2 方式がある
- Setup Token は env が設定されている限り何度でも使える。漏洩リスクを下げるため、不要になったら速やかに env を削除する
- 運用者本人にも利用規約への同意 (`acceptTerms`) を求める。これは通常 SignUp と同じ DTO 形状を踏襲することで「セルフホストの運用者であってもこのインスタンスを使うエンドユーザーである」という建前を崩さないため。利用規約自体は運用者がインスタンス設定で差し替え可能（規約の妥当性は運用者責任）

## I1: LLM API キーの設定・差し替え

### 正常系
1. 管理者がインスタンス設定画面 → 「LLM」セクションを開く
2. MVP では LLM プロバイダは単一固定（Anthropic Claude を既定とする）。API キーとモデル名のみ管理者が設定する
3. 値は環境変数を優先し、未設定時のみインスタンス DB に保管（保管時は暗号化）。両方ある場合は環境変数が勝つ
4. 接続テスト（軽量プロンプトでの呼び出し）を実行し、成功・失敗を表示
5. 保存すると、以降の取り込み・編集系で新しい設定が使われる

### 異常系
- キーが空 / 不正フォーマット: 保存前に弾く
- 接続テスト失敗: エラー詳細（ステータス / メッセージ）を表示し、保存は任意
- API クォータ枯渇: 取り込みが失敗し、管理画面に通知バナーが出る

## I2: カスタムプロンプトの設定

### 正常系
- インスタンスレベルのデフォルトプロンプト（`structure` 取り込み構造化 / `title` タイトル生成 / `directory` ディレクトリ提案 / `metadata` メタデータ抽出 / `ocr_assist` OCR 補助 の 5 種）を編集
- 上書きがあるプロンプトには「上書き中」バッジを表示。未上書きのプロンプトは「LLM プロバイダの既定指示を使用」と表示
- 各プロンプトに「この項目をリセット」ボタンがあり、上書きを削除して既定値に戻せる（未上書きの項目では disabled）
- 「すべてのプロンプトをリセット」ボタンで全上書きを一括削除可能（確認モーダル経由）
- ユーザーは個人プロンプトを上書き可能。インスタンスに上書きがあればそれを、なければビルトイン既定（= LLM プロバイダの既定指示）を継承
- プレビューとして「サンプル入力」に対する LLM 出力を試せる

### 異常系
- プロンプトに不正なテンプレート変数: 保存前に弾く
- プロンプト変更直後にエラー率が急増: ダッシュボードに警告

### 注記
- `ocr_assist` は OCR 機能の将来的プロビジョン。現状の ingestion パイプラインでは未参照だが、admin 画面では編集可能とする
- 「既定 = 空文字 = LLM プロバイダの既定指示にフォールバック」は `promptResolver` の不変契約。Issue #218 でも維持

## I3: デフォルトスタイル / デザイントークン

### 正常系
- 管理者がデザイントークン（CSS カスタムプロパティ）を編集可能
- プレビューでサンプルノートに即時反映を確認できる
- 上書き行ごとに「既定に戻す」ボタンがあり、その行を削除して即座に保存される
- 「すべてリセット」ボタンで全上書きを一括削除可能（確認モーダル経由）

### 異常系
- 不正な CSS 値: 保存前に弾く
- 大幅な値変更後の既存ノートのレイアウト崩れ: プレビュー段階でユーザーが気づける UI 配置

### 注記
- 既定値の SSOT は `app/styles/tokens.css`（`spec/design/tokens.md` にミラー）。admin UI には「上書きあり」の一覧のみを表示し、ビルトイン既定値の値リストは表示しない（Issue #218 ADR-003）

## I4: 新規ユーザー登録の許可・停止

### 正常系
- インスタンス設定 → 「登録」セクションで `公開 / 停止` を切替
- 停止中はサインアップ画面でその旨を表示し、操作不可
- 既存ユーザーには影響しない

### 異常系
- 停止中にトークン付き招待リンクを発行する仕組み（MVP では UI 余地のみ確保し、招待発行はスコープ外）
- 設定変更タイミングで進行中のサインアップトランザクション: 開始済みのフローは完了させる

## I5: 利用状況の確認（補助）

### 正常系
- ユーザー数、ストレージ消費（D1 / R2）、当日のアップロード数、LLM 呼び出し回数を確認できる
- アラートしきい値を超えると管理画面にバナー表示

### 異常系
- 指標取得失敗: 「指標が取得できませんでした」と表示し、再試行可
