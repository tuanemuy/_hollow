# ADR 005: ドメイン境界の切り方

## ステータス

承認済み（2026-05-15）

## コンテキスト

シナリオ・ページ設計から多数の責務が抽出された。これらをどの粒度のドメインで切るかにより、集約境界・トランザクション境界・実装の保守性が大きく変わる。

## 決定

11 ドメイン（Identity / Directory / Note / Tag / Publication / Ingestion / Media / Export / Search / View / AdminSettings）に分割する。

切り方の指針:
- 「ユーザー視点で意味のある主体」がほぼそのまま集約になる（Note, Directory, Tag, Publication, Ingestion job, Media asset, Export job, SavedView）
- 「アプリ運用面の関心事」は専用ドメインに分離（Identity, AdminSettings, Search）
- インデックス・派生データは Note とは別ドメイン（Search）に置き、Note 集約の不変条件と切り離す

集約境界:
- Publication は Note の一部にせず別ドメインに分離（限定公開リンクの集合管理・複数発行を独立して扱うため）
- Tag は Note の一部にせず別ドメインに分離（リネーム / 統合 / ブラックリスト等の独立管理が必要なため）
- FrontMatter と内部リンクは Note 集約内（Note の不可分のメタデータ）

## 検討した代替案

### Note 集約に Publication / Tag / Media をすべて内包する
- 利点: 集約が少なく、シンプル
- 不採用理由: 限定公開リンクの発行数や状態を Note の整合性境界に含めると、リンク 1 つの操作で Note 全体をロックする必要が出る。Tag のリネームも複数 Note にまたがるためミスマッチ

### Publication を Identity（ユーザー）の一部にする
- 利点: ユーザー単位の公開設定として一貫
- 不採用理由: 公開設定は Note 単位の属性。Identity に置くと Note と Identity の双方向参照が必要になる

### Search をドメインとして分けない（インフラ層に押し込む）
- 利点: ドメイン数を削減
- 不採用理由: 検索結果のランキングや公開フィルタの判定はビジネスルール。ポートだけでなく検索ドキュメントの集約として扱う方が再構築・テストが容易

## 影響

- 集約間参照は ID のみ。シナリオの「内部リンク」「公開設定変更」などは Outbox 経由のイベントで連携する
- 検索などのインデックスは UoW 内で同期更新しない（イベントで非同期）
- 各ドメインは独立してテスト可能
